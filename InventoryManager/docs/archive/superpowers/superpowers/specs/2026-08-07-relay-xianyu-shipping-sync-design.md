# 接力已寄出联动后一单与闲鱼发货设计

## 背景

接力管理在操作员把接力状态改为“已寄出”时，已经要求录入顺丰运单号，但目前只把运单号保存到接力记录，并刷新顺丰轨迹。后一单 rental 的寄出运单和发货状态没有同步，闲鱼订单也没有收到发货通知，导致接力页、甘特图和闲鱼订单状态不一致。

## 目标

当接力状态首次变为 `shipped` 时：

1. 将接力顺丰运单号写入后一单的 `ship_out_tracking_no`。
2. 将后一单 rental 状态改为 `shipped`。
3. 如果后一单没有 `ship_out_time`，写入本次操作时间。
4. 在本地事务提交后，复用 `XianyuOrderService.ship_order(successor)` 将后一单运单上报闲鱼。
5. 闲鱼同步失败不回滚本地“已寄出”状态，只向操作员显示失败原因。
6. 继续执行现有顺丰物流刷新，不受闲鱼同步结果影响。

## 非目标

- 不新增闲鱼同步状态字段或数据库迁移。
- 不新增自动重试、后台队列或重试按钮。
- 不修改现有独立“发货到闲鱼”功能及其按钮可见性规则。
- 不在接力直接跳到 `completed`、回退状态或重复保存 `shipped` 时自动上报闲鱼。
- 不改变接力状态机、绑定规则、顺丰运单校验和物流查询规则。

## 方案选择

采用“本地提交后同步闲鱼”的同步编排方案。

备选方案及不采用原因：

- 闲鱼成功后再提交本地：闲鱼失败会阻止本地标记已寄出，不符合已确认的业务规则。
- 异步任务或 outbox：可以提供持久重试，但本次不需要自动重试，并且无法在当前操作中给出直接的成功或失败结果。
- 从接力接口内部调用现有 HTTP“发货到闲鱼”接口：会把业务服务耦合到路由层并产生两次独立本地事务，不利于保持接力记录和后一单的一致性。

## 后端设计

### 本地事务

`RelayCaseService.update_case()` 保留现有锁、状态校验、接力绑定、里程碑和审计行为。仅在旧状态的顺序早于 `shipped` 且目标状态恰好为 `shipped` 时执行以下联动：

1. 校验并规范化 `sf_tracking_number`。
2. 保存 `relay_case.sf_tracking_number`。
3. 设置 `successor.ship_out_tracking_no` 为同一运单号。
4. 设置 `successor.status = "shipped"`。
5. 当 `successor.ship_out_time` 为空时，设置为本次 `now`；已有时间保持不变。

上述变化与接力状态、绑定、里程碑和审计在同一个数据库事务中提交。数据库提交失败时，所有本地变化一起回滚，也不调用闲鱼。

### 闲鱼同步

本地事务提交成功后，调用现有 `get_xianyu_service().ship_order(successor)`。该调用直接复用已有顺丰快递编码、闲鱼订单号和寄件方配置。

闲鱼同步结果规范化为：

```json
{
  "attempted": true,
  "success": false,
  "message": "没有闲鱼订单号"
}
```

- 成功：`success = true`，保留服务返回的消息。
- 缺少闲鱼订单号：视为已尝试但失败，使用服务的 `skipped` 原因作为提示。
- API 返回失败或抛出异常：捕获并转换为 `success = false` 和可展示的失败原因。
- 闲鱼失败不得抛出到本地事务，也不得回滚接力或后一单。
- 非首次进入 `shipped` 的操作返回 `attempted = false`，不重复上报。

服务返回结构化的 `RelayCaseUpdateOutcome`，包含 `relay_case` 和 `xianyu_sync`，避免通过临时模型属性在服务层和 handler 之间传递外部调用结果。接力 handler 用该结果组装现有 mutation payload。

接力更新接口返回 HTTP 200，并在现有 mutation payload 中增加 `xianyu_sync`。之后继续调用现有顺丰轨迹刷新；顺丰查询失败仍按现有逻辑保存 `query_failed` 摘要，不影响接口成功。

## 前端设计

桌面端和移动端的 `RelayCaseMutationResponse` 增加：

```ts
xianyu_sync?: {
  attempted: boolean
  success: boolean
  message: string
}
```

保存“已寄出”后的交互：

- `attempted && success`：显示“接力状态已更新，已同步闲鱼”。
- `attempted && !success`：显示警告“接力已标记已寄出，但闲鱼上报失败：{message}”。该操作仍视为保存成功，关闭维护弹窗并刷新列表。
- `!attempted` 或无该字段：沿用“接力状态已更新”。

不新增重试入口。操作员需要重试时继续使用现有独立“发货到闲鱼”功能。

## 错误与一致性

- 本地数据库失败：接口失败，接力与后一单全部回滚，闲鱼不调用。
- 闲鱼业务失败、缺配置、缺订单号或网络异常：接口仍成功，本地状态保持已寄出，并返回警告信息。
- 顺丰轨迹刷新失败：沿用现有 `query_failed` 记录方式，不覆盖闲鱼提示。
- 外部调用发生在本地提交之后，避免网络等待期间持有 rental 行锁。
- 本次不持久化闲鱼同步结果，因此刷新页面后不展示历史失败提示；这与“仅即时提示、使用独立按钮重试”的业务选择一致。

## 测试策略

后端使用隔离 MySQL 测试库覆盖：

1. 首次进入 `shipped` 时，后一单得到相同运单号、状态变为 `shipped`，空发货时间被填写。
2. 后一单已有 `ship_out_time` 时保持原值。
3. 闲鱼成功时返回成功同步结果。
4. 缺少闲鱼订单号、闲鱼业务失败及异常时，本地状态仍提交，接口返回 HTTP 200 和失败原因。
5. 数据库提交失败时不调用闲鱼且本地变化回滚。
6. 重复保存 `shipped`、改为 `completed` 或回退时不自动上报。
7. 现有顺丰轨迹刷新仍执行。

桌面端和移动端组件测试覆盖成功提示、失败警告，以及失败时仍关闭弹窗并刷新列表。最后构建两个前端并运行完整接力相关后端测试。
