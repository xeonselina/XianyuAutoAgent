## Context

现有 `rental_relay_bindings` 表表示甘特图重排不能拆分的永久接力关系，不适合表示尚未通知或尚未同意的运营进度。现有顺丰路由已能查询运单，但验证手机后四位为固定寄件人，接力场景需使用前单客户手机号。

## Goals / Non-Goals

- Goals: 实时候选识别、可持久运营状态、永久绑定同步、顺丰跟踪、PC 和移动管理页。
- Non-Goals: 其他快递公司、自动通知客户、自动创建运单、签收自动完成。

## Decisions

- Decision: 新增 `rental_relay_cases` 管理表，不扩展永久绑定表。这使“运营进度”与“重排约束”的语义保持独立。
- Decision: 待处理候选按请求实时计算，首次状态变更才写入管理表。这避免了 GET 写入和后台同步任务。
- Decision: 进入或退出 `agreed` 及之后状态时，在同一事务中创建或删除现有永久绑定。
- Decision: 顺丰查询抽取为共享服务，接力查询提供每笔运单自己的验证手机后四位。
- Decision: 桌面端使用宽表；移动端使用独立工作台，以状态快捷筛选、日期预设、紧凑卡片、折叠详情和大触控操作为核心。两端共享 API 而不共享视图组件。
- Decision: 前后配置差异在前端根据同一列表项已有字段计算。镜头组合值不同，或后单附件数组长度大于前单时，就地显示带具体原因的黄色告警，不增加后端派生字段。

## Risks / Trade-offs

- 实时候选扫描会增加列表查询成本。使用主 rental、非取消、日期范围和现有时间字段缩小数据集，并保持服务端分页。
- 已开始处理的组合可能与当前档期不一致。列表保留记录并显示 `schedule_changed`，不自动丢失运营上下文。
- 顺丰轨迹依赖客户手机号。缺少电话或外部服务失败不阻止已寄出状态，只记录可重试错误。

## Migration Plan

1. 创建 `rental_relay_cases` 表。
2. 为每个现有 `rental_relay_bindings` 行插入组合唯一的 `agreed` 记录，并使用绑定确认时间作为 `agreed_at`。
3. 部署后端 API 和共享顺丰服务。
4. 部署 PC 和移动页面及入口。
5. 回滚应用代码时可保留新表；旧甘特图和永久绑定不依赖新表。
