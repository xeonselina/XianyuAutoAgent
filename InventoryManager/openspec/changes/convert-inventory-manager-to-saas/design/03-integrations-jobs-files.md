## 8. Tenant Integrations and Secrets

### 8.1 One platform root key and deterministic database passwords

- Core 正常运行只维护一把 256-bit 随机 `PLATFORM_ROOT_KEY`。它是所有租户数据库密码和可恢复应用 Secret 的唯一密码学根，不再为每条记录生成或保存 DEK。不同用途必须通过 HKDF-SHA256 的固定 domain label 隔离，禁止把根密钥本身直接当作数据库密码、AES key 或 HMAC key 使用。
- `CryptoCodecV1` 统一编码所有 HKDF info 和 AAD：按协议规定顺序把每个字段编码成 `uint32 big-endian length || value bytes` 后拼接。协议/domain/provider 使用严格小写 ASCII；UUID 使用 RFC 4122 network-order 的原始 16 字节；generation/revision/version 使用 uint64 big-endian。provider 只接受固定枚举 `sf`、`xianyu`、`kuaimai`。`crypto_version=1` 固定对应 HKDF-SHA256 + AES-256-GCM，`aad_version=1` 固定对应本编码；任何字段类型、顺序、大小写或算法变化都必须发布新版本并保留旧解码器与固定测试向量。
- 代码实现单一、版本化的数据库密码派生组件，但按账号用途选择不同固定协议标识：租户 DML 账号使用 `inventory-manager/tenant-db-password/v1`，平台只读账号使用 `inventory-manager/platform-read-db-password/v1`。salt 均为不可变 `database_uuid` 的 RFC 4122 原始 16 字节，info 通过 `CryptoCodecV1` 继续编码 tenant UUID、database UUID、对应 credential generation、`root_key_version` 和 `derivation_version`。输出 32 字节并转为无填充 Base64URL 密码；两类固定测试向量锁定字节级协议并证明用途不同必得不同值。
- 宿主机每个根版本是 `/etc/inventory-manager/secrets/platform-root-key-v<N>` 普通文件，内容只能是一行 Base64（可有一个末尾换行），解码后必须恰好 32 字节；Base64 只是编码，不是加密。Compose 把获授权版本逐个只读挂载为 `/run/secrets/platform-root-keys/v<N>`，app/worker/provisioner 环境变量只保存该目录路径，不保存当前版本号或 key 内容。
- `platform_root_key_versions` 是活动版本的唯一权威来源：新派生/加密只使用唯一 active 版本，读取既有路由或密文时严格使用行内声明的 active/legacy 版本，并按 `version -> /run/secrets/platform-root-keys/v<N>` 读取。进程启动时对 Base64 解码后的原始 32 字节计算 SHA-256 指纹并核对；active 状态、挂载文件和指纹任一不一致即拒绝启动，新写入不得由环境变量另选版本。未知版本、文件缺失或指纹不符也不得遍历所有文件“试到成功”。
- 算法、salt、info 和源码都可以公开，根密钥不能写入代码、Git、镜像、普通 `.env`、日志、API、控制库或平台页面。生产 Linux 基线为目录 `/etc/inventory-manager/secrets` 使用 `root:<固定 app gid>` 与 `0750`，根密钥文件使用 `root:<固定 app gid>` 与 `0440`；容器固定非 root UID/GID，只向 app、worker、provisioner 挂载所需版本，不挂给 Nginx、前端或 MySQL。Compose `file:` secret 的权限以宿主机真实权限为准，不能依赖 YAML 的 `uid/gid/mode`。
- 相同根密钥与上下文必须产生相同密码；任一 tenant/database UUID、代数、用途或根版本不同必须产生无关联输出。控制库不保存租户密码的明文、密文或哈希，MySQL 自身只保存其账号认证材料。
- 连接 URL 在内存中由分离字段安全构造；派生值仅传给数据库驱动，不进入任务、共享缓存、异常、审计或日志。`inventoryctl db shell` 等维护工具调用同一派生库，但默认不显示密码。
- 日常租户数据库密码轮换只递增各账号用途自己的 `credential_generation`，无需更换平台根密钥。平台根密钥不做无意义的频繁定期轮换；仅在疑似泄露、算法升级或明确维护窗口中生成新版本。根密钥换代要求逐租户分别创建新的 DML 与平台只读数据库账号并切换对应路由，同时可重入地重加密全部外部 Secret、完整兑换码和平台管理员 TOTP seed；迁移窗口会短暂同时挂载旧/新两版，完成后恢复为只有一把活动根密钥。旧版离线副本保留到引用它的备份过期，或者明确接受旧备份恢复后重新录入外部凭证并通过 CLI 重绑平台 TOTP。
- 稳态在线只有一个 active 文件；换代期间在线为一个 active 加仍被现有记录引用的 legacy 文件；全部在线引用迁移后，旧版从服务卸载并标为 retired 离线归档。retired 不等于可销毁，只有备份 manifest 已无引用且恢复/合规保留期结束后才能经双人复核删除。
- 根密钥丢失不破坏租户业务表：可通过受控 provisioner 的 root-key recovery 模式先建立新根、重置租户 DML/平台只读 MySQL 账号并把新版本登记为唯一 active；普通 Web 在此之前继续拒绝启动。随后只开放受限的平台 setup/recovery 入口：平台管理员可用正确密码 + current generation 未使用恢复码重绑新 TOTP；恢复码也丢失时走 CLI 重置。控制库中的第三方凭证、完整兑换码和旧 TOTP seed 密文无法用新根恢复，必须从离线旧根找回或分别重新录入/作废/重绑。该流程只适用于当前控制库仍在而根密钥永久丢失；control/full 旧恢复点导入仍按 D58 作废旧平台认证材料，不能借恢复码绕过。上线门禁因此要求至少两份位于不同故障域的离线加密根密钥副本，并在正式对外前执行一次“恢复根密钥、派生两类测试数据库密码、解密测试 Secret”的演练；此后按 D30 由项目负责人按需手工重复，不建立固定周期。这是同一把逻辑根密钥的冗余副本，不是多把业务密钥。
- 平台根密钥不用于加密它自己的离线副本，也不替代云主机/数据库管理账号、短信供应商账号和备份存储凭证。这些是外部基础设施访问凭证，应由密码管理器、云账号恢复机制或独立受控配置管理；“只有一把根密钥”特指应用内部租户 Secret 体系，而不是整套生产环境只有一个 Secret。

### 8.2 Direct encryption of recoverable stored secrets

- D55 已确认 SaaS Core 完全不提供 tenant API key；Core 不定义对应数据表、哈希/加密 domain、鉴权中间件、创建/轮换/撤销/查看端点或前端 Secret 展示流程。本节的 tenant Secret 只指顺丰、闲鱼、快麦等第三方 provider integration credential，继续作为 write-only 集成配置加密保存，不能充当 tenant API 鉴权凭证。
- 顺丰、闲鱼、快麦凭证是外部给定值，需要重复查看的兑换码是系统随机生成值；二者都不能从租户 UUID 确定性重建，仍需可恢复加密，不能只存哈希或明文。
- 每次写入使用 `PLATFORM_ROOT_KEY` 经 HKDF-SHA256 派生记录级 AES key：salt 为随机不可变 `crypto_context_uuid` 的原始 16 字节，info 通过 `CryptoCodecV1` 依次编码 `inventory-manager/tenant-integration/<provider>/v1`、`crypto_context_uuid`、tenant UUID、provider、`secret_revision`、`root_key_version`、`crypto_version`，或依次编码 `inventory-manager/redemption-code/v1`、`crypto_context_uuid`、batch UUID、`secret_revision`、`root_key_version`、`crypto_version`。不同记录、用途、租户/provider、批次或修订不得得到相同 key；派生 key 只存在于当前进程的短生命周期内存中。
- `tenant_provider_account_secret_revisions` 使用独立 domain `inventory-manager/tenant-provider-account/<provider>/v1`；HKDF info 依次绑定 `crypto_context_uuid`、tenant UUID、provider、provider account UUID、不可变 integration UUID、`secret_revision`、根/协议版本，AAD 使用对应 `/aad/v1` domain 并额外绑定 `aad_version`。稳定 `tenant_provider_accounts` 行不保存该密文。月结账号不能复用 tenant-integration 的 domain/key；改绑 API connection 时创建新 account 记录并迁移 warehouse binding，不能原地修改进入密码学上下文的 integration UUID。
- `platform_admin_totp_credentials` 使用独立 domain `inventory-manager/platform-admin-totp/v1` 和对应 AAD domain，绑定 credential UUID、platform admin UUID、secret revision 及根/crypto/aad version；不得复用租户 Secret、短信验证码或兑换码 domain。TOTP seed 使用新随机 nonce 的 AES-256-GCM 密文保存，恢复码另行高熵生成并只存不可逆摘要，二者不能互相推导。
- 月结账号全局查重不比较 AES-GCM 密文，也不保存可被枚举的普通 SHA。服务端先按 provider 固定版本规则规范化输入，再从当前平台根密钥以独立 domain `inventory-manager/provider-account-fingerprint/<provider>/v1` 派生 HMAC-SHA-256 key，计算 32 字节 fingerprint，并由控制库唯一索引取得 claim。fingerprint 与加密账号使用不同派生用途；租户 API、日志和普通审计均不得返回 fingerprint。平台根密钥换代时暂停 provider account 新增、绑定、解绑和转移写入，在同一全局 lease 下解密全部有效账号、计算 shadow fingerprint、验证全平台无重复后原子切换活动 fingerprint 版本；迁移完成前 resolver 同时校验版本与 claim，任何部分迁移或不一致均 fail closed，不能让旧/新 key version 分区绕过唯一性。
- 使用 AES-256-GCM 直接加密，每次加密必须由 CSPRNG 生成新的 96-bit 随机 nonce，并保存完整 `ciphertext || 16-byte tag`。integration AAD 通过 `CryptoCodecV1` 依次编码 `inventory-manager/tenant-integration/aad/v1`、`crypto_context_uuid`、tenant UUID、provider、`secret_revision`、`root_key_version`、`crypto_version`、`aad_version`；redemption-code AAD 依次编码 `inventory-manager/redemption-code/aad/v1`、`crypto_context_uuid`、batch UUID 及同样四个数值版本字段。不得使用普通字符串拼接、非规范 JSON、状态、显示名称、`last_verified_at` 或其他可变业务字段。把密文、nonce 或元数据调换到另一租户、provider 或兑换码时必须认证失败。控制库只保存密文、nonce、修订和版本，不保存派生 key 或逐条 DEK。
- 兑换码遵循第 7 节固定的 26 字符生成与规范化协议；`lookup_hash = SHA-256(normalized_code)` 仅用于稳定匹配，完整码只从认证密文解密。由于原始码具有 130 bit entropy，查找摘要不承担加密或低熵口令保护职责。
- 集成设置接口只返回 `configured`、掩码提示、最近验证时间和状态；更新 secret 采用 write-only 字段。只有具备专门平台权限的兑换码查看接口可以返回完整码，且每次查看写不可变平台审计。凭证只通过短生命周期内存对象传给有权限的 provider adapter，不进入共享缓存、日志、异常或审计 before/after。
- 普通 integration Secret 或 provider-account Secret 更新都不得覆盖旧 revision 的密文。稳定 `tenant_integrations` connection 行与稳定 `tenant_provider_accounts` account 行分别只保存各自的 `current_secret_revision_id` 和非秘密配置/当前 claim 引用；每次创建或更新凭证都预分配新的 immutable secret-revision UUID 和单调 `secret_revision`，以新的随机 nonce 分别写入独立、只追加的 `tenant_integration_secret_revisions` 或 `tenant_provider_account_secret_revisions`，并保存对应 integration/account、tenant/provider、crypto context、密文、根/crypto/AAD 版本、创建动作和验证结果。迁移时把既有 connection/account 行中的 ciphertext/nonce/secret revision 分别原子搬为各自 revision 1 并写对应 current pointer；目标 schema 不再把稳定 connection/account 行上的可变 ciphertext 当作凭证权威。D48 确认事务先原子消费 challenge、保存状态为 pending-validation 的新 revision、authorized intent、安全事件与 outbox，但不得在持有事务时调用 provider 或提前切任一 current pointer；worker 只按该 immutable revision 调用必要的 provider 验证。integration revision 验证成功后的短控制事务重验 intent、tenant gate 与 expected integration/current revision 后 CAS 切换 connection pointer；provider-account revision 还必须 current-read 核对该 revision 对应的全局 claim reservation/owner/fingerprint、expected account/current revision 和 claim generation，并在同一最终事务 CAS 切换 account pointer、固化匹配的 current claim generation 与安全结果，不能让 account current revision 和 current claim 指向不同月结号。仅需本地格式验证且不涉及 provider-account claim 的 provider 可在同一 D48 确认事务完成 pointer CAS。验证失败、响应未知、任一 current revision/claim generation 漂移或响应丢失都不得覆盖旧 current、产生两个 current、占住无法证明归属的 claim，或把新 revision 的明文/密文写入日志；未知结果进入受限复核而不自动重复不可证明安全的 provider 动作。两类 revision 的业务明文、integration/account/provider 归属和 revision number 均不可改写；平台根密钥换代只允许在全局写屏障下保持业务 revision UUID/语义不变，以行内旧 `root_key_version` 解密后用新根版本、新 nonce 认证重加密同一 revision，并采用行锁/乐观版本保证可重入，单条成功后才切换 envelope 的 root-key version。
- 新 provider operation 必须同时解析 connection 与 provider account 的 current pointers，核对 account current claim/binding 一致后，在首次持久提交中固化 exact `integration_secret_revision_uuid` 与 `provider_account_secret_revision_uuid`；已经创建的 shipment、provider attempt、waybill/第一联和 print job 必须按各自 ledger 保存的这两个精确 UUID 读取对应历史 revision 密文，不能跟随任一 current pointer。任何被未终结 operation 或保留期内历史 shipment/waybill/job 引用的两类 revision 均不得物理清理；停用 connection/account、切换租户默认 connection、解绑或转移 claim、普通凭证轮换和 current pointer 前进都只阻止旧 revision 用于新 operation，不删除历史 revision。若任一旧凭证已经在 provider 侧撤销、revision 缺失或 tag/版本校验失败，历史动作进入稳定的 credential-invalid/`needs_review` 并 fail closed，不得从稳定 account 行读取可变凭证，也不得改用任一 current/default/其他 connection 或 account 猜测重试。只有该 revision 的引用已全部终结且超过已批准的历史保留边界时，系统清理才能删除；删除只记录类型、UUID/revision 和安全结果，不记录密文、明文、provider 原始错误或请求响应。

### 8.3 Provider adapters

顺丰、闲鱼和快麦服务构造函数改为显式接收 `TenantIntegrationConfig`，禁止在模块内部直接读取业务凭证环境变量。短信由平台配置，不进入租户 integration。每个业务 provider 支持：

- `validate_config()`：D48 confirmation 前只做纯本地格式验证；需要调用第三方的主动测试必须在 pending secret revision 与 authorized outbox 已提交后执行，不持数据库事务，也不在验证成功前切换 connection 或 provider-account 的任一 current pointer。
- `health_check()`：记录可用性但不泄露错误中的 secret。
- `execute(..., idempotency_key)`：第三方写操作使用稳定幂等键或本地去重记录。
- 按租户限流、熔断、重试和指标标签；禁止高基数标签放入指标系统。

SF adapter 额外经过 `WarehouseProviderResolver`：

- 新时效查询和创建新运单只能输入可信 tenant context 与服务端解析出的 warehouse/device/rental；`WarehouseProviderResolver` 必须先 current-read 复核 tenant/subscription 为 `active`，且无 recovery/suspension/deletion 门禁，再读取当前 active `warehouse_provider_bindings` 和匹配的 active claim，并从控制面加载当前 provider account 与 API connection。expired tenant 在任何 binding/config lookup 前返回 `TENANT_EXPIRED`，`suspending/suspended/resuming` 返回 `TENANT_SUSPENDED`；客户端传入的月结卡号、account UUID、sender 或 origin 只能被忽略/拒绝。
- 已经持久化 shipment/execution ledger 的取消、查询、幂等重试、获取/打印第一联等历史操作一律不再解析当前仓库绑定、当前 claim 或任一 current pointer，而是严格读取 ledger 保存的原 warehouse、provider account、integration、binding revision、exact `integration_secret_revision_uuid`、exact `provider_account_secret_revision_uuid` 与寄件资料快照，并分别从保留的两类 immutable secret revision 记录解密所需凭证；稳定 account/connection 行上的非秘密元数据或任何可变字段都不能充当历史凭证来源。原仓解绑、停用或同一月结账号后来被另一仓、另一租户重新验证并绑定，都不能改写历史上下文或让历史 operation 切换 credential；没有可信 ledger snapshot 或缺少任一必需 revision UUID 的请求不能伪装成历史操作绕过当前绑定门禁。该快照规则不扩大执行资格：expired/suspended/recovery/deletion 的外层门禁仍先决定操作能否运行；只有获准继续的历史查询、取消、对账或幂等收口才使用原快照，绝不因当前 binding 缺失而回退默认账号或另一个仓库。
- 各顺丰接口只提交协议实际要求的字段，不能臆造所有接口都需要 `monthlyCard`。创建新运单等要求月结号的动作使用当前仓绑定账号；时效查询即使协议只要求 partner credential 与起终点，也必须使用当前账号引用的 connection，并把 account/binding 上下文计入审计和 capability。寄件联系人、电话和地址来自同一仓库记录。第二联仍只使用仓库寄回信息且不把该内容加入顺丰第一联 payload。
- 首次产生第三方副作用前，在 execution/waybill ledger 保存 `warehouse_uuid`、provider account UUID、integration UUID、binding revision、exact `integration_secret_revision_uuid`、exact `provider_account_secret_revision_uuid`、月结号掩码和寄件资料快照；不保存明文 secret，也不能只保存可能重号或可被重新解释的模糊 revision number。后续取消、查询、重试、对账和第一联获取/打印只使用该账本的两个 revision UUID 解密，仓库换绑、claim 转移或 current pointer 前进不得让旧运单悄悄切换账号或凭证。
- 设备在实际发货前换仓且已有运单时，shipment 进入 `cancel_requested` 并使用原快照、稳定取消幂等键调用 provider；明确成功后进入 `cancelled`，超时或响应丢失进入 `cancel_unknown/needs_review`，明确失败保留安全错误码。只有旧运单已确认取消或平台人员完成可审计对账，才允许以新 shipment UUID/provider order id 解析设备新仓并重建；不得覆盖旧行、复用旧运单号或因取消结果未知并行创建第二票。
- 顺丰 `orderId` 使用不含姓名/手机号的稳定值，例如 tenant 非敏感短标识 + immutable shipment UUID；同一 operation retry 必须逐字节复用。禁止继续把 customer name 拼入 provider order id，也禁止仅用租户库内可能重复的 rental 整数 ID。
- 只有 `active` tenant 的 Admin 可以新增、验证、停用账号，也可以主动解绑本租户仓库的账号或让仓库改用另一个未被占用的账号；解绑后无需平台审批。expired tenant 的任何角色都不能列出或查看 integration/SF connection、provider account、warehouse binding 或其非秘密元数据，也不能绑定、解绑、验证、测试、停用或更新；suspending/suspended/resuming tenant 同样没有解绑例外，必须由平台先完成恢复。新仓必须用自身有权使用的 API connection 重新提交并验证，不能直接继承原租户的 provider account、integration 或验证状态。active tenant 的设置接口只显示名称、掩码、绑定仓库和验证状态；Operator 可以执行获授权的发货/打印动作，不能读取或修改 partner secret、checkword 或完整月结号。
- Admin 首次配置 SF 时建立租户默认 connection；新增月结账号自动写入该 connection 的 ID，只有高级设置允许改为同租户、同 provider 的其他 active connection。物理停用或删除旧 account/connection 前必须检查未完成 operation 和历史运单引用，避免删掉历史快照仍需的凭证；该检查不得复用为仓库月结账号解绑的前置门禁。不得在运行时发现专用 connection 不可用后回退默认凭证。
- D26 已进入不可撤销删除阶段并取得匹配的站外 tombstone ack 后，删除执行器在删除 tenant provider account、integration 或租户库 binding 之前必须运行 system-only 全局 claim release。该路径不是 D50 的 Admin 主动解绑，不创建或消费 D48 短信 challenge/intent，也不是 D56 为 expired/suspended/deletion tenant 开放的页面或 API 例外；租户和平台用户均不能直接调用、选择目标账号或提前触发。执行器按统一 tenant-first/deletion 锁序取得 current deletion generation，再按 `(provider, claim UUID)` 固定顺序锁定该 tenant provider account 声明的全部 claim，逐条 current-read 核对 `active/reserved` claim 的 current tenant、provider account、warehouse、reservation/execution generation 与 expected row version 均仍属于本次删除；匹配者递增 fencing/row generation、原子置为 `released`，清空 current account/tenant/warehouse 与 reservation/lease owner，并在同一控制库事务写 system actor 的不可变安全审计。account 指向 claim 而 claim owner 不匹配、存在未知状态/代数或审计提交失败时整批 fail closed，不能先删 account 留下 active orphan，也不能释放其他租户的新归属。
- D26 claim release 与正常 bind/reservation/解绑使用同一 claim 行锁、owner/generation CAS 和唯一索引线性化：绑定或 reservation 先提交时，删除执行器随后只能核对并释放该 tenant 的最新 generation；删除 gate/释放先提交时，旧 tenant 的迟到验证 worker、outbox 或 D48 intent 因 deletion/access/claim generation 不匹配只能 no-op，新仓则在 release 提交后以自己的新 reservation generation 重新验证。释放事务提交后 D26 才可继续删除租户库 binding、provider account/integration 和 schema；重复执行只返回同一 released 结果并复用同一幂等审计，不复活旧 owner。该系统释放不调用 provider、不改写历史 shipment/waybill 快照，也不能在仍可撤销的冷静期、普通 expired/suspended 状态或仅因 tenant recovery-hold 审核而运行；current hold 不阻断已经不可逆的 D26 单调删除，但 release 必须绑定该 deletion generation，并由既有 D58 删除处置把 hold/normalization item 收口为 tombstoned，绝不能借此 release tenant route 或其他业务权限。
- 仓库无 active/verified SF binding 时，官方时效查询进入 D19 的人工确认 fallback；顺丰下单、批量发货中的顺丰步骤和第一联打印必须 fail closed 并提示配置该仓账号，禁止回退到默认仓、其他仓或进程环境变量账号。
- 对 active tenant，上述缺配置门禁统一返回结构化错误 `SF_WAREHOUSE_ACCOUNT_REQUIRED`，至少包含可信解析出的 `warehouse_id`、可展示仓库名、被阻止的 action、`can_configure`、稳定站内 `help_path`，以及仅对 Admin 返回的租户内 `settings_path`；响应不得包含月结号、connection ID、secret 状态细节或由客户端传入的跳转 URL。expired/suspended 门禁必须先于该错误与 resolver 执行，分别返回 `TENANT_EXPIRED`/`TENANT_SUSPENDED`，不返回 `can_configure`、`settings_path`、binding/account 状态或其他配置元数据。前端不得依靠文案字符串判断错误。
- active tenant 的 Admin 看到“去绑定顺丰月结账号”和“查看配置指引”两个操作：前者深链到当前仓库的顺丰设置并在保存/验证成功后返回原业务上下文，后者打开站内版本化帮助页 `/help/integrations/sf/warehouse-monthly-account`。active tenant 的 Operator 只显示具体仓库、“联系租户管理员”和相同帮助入口，不显示或绕过无权访问的设置链接。expired/suspended tenant 的受限页面不显示这些操作、帮助入口或 integration 状态，直接访问设置/帮助深链也必须被租户状态路由拦截。批量操作涉及多个仓库时按仓聚合缺失项，不为每个订单重复弹窗。
- 站内指引随应用版本发布，至少覆盖：准备 partner id/checkword 与月结账号、配置租户默认/专用 connection、绑定并验证仓库、权限说明、人工物流天数 fallback、常见错误，以及“原仓 Admin 主动解绑 → 当前 claim 释放 → 新仓重新录入并验证”的换仓流程。指引明确历史/未完成运单不阻止解绑且继续使用旧快照，不提供平台审批、强制转移或目标仓预留入口；这里的“不阻止解绑”只适用于 active tenant 的 Admin，不形成 expired/suspended 状态例外。可链接顺丰官方开放平台文档，但站内主流程不能只依赖一个可能变化的外部 URL；帮助页和设置深链均须经过正常租户鉴权与 tenant 状态门禁，URL、埋点和日志不得携带 secret。
- provider 日志采用字段 allowlist，只记录 request/order/waybill hash、safe result code、耗时和已脱敏标识；完整请求/响应、月结号、客户/仓库地址电话、PDF URL/token 不得写日志。现有 SF mock/order/status 测试路由不得在生产注册；仓库绑定测试由 Admin 专用接口执行且只返回 configured/masked/capability/error code。
- Phase 0 用真实但受控的租户账号验证认证模式、官方时效接口、月结号与仓库寄件资料权限以及 sandbox/production 差异，记录 capability；不能仅根据仓库中的旧样例报文假定所有月结账号都有相同 API entitlement。

### 8.4 Platform SMS via Tencent Cloud (D35 confirmed)

- 实现平台级 `SmsProvider` 接口，Core 生产只启用腾讯云国内短信 adapter；该 adapter 使用腾讯云 SMS API 3.0 当前版本和官方 SDK。provider、AppID、签名和验证码模板 ID 是平台配置，不创建租户 integration，也不按 tenant 计费或选择签名。
- `SmsProvider` 的身份验证码接口只接收已经通过 D46 的 canonical `+86` E.164；号码规范化、phone subject hash、HMAC 和全部手机号 rate-limit counter 必须先完成，再允许创建 provider attempt。adapter 收到非 canonical、非 CN mobile 或其他地区输入时 fail closed，不能自行猜测/补国家码、选择国际短信路由或调用腾讯云。对手机号变更 purpose，D57 要求收件号码只能来自身份工作流对当前 `phone_change_old` 或同一 change request 新号码的可信解析；provider adapter 不接受备用恢复号码、平台/客服覆盖参数或“代验证”模式。腾讯云的提交成功、送达回执、控制台状态和人工查询对所有 purpose 都只表示 delivery evidence，绝不能消费 challenge、证明号码控制权或替代用户提交 OTP。
- 腾讯云 SecretId/SecretKey 使用独立、最小权限的 CAM 身份，通过宿主机 Docker Secret 只读挂载给实际发送短信的服务；不得使用腾讯云主账号长期密钥，不进入 Git、镜像、Compose 环境变量值、控制库、备份、日志或平台页面。AppID、签名和模板 ID 虽非密码，也只能由平台部署配置修改，租户客户端不得提交或覆盖。
- 所有租户共享平台运营主体的一个签名。`tenant_branding.display_name/legal_name`、默认租户名称、仓库或客户信息均不得拼进签名；未来若需要白标租户签名，必须新增资质、成本、模板、路由和滥用治理决策，不能在 Core 暗中扩展。
- 生产启动与发布门禁分两层：配置门禁验证 provider/credential/AppID/sign/template 完整且禁用 fake；上线门禁验证企业实名认证、实名资质、腾讯云平台审核、运营商实名报备均处于可用状态，并用受控真实号码完成“发送 → 接收 → purpose/context 校验 → 单次消费 → 审计”测试。未满足时认证发送端返回统一暂不可用状态，注册、登录、D48 Admin 高危动作、手机号变更、删除申请/撤销等依赖短信复验的入口均 fail closed。
- `FakeSmsProvider` 只允许测试或明确的非生产本地环境通过依赖注入启用；生产环境发现 fake、固定验证码、回显验证码或日志验证码时必须拒绝启动。自动测试可直接取得注入 provider 的测试夹具结果，但公开 HTTP 响应永不返回 code。
- 腾讯云发送频率限制、应用级国内短信阈值、验证码防盗刷监控和告警联系人必须在控制台启用，同时由应用的 MySQL `sms_rate_limit_counters` 执行更细的 phone/IP/device/purpose 限制。provider 返回限流、资质、签名、模板或余额错误时只映射稳定内部错误码和可重试时间，不向客户端泄露腾讯云账号结构。
- 资质规则可能变化，部署 runbook 在每次生产开通/签名变更时复核腾讯云官方[国内短信快速入门](https://cloud.tencent.com/document/product/382/37745)、[实名资质审核标准](https://cloud.tencent.com/document/product/382/108274)、[签名实名制报备](https://cloud.tencent.com/document/product/382/117410)和[安全设置](https://cloud.tencent.com/document/product/382/61409)。截至本次设计核对，新增签名的运营商报备平均需 7–10 个工作日且无时效承诺，因此不得排到切换当天才开始。

## 9. Background Jobs

D09 已确认使用控制库 `background_jobs` + 单个独立后台进程。该进程同时运行 APScheduler 定时触发器并领取/执行持久任务，满足以下契约：

- Web 进程不再启动 APScheduler。
- 后台进程中的 scheduler 只生成平台级 fan-out 任务；任务逐租户写入 `background_jobs`，不在一个长事务里扫描全部租户。current host-restore run 尚未完成覆盖，或 tenant hold 非 released 时不得为该 tenant fan-out；恢复平台控制任务使用独立类型和 capability，不能伪装成租户业务 job 绕过。
- payload 至少包含 `tenant_id`, `tenant_access_version`, `job_type`, `resource_id/period`, `idempotency_key`, `requested_by`，时效性任务另含 `not_after`；客户端不能提供或覆盖可信 tenant/access version。
- worker 在领取任务后、进入租户上下文前、写入持久 provider 提交边界前，以及每次第三方副作用前，重新验证外部部署 marker/current recovery run、本 tenant hold/revision、最新 tenant route/access version、subscription、D52 suspension 和 D26/D27 deletion state；tenant 非 `active`（包括 `expired`）、缺 current hold、hold 非 released、`suspending/suspended/resuming`、`deletion_cooling_off`、`committing`、`awaiting_offsite_ack`、`dropping`、`completed/deleted` 均优先于旧 job payload 或旧租约并 deny 新执行。不能只在任务创建时检查，否则到期、恢复、暂停或删除过程中已排队任务仍可能发货、打印或同步。已经越过持久 provider submission boundary 的不确定 operation 只能按既定安全规则查询/对账，且 resolver 必须使用其不可变 ledger snapshot，不能回查当前 binding。
- D52 首个 freezing 事务提交后 scheduler 不再为该 tenant 生成 fan-out，worker 不再取得新 lease；未越过持久 provider 提交边界的 pending/running job 以旧 `tenant_access_version` 失效并进入 `suspension_blocked`，不能靠延长旧 lease 继续。已越过该边界的 operation 视为在途不确定窗口，只允许按不可变 idempotency/snapshot 查询或对账，明确禁止自动 retry/resubmit/print；屏障重试必须能区分这两类，不能用进程内布尔值猜测。
- provider submission boundary 必须由短控制库事务实现：worker 按 6.2 的统一顺序锁 `tenant → current recovery run → tenant hold → deletion → suspension → job/execution`，复核 run/hold released、tenant active/access version 后把 operation 原子推进到 `provider_submitting` 并提交，之后才能发起网络调用；D52 freezing、D58 hold/review 和 D26 deletion 竞争同一 tenant 权威行。worker 先提交则该 operation 明确进入在途隔离，安全门禁先提交则 worker 无法越界；不得把“即将调用”的内存状态、日志时间或租户库中未与 gate 协调的行当作边界。
- D52 恢复到 `active` 或 D58 逐租户放行时，普通周期性读/同步任务只从当前调度点重新生成，不补跑暂停/灾备窗口内每个错过周期；只有 `not_after` 未过、前置事实仍成立且动作可证明幂等/尚未提交的安全 job 才可新建 current run/current access-version job。被阻断的用户触发发货、运单创建、打印及任何结果未知操作全部进入 `needs_review/recovery_review`，由用户重新确认后创建新 job；恢复结果为 `expired` 时仍不得领取业务任务。D52/D58 都绝不把旧 job 状态批量改回 pending，tenant release 也不改变任何旧 execution 行。
- 发货、打印、闲鱼同步等外部副作用使用 outbox/job execution 表记录状态。可证明未提交或 provider 明确拒绝的操作才允许按稳定幂等键自动重试；物理打印已提交但响应超时/丢失时无法证明纸张未打印，必须进入 `needs_review`，由用户核对后显式新建重打 job，不能自动重试并宣称绝不重复。
- 顺丰批量发货在数据库事务中先为每个 rental 创建独立、唯一幂等键的 pending execution 并提交，再逐项调用 provider；每一项返回后立即在短事务中保存 waybill/account/binding/寄件快照和结果，不能等整批结束才统一 commit。崩溃恢复先按本地 order id 查询 provider/账本状态，不能盲目再次创建运单。
- 顺丰追踪任务按历史 waybill ledger 的 integration/account credential 与查询手机号后四位分组，每组再按 provider 上限分批；不得把不同仓库/账号的运单塞进同一个全局 credential 批次，也不得从当前仓库绑定覆盖历史运单上下文。
- 闲鱼调度器为每个 active tenant 按 180 秒周期产生一个 `xianyu_alert_sync` 任务，并使用稳定 tenant/integration + time-bucket 幂等键；租户采用确定性错峰，不能让所有租户在同一秒请求第三方。一个租户若有多个 active 闲鱼 connection，由同一租户任务按 connection 记录独立结果并在最后更新聚合 revision。
- 闲鱼 provider 网络调用不得持有租户数据库事务或连接；worker 先读取必要配置并释放连接，调用第三方后再用短事务 upsert 告警摘要、各 connection 状态、`snapshot_revision`、`last_attempt_at` 和 `last_successful_sync_at`。单个 connection 失败不得清空上一次成功告警，也不得覆盖其他 connection 的成功结果。
- Admin/Operator 手动刷新提交高优先级 `xianyu_alert_sync_now`；若同租户已有 scheduled/manual sync 在途，则返回同一 job ID 而不是再次调用第三方。接口先返回 `202 + job_id/snapshot_revision`，页面显示“同步中”并读取任务结果；provider 限流时展示可重试时间。服务端仍实施按租户有界频率，不能依赖按钮禁用防刷。
- 页面自动刷新只调用租户库摘要 API 或随 `gantt view` 读取 count/revision，不调用闲鱼。仅页面可见时每 3 分钟读取一次，重新可见时可立即读一次本地摘要；多个标签页增加的是轻量租户库读取，不会成倍增加第三方同步。响应携带 `snapshot_revision`、`last_successful_sync_at`、`sync_status` 和是否已超过两个调度周期的 `stale` 标记，不使用 localStorage 或跨请求内存缓存保存告警事实。
- 同一后台进程使用 MySQL 8 的行锁/租约机制安全领取任务；超时租约可被回收，同一幂等键只能有一个有效执行记录。
- 任务按 priority/type 调度，避免大导出阻塞发货；规模增长后可以在保持 job contract 不变的情况下换成专用队列。
- 普通业务任务失败进入有界重试和 dead-letter 管理；只有明确列入普通 job 运维 allowlist 的类型才允许平台后台查看后重放或取消，操作留审计。D54 replacement 残留清理和 D58 recovery cleanup 属于 system-only control outbox/janitor，不是普通 `background_jobs`：平台页面不展示逐 attempt 的 cleanup 任务、资源清单或进度，也不能 cancel、replay、改 payload 或新建同类 cleanup；系统接管必须复用原 source generation、幂等键和 fencing lease，失败只进入内部聚合指标、运维告警与不可变审计，直到安全终态或 fail closed。

## 10. Files, PDFs and Exports

- SaaS Core 不提供公司 Logo、身份证、合同或发货单文档上传，因此不新建通用文件资产表，也不引入对象存储。
- 顺丰快递面单、PDF 转换结果和同步导出优先在内存中生成并由鉴权接口直接返回；确需落盘时只能写入租户隔离的临时目录，使用不可预测文件名，并在请求或任务结束后清理。
- 临时结果不得由 Nginx 公开目录直接访问，不得以客户端文件名、手机号或业务顺序 ID 作为路径。
- 如果未来新增验货图片留存、大型异步导出或多实例间共享文件，再单独评审对象存储、文件元数据、保留期、病毒扫描和签名 URL，不提前纳入 Core。
