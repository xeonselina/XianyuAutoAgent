# SaaS 转型设计：安全、迁移与测试

> 返回：[总体设计索引](../design.md)

## 13. Security and Privacy Baseline

- 强制 TLS，生产环境不得读取或依赖通用 Flask `SECRET_KEY`/全局 `API_KEY`，并拒绝通配 CORS 和 debug 模式；旧配置、快照或恢复数据即使仍含这些值也不得恢复任何签名、会话或机器身份入口。
- 增加 CSP、HSTS、Permissions-Policy 等安全头，逐步移除当前 CSP 中不必要的 `unsafe-inline`。
- 对客户姓名、手机号和地址按权限最小化展示；日志使用结构化脱敏器。SaaS Core 不采集身份证 OCR 数据。
- 输入验证和 HTML/PDF 模板转义列入普通安全测试清单；发现失败即修复并重跑。如未来重新引入上传，再增加 MIME/大小校验与恶意文件扫描。
- 任务 payload、第三方 Secret 和根密钥副本仍按各自规则加密；数据库逻辑 dump 在 NAS 和云盘上的 artifact 是 D24/D32 明确批准的静态加密例外。该例外不取消 SSH/TLS 链路保护、最小权限、checksum、NAS 只读快照、云盘版本历史、访问审计或事件响应，并须在正式向外部付费租户提供服务前进行一次隐私/合规复核。
- 租户级审计日志只追加；平台审计与租户业务库逻辑分离。
- 数据保留、导出、注销和客户个人信息请求需要结合实际经营地区做合规评审，本设计不替代法律意见。

## 14. Migration and Rollout

### Phase 0: Baseline and scheduling readiness

Phase 0 只记录当前仓库/部署的只读基线、可独立取得的外部账号资格与 provider capability 事实，以及后续实现/测试计划。它不得要求只有 Phase 1 之后的数据结构或后续运维实现才能产生的 Core 根密钥文件、加密 revision、控制表/outbox、健康端点、监控 adapter、NAS wrapper、备份恢复或真实故障演练结果；这些作为后续普通任务完成，并在记录 `project_complete_at` 前勾选。Phase 0 也不设置阶段审批、receipt 或 hard release gate。

- 建立当前 schema 快照、迁移链校验、生产数据量统计和关键查询基线。
- 为所有现有 endpoint 建资源矩阵，标出读/写、涉及模型、权限和第三方副作用。
- 用桌面/移动端浏览器 network trace 与服务端 SQL query counter 建立页面基线，至少记录预约建单、编辑、甘特窗口移动、写后刷新、搜索、批量发货、顺丰追踪和验货：每个用户动作的 HTTP 数、取消数、租户连接 checkout 数、SQL 数、p50/p95、未压缩/压缩字节。明确记录当前预约 `D+A`、桌面甘特 16、移动甘特 14 的放大因子，后续以相同数据夹具对比。
- 先修复与业务语义无关的连接复用问题：普通 `/api/` location 移除无条件 `Connection: upgrade`，保留 HTTP/1.1 upstream keep-alive；若存在专用 WebSocket 路由再单独配置。该调整需以 Nginx 配置测试和连接指标验证。
- 建立品牌/地理硬编码清单，覆盖物流估算器、顺丰寄件信息、接力判断、第二联和遗留页面；生产路径不得再以“广东/深圳”或任一旧公司地址推断租户仓库。示例/测试数据必须与生产默认值分离，不能在配置缺失时回退成真实地址。
- 执行下方 D12 活跃变更基线，不得在实施时自行把“保留并随 SaaS 适配”的能力降级为暂停或删除。D63 已取消代码、schema、核心模块冻结及冻结例外/解冻/持续 48 小时流程；D64 已取消阶段审批门、候选签字/receipt/evidence digest 和 hard release gate。全部项目实现、默认租户迁移/回滚工具及必要测试完成时直接记录 `project_complete_at=T`，首次生产规模迁移演练使用不早于 `T+168h` 的可用窗口。影响迁移结果的后续实现变更按普通开发处理，重跑相关测试后更新 T 并重新计时。
- Phase 0 盘点并登记高风险基线问题及负责人：Compose、健康检查、部署脚本、`simple_backup.sh`、SF 示例调用脚本和已跟踪配置中的硬编码密码/API credential/完整 DSN，快麦等明文凭证日志，以及 `.gitignore`/`.dockerignore` 缺口；实际修复、扫描和复测列入后续普通任务。D61 只覆盖现有旧数据库账号、默认租户顺丰和快麦三类 legacy 凭证；用户确认的是“有期限”，当前 policy v1 的 30×24 小时只是保守默认值/单次上限，每次显式复核、可更短且不自动续期，并最迟在首次生产规模演练开始时失效。它不豁免扫描、网络/provider 限制、异常监控、最小权限或清理，也不允许旧值进入 Core 新账号或新 provider revision。
- Phase 0 只启动并记录 D35 腾讯云企业/短信资质、统一签名、模板和运营商报备的申请状态、账号 capability、预计时间与负责人；最小权限 CAM/Docker Secret、adapter、阈值和真实号码完整流程在后续实现，作为普通任务测试。材料未就绪不阻止继续开发；运行时不得用 fake 对外开放生产认证。
- Phase 0 只核对 D49 所需腾讯云 capability、配额、费用、生产 DNS/账号可用性并记录 provisional `MonitoringPolicy` 计划；CVM Agent、两类健康端点、云拨测、operational signals、消息 adapter、NAS 状态回报及其真实故障测试均在后续实现。实现后的非空参数由受控非生产故障测试修订并列入项目完成清单，不在 Phase 0 假装已有产物，也不引入 Managed Prometheus/Grafana。
- Phase 0 记录生产 MySQL 不应公网暴露、备份目标、启动 Secret 清单和根密钥恢复方案；首个 `PLATFORM_ROOT_KEY` 文件、异地副本、派生连接和解密恢复测试在后续实现。运行时缺失正确密钥仍 fail closed。
- Phase 0 记录 D23/D24 NAS pull 的账号、网络、容量和保留方案；专用 SSH 身份、root-owned wrapper、`.partial` 原子完成、48 小时/30 日/12 月保留和失败通知均在后续实现并作为普通测试任务核对。

#### D12 已确认的活跃变更基线

“保留并随 SaaS 适配”表示保留用户能力和正确的现有实现，但将不适合 SaaS 的全局配置、固定仓库、Web 进程内定时器、同步第三方副作用、逐项 API 请求等部分迁入本文已经确认的租户路由、仓库绑定、MySQL 持久任务、不可变执行快照和聚合 API；它不表示推倒重写。

### Phase 1: Expand

- 新建 `inventory_control`、control-plane 表、D45 租户逐设备会话表、独立平台管理员/认证因子/恢复码/会话表、只存版本/指纹/状态的 `platform_root_key_versions`、同时登记 DML 与平台只读账号代数的 `tenant_databases` 路由注册表、provider API connection/account 表和默认租户，但不改变现有业务行为。
- 按 D11 在当前业务数据库新增且只允许一行的 `database_identity`，将它原地注册为默认租户数据库；无需给业务表增加或回填 `tenant_id`。首次切换不复制、移动或重命名 schema，不修改现有业务表主键；控制库中的 route 只引用经过白名单校验的原 schema 名和新生成的不可变 tenant/database UUID。
- 原地迁移前冻结并记录当前 schema 名、Alembic 版本、表/行数、关键金额/订单状态、外键孤儿和第三方配置来源。`database_identity` 一旦写入不得重置为其他 tenant；发现已有错误 identity、同一 schema 被两个 route 引用或控制库/库内 UUID 不一致时立即停止，不能靠覆盖修复。
- 使用首次迁移时提供的必填租户显示名称和首位 Admin 手机号，创建默认 tenant、Admin 用户、membership 和初始 subscription，并加入订阅事件表。初始 subscription 严格执行 D60：使用迁移制品冻结的 Core plan revision、`member_seats=10` 和精确 36,500 天，以最终控制库事务的数据库当前时间为基准，写入唯一 `migration_grant` event；迁移命令不接收期限参数，不创建/消费兑换码，也不引入 perpetual 状态。迁移命令不得为显示名称或手机号提供隐含默认值或把参数回显到日志；Admin 手机号必须通过 D46 的同一 `+86` 规范化器和唯一性检查，非法、国际或歧义输入在任何控制面写入前终止并进入人工修正。CLI 录入不能伪装成 OTP 验证，初始 `phone_verified_at` 保持 NULL，首位 Admin 第一次成功短信登录后才设置；重复运行仅允许命中同一 canonical tenant/user 身份，并返回同一 migration grant，不能再次增加 36,500 天。
- 为默认租户分别创建派生密码的独立 DML 账号和独立平台只读账号；前者只获本 schema 所需读写，后者只获本 schema 的 SELECT/SHOW VIEW。第三方业务配置的非秘密所有权可迁入默认租户 integration，但 D61 覆盖的旧 SF/快麦值只保留在受控 legacy 运行边界直至轮换，不得读取、复制、散列、机械加密或包装为 Core Secret revision 1/current revision。迁移工具可以建立 `unconfigured/pending` 的稳定非秘密元数据；只有 provider 侧轮换后重新提交并验证成功的替代值才创建新的 revision 1 和 current pointer。仓库尚未完成回填前不创建虚假的 SF binding。旧读取路径只允许有期限、可观测且不可新增调用方的受控 fallback，并在 D61 到期或首次演练前删除。
- 当前应用使用的旧数据库账号只在回滚窗口内保留；DML 新路由账号通过“仅本 schema 可读写、其他 tenant/control schema 拒绝”，平台只读账号通过“本 schema 可 SELECT、所有写入及其他 schema 拒绝”测试并完成切换后，旧账号先停止被新应用使用，contract 阶段再撤销。不得把当前 root/广域账号直接登记成任一种默认租户账号。
- 在 tenant-aware 应用首次开放前，迁移 CLI 必须幂等建立唯一 current、status=`completed` 的 `initial_baseline` recovery run，为默认 tenant 写入同 run 的 `released` hold 基线，并用当前主机新建的 installation ID 生成匹配的 root-owned 只读部署 marker。三者与 default tenant/access/database identity 全部匹配后才能开放；任一缺失、重复 current run、版本/指纹不符或文件写入中断均 fail closed。该 marker/installation ID 不进入 Git、容器镜像、Compose bundle、数据库/NAS/云盘备份或可复用 CVM 镜像。相同 migration idempotency 输入在普通重启/重跑时只能核对原 baseline，不能生成第二个 current run、替换 marker 或递增 tenant access version；不同输入必须人工处理而非自动覆盖。

### Phase 2: Backfill and verify

- 实现版本化 `DatabasePasswordDeriver`、`TenantDatabaseRouter`、`PlatformTenantReadRouter`、用途隔离的 routing session/有界 engine cache、连接身份校验和租户库 migration runner；平台读路由强制 query timeout、分页和 read-only transaction。缺失/错误/未知版本根密钥或任一种派生连接失败时不得回退到固定密码、DML engine 或默认数据库。
- 对默认租户数据库记录表行数、外键孤儿、关键金额和关联一致性，确认路由前后查询结果一致。
- 自动创建一个不含生产数据的第二测试租户数据库，验证开户、迁移、连接回收、暂停与删除流程。
- 验证删除 OCR、合同和独立发货单页面后不存在需要迁移的长期上传文件；顺丰第一联、本地第二联和 PDF 转换只使用受控临时数据。
- 创建默认仓库并回填主设备 `warehouse_id`；随后只使用 provider 侧已轮换、重新提交并验证成功的 SF 替代值创建 provider account/integration 的 revision 1，再建立默认仓 binding；不得使用 Phase 1 或任何迁移工具把 D61 legacy 月结号/credential 加密搬入。按 D68 将可识别的旧生命周期、出入库运单号和打印发生事实写入独立 `legacy_unattributed` 只读快照，只保存租户内展示和反向核对所需事实，不创建或引用 integration/account/binding/credential revision/provider order/printer task，也不进入任何 provider、PDF、取消、重试、重打或对账执行队列。先对可可靠识别的活动订单生成 `planned_ship_out_date/planned_return_date`，再按唯一 legacy source 把每个现有有效手机支架/三脚架记录幂等转换为一个隐藏逻辑单元，把未完成附件 child rental 幂等 upsert 为 request；能可靠核对时建立对应的带窗口 unit link，并写 `created/linked` 事件及 `reason=migration`、稳定 idempotency key，不能可靠判断时保持单元不可用并进入人工核对。迁移按仓库、类型、基础状态、活动占用、未来 request、link 和 D68 历史快照逐项对账，顺序不得颠倒。
- 新增并回填计划与实际物流字段。旧 `ship_out_time/ship_in_time` 已被实际事件覆盖或无法可靠映射时进入人工核对清单，不能静默猜测。已有订单仅发生 `overlap_days > 1` 的物流重叠时保留为合法订单并生成甘特警告/接力候选；真实客户使用期重叠进入人工核对。迁移接力中的附件时，为已知随行逻辑单元、经过的 rental 建立 unit link，写入当前持有订单并导入交接事件；中间单未选择附件时不创建 request，但仍建立随行 link，不创建特殊 role。无法确定附件是否仍在客户手中的记录保持不可用并进入人工核对，不能直接恢复为仓库可用。逻辑单元功能开关切换后，旧手机支架/三脚架 Device 与对应 child rental 立即变成只读迁移来源，并从所有可用性、计数、验货和发货查询排除，直到 contract 阶段归档/删除，禁止新旧双计数。completed/cancelled 历史记录保留原事实字段但不参与未来约束。
- 在影子环境用生产数据副本运行完整回归和迁移演练。

### Phase 3: Enforce in application

- 本节描述切换工作流的实现与测试；实际生产切换发生在 `project_complete_at+168h` 之后的演练和后续窗口，不属于项目完成时点。默认租户正式切换至少提前 24 小时通知并预留连续 2 小时维护窗口。进入窗口后展示维护页，停止旧应用业务写入、Web 内 scheduler、独立 worker 和第三方副作用，再做最终 backfill/对账并启用可信 route；Core 不建设旧版与新版双写。目标停写不超过 30 分钟；维护开始满 60 分钟仍有必要核对未完成或失败时执行已测试回滚，剩余时间用于恢复旧应用和验证。

### D64 project-complete scheduling boundary

- 全部 Core 项目实现、默认租户迁移/backfill/verification/rollback 工具和能够在首次生产规模演练前执行的必要测试完成后，直接记录 UTC `project_complete_at=T`；它是简单时间记录，不需要候选签字、receipt、evidence digest、阶段审批或 release approval。
- `project_complete_at` 明确不等待首次生产规模演练、实际生产切换、切换后 48 小时观察或 Phase 6 contract cleanup。首次生产规模演练安排在不早于 `T+168h` 的可用运维窗口；窗口延期不产生冻结、不需要解冻，也不延长 D61。
- 代码、schema 和核心模块始终按普通开发流程变更。T 之后若实现变更会影响迁移结果，就完成改动、重跑相关迁移/回滚/隔离/API 契约测试并更新 T，再从新 T 计算 168 小时；不影响迁移结果的文档或普通开发变更不触发重算。全部测试和核对仅作为普通可勾选任务，失败就修复并重跑。
- D63/D64 只取消交付冻结与项目审批/门禁流程，不改变 tenant lifecycle、RBAC、数据库隔离、Secret 验证、持久 provider submission boundary、恢复 hold 或其他运行时 fail-closed 规则。

### Rollback

- Expand/验证阶段只新增控制库、身份表和路由元数据，默认租户仍指向原业务数据库，应用可回退到旧版本。
- D11 的原地注册使维护窗口内的预开放回滚无需把数据复制回另一 schema：在新版业务写入重新开放之前停止新应用/任务，核对第三方副作用仍处于隔离状态后恢复旧应用和旧兼容账号。`database_identity`、控制库审计及 expand 新表保留但旧应用不使用，不能在回滚时删除后伪装成从未迁移。
- 认证强制、数据库路由强制和任务切换分开发布，每步均保留 feature flag 和单独回滚步骤。
- 一旦重新开放新版业务写入，哪怕尚无第二租户，旧应用也已经无法解释新的多仓、逻辑附件单元/request/event 和任务账本写入；不允许再回滚到不认识这些结构的旧应用。此后只能回到兼容这些写入的上一版 tenant-aware 应用或 forward-fix。
- 删除固定数据库 fallback 和旧连接配置属于 contract 动作，必须在备份、校验和观察窗口完成后执行。

## 15. Testing Strategy

### 15.1 Tenant isolation suite

为每个业务资源生成两个租户 A/B 的固定数据，执行完整矩阵：列表、详情、创建、更新、删除、搜索、导出、打印、文件、聚合、任务。对 A 用户传入 B 的顺序 ID、关联 ID、批量 ID 和文件 key，必须得到 404/拒绝且 B 数据无变化。

必须重点覆盖数据库路由和连接复用边界：

- 同一 Web/worker 进程连续处理 A → B → A 请求时，engine/session/transaction 不得残留上一租户连接。
- 客户端伪造 `tenant_id`、数据库名、Host、资源 ID 或任务 payload 时，不得改变可信路由。
- `db.session.query`、聚合、join、subquery、bulk update/delete、原生 SQL 和 CLI 必须落在当前租户数据库。
- `database_identity` 不匹配、路由版本过期、租户迁库中或 schema 不兼容时必须 fail closed。
- 进程内缓存污染、注销/membership 变化后的前端 store、临时面单/PDF 下载鉴权与清理。
- MySQL job 租约回收/重试、定时 fan-out、外部 webhook、导入导出。

### 15.2 Other test layers

- 数据库测试环境边界：本机可以对当前生产业务库执行显式启用的只读观察，但只允许使用经 `SHOW GRANTS` 证明仅对该目标 schema 具有 `SELECT/SHOW VIEW` 的账号，并将 SQL 限制为单条、非锁定、无文件读写的 `SELECT/SHOW/DESCRIBE`；不得把该连接交给 ORM session、migration、fixture、清理器或任何会隐式 flush/DDL 的代码。按 D65–D67，凡测试实际创建数据库 engine/session、建表、持久化或验证 SQL/事务/迁移行为，均统一串行连接同实例中名称精确为 `inventory_management_test` 的现有 schema，不创建数据库、账号/grant、第二测试库或一次性 MySQL 容器；连接必须显式设置 `ALLOW_REAL_TEST_DATABASE=true` 与 global-DBA test opt-in，并在连接后再次核对当前数据库和账号 grants。测试代码还必须持有固定 advisory lock，拒绝 `USE`、建删/修改 database/schema、账号/grant、文件或插件 SQL 以及显式跨 schema 写入。该测试库的 schema 不视为已与生产或当前 migration head 对齐：测试先只读观察实际 inventory/generation，再按用例 fail closed、仅在该测试库内显式重建或执行受测迁移。旧有依赖多个物理 identity 的组合拆成顺序组件验证，不再要求额外实例；纯函数、解析器、状态机、fake repository 与前端测试不需要建立数据库连接，SQLite 不再作为成功数据库 backend，负向 dialect 分支只使用无连接 stub；未显式启用真实测试时不得连接任何实例。
- 单元测试：permission/entitlement、tenant context、HKDF domain separation、AES-GCM secret encryption、provider adapters、quota concurrency。
- 数据库密码派生测试：固定根密钥/UUID/版本测试向量在不同进程、部署和语言实现中分别产生稳定的租户 DML 与平台只读密码；任一 tenant/database UUID、代数、账号用途、派生版本或根版本变化都产生不同密码，同一上下文的两种用途也绝不相同；无秘密固定规则、未知根版本、错误长度/指纹根密钥和派生连接失败均 fail closed；结果不进入日志、异常、任务或控制库。
- 数据库权限测试：用租户 A 的实际 DML 账号直接查询、写入或 `USE` 租户 B schema 必须被 MySQL 拒绝；用平台只读账号可 SELECT 对应租户 schema，但 INSERT/UPDATE/DELETE/DDL、FILE/EXECUTE 和访问其他租户 schema 均被 MySQL 拒绝。普通 Web/worker 账号不能建库、授权或读取控制库外的其他 schema；provisioner secret 不挂载给 Web/worker，平台只读 handler 不能取得或回退 DML engine。
- 数据库账号轮换测试：在 preparing/prepared_locked/verified/switched/draining/revoked 每个边界模拟进程崩溃并重试，必须从持久状态安全续跑；任何时刻每种 account kind 最多一个账号被对应可信路由选为 active，最终旧账号被撤销且 MySQL 中不存在未登记的孤立账号，轮换表始终不含密码材料。所有 suspension、D58、deletion、DML/platform-read rotation 和 reconciler 必须通过同一 account-mutation 三段锁序；分别在第一段 intent 提交前后、第二段每次物理账号动作前后和第三段 final CAS 前后令 lease/token 过期、advisory 连接断开或旧 owner 迟到，断言旧 token 不能提交 route/observed/action，新 owner 不持控制行锁等待 MySQL 且先按最新 desired 收敛。以两个 worker 反复交错 `dml(A) → platform_read(A)` 的双用途根密钥轮换、单独 DML freeze/resume、单独 platform-read rotation 和删除清理；任何实现若出现 `platform_read → dml` 反向取锁即测试失败，合法执行不得死锁、串用 candidate/route/cache、误切断另一用途连接或提升权限。同一租户连续执行 `tenant-DML(A) → platform-RO(A) → tenant-DML(A)` 时，cache key、engine、route version 和权限也不能跨用途复用。
- 外部 Secret 加密测试：为两个 provider connection、一个 SF provider account 和一个兑换码建立跨实现固定 HKDF/AAD/AES-GCM 测试向量，锁定 UUID 字节序、字段顺序、长度前缀、大小写、数值端序及 crypto/aad version；固定根密钥下不同用途、记录 UUID、tenant/provider、integration/account UUID 和修订号得到不同派生 key；每次加密使用新 96-bit nonce；正确 AAD 可解密，任何 ciphertext/nonce/tag、tenant、provider、记录 ID、integration ID、修订或版本被篡改/调换都必须认证失败；控制库、日志、异常和审计中不出现明文、完整月结号或派生 key；兑换码规范化/lookup hash 可稳定匹配但不能替代密文。
- Secret 交付与轮换测试：平台根密钥不出现在镜像层、Git、`docker inspect` 环境变量、Compose 展开、日志、API 或平台页面；仅获授权服务能读取挂载文件；离线副本恢复后可以复现两类测试数据库密码并解密测试 Secret/TOTP seed。DML/平台只读账号代数切换和根密钥 v1→v2 迁移期间请求不中断，外部密文、完整兑换码与 TOTP seed 可重入重加密，旧连接/用户按序失效；未知或缺失根版本一律 fail closed。
- 单机 Docker 恢复测试：停止并 recreate MySQL 容器后所有 control/tenant schema 仍来自显式持久卷且校验一致；生产 `3306` 不监听公网。模拟整台云主机永久丢失，从站外 serving 云拨测首次达到实际失败 quorum 的 P1 事件 UTC 时间开始计时，在全新主机只使用异机数据库备份、对应 manifest 和离线根密钥副本恢复，验证全部租户映射、派生账号连接、外部 Secret 解密、D58 全量 hold/人工审核、关键业务抽样和外部副作用隔离；分别记录 host-hold-ready、首个业务或 DR-only smoke、run completed、故障域外 `/health/external` 成功命中新 origin，以及每个 tenant disposition 的时点。全量安全覆盖和平台管理员恢复后，至少一个原应 active survivor 通过核心 smoke，run 才达到内部安全完成状态；若 sealed survivor 集合中没有可安全 active 的 tenant，必须改用由恢复 wrapper 临时创建、与 tenant/control inventory 完全隔离的 DR-only scratch schema 做数据库派生连接、migration 与读写 smoke，随后销毁，整个过程不得创建 tenant/membership/session/job/provider binding 或发起任何外部调用。只有故障域外探测随后成功命中新 origin 才停止本次主机恢复计时。超过 4 小时只记录内部改进项，不构成对外承诺、发布门禁或自动放行理由。仅保留同机 volume/snapshot、跳过 recovery hold/provider 不确定窗口处理、没有完成规定的业务或 scratch smoke、未取得新 origin 外部成功证据，或到时自动 release 才判失败。
- NAS 拉取备份测试：专用 SSH key 无法取得 shell、端口/agent/X11 转发、执行任意参数、读取根密钥或调用非备份 Docker 操作；中途断网、NAS 满盘、任务重叠、dump/压缩/checksum 失败只留下可清理的 `.partial`，不得覆盖最近成功备份。连续正常运行覆盖小时→日→月晋级与清理边界后，准确保留 48 个小时、30 个每日和 12 个每月成功副本，失败任务不触发清理。完成文件的 manifest、校验和、schema 列表/binlog 坐标与实际内容一致，并可在没有原云主机的隔离环境中恢复；最新成功恢复点年龄超过 90 分钟或连续 full dump 三次超过 20 分钟时必须通知维护者并判定小时级目标失守。权限测试还须证明非备份 NAS 用户和普通 SMB/NFS 客户端无法列出或读取目录，但不把此结果误称为静态加密。
- NAS→云盘同步测试：同步源只能看到完成态 dump/manifest/checksum 和永久 tombstone ledger，无法读取 `.partial`、平台根密钥、SSH/MySQL/云盘凭证或临时恢复数据。模拟同步延迟、断网、云盘满额、NAS 文件被误删和云盘版本回滚，分别记录 NAS/cloud latest-success，不得把旧云盘副本报告为最新；从云盘下载一个完成集合后可通过 checksum/manifest 校验并在隔离环境恢复。普通 dump 的保留/删除不得删除或回退永久 ledger，缺少最新 ledger 时恢复 fail closed。
- 集成测试：认证会话、CSRF、邀请、角色矩阵、订阅状态、所有现有 API。
- 租户逐设备会话测试：Cookie 只含至少 256 bit 的高熵不透明随机 token，控制库只含唯一 SHA-256 token hash；原始 token 不得出现在数据库、URL、HTML、日志、异常、审计、指标或浏览器持久存储。模拟 token hash 碰撞时必须丢弃并重试，不能覆盖已有行。同一短信 challenge 的重复/并发成功校验最多创建一个 session；登录前固定 Cookie、旧登录 token 和登录响应重放均不能复用攻击者指定的 session，成功登录必须签发全新 token 并撤销被替换行。Cookie 使用独立固定名称和 `/` path，且为 host-only、`Secure/HttpOnly/SameSite=Lax`；CSRF token 与 bearer token 分离，CSRF/CORS 门禁有效，tenant/platform 两套 Cookie 互不接受。

- 性能：比较固定单库与动态路由后的关键查询和连接获取开销；p95 超出当前基线 20% 时记录普通待办、优化并重跑，或明确记录保留原因，不设置额外审批门。
- 安全：IDOR/BOLA、会话固定、CSRF、速率限制、secret 泄露、上传和权限提升回归。
- D49 监控信号 E2E：分别移除/停止 CVM Agent，停止 Nginx/Web、MySQL、worker/evaluator 和整台 CVM，模拟 CPU/内存/load、磁盘/inode 水位，数据库连接耗尽、queue depth/oldest age/任务连续失败、backup 超过 90 分钟、dump 连续三次超过 20 分钟、NAS cloud-sync heartbeat stale，以及短信/SF 等 provider 聚合故障；验证每种事件来自预定信号层、按矩阵进入 P1/P2、missing-data 不显示绿色、恢复有迟滞且同 fingerprint 不重复风暴。整机停止后应用自报必须消失，但至少两个外部 serving 拨测点仍产生 P1；内部恢复耗时起点使用 serving 云拨测首次达到实际失败 quorum 的 P1 事件 UTC 时间，而不是人工看到通知的时间，拨测任务无数据本身只产生 P2。host restore 中即使平台后台和 hold 页面已可访问，只要 current recovery run 未达到 D59 的 completed 条件，`/health/external` 仍为 503/P1；达到后其余 held tenant 数和最老 review age只用无 tenant ID 的聚合 P2 状态展示，不能自动 release。仅停止 worker/evaluator 时，`/health/external` 仍为 200、`/health/monitor` 变为 503 并只产生 P2，不得启动整机 DR。撤销自定义消息凭证后必须在维护窗口产生一次隔离的 P2 测试事件，验证真实投递失败会锁存 delivery-unhealthy、使 `/health/monitor` 返回 503 并由独立云拨测链告警；恢复凭证后的显式成功投递测试清除锁存，健康空闲期不能仅因长时间没有告警可发而判 stale。两个端点的 DNS/TLS/status/body/no-store 与直连 origin 都要验证，重复调用不得创建业务数据/job/provider 请求或无界占用控制库连接，响应和腾讯云维度中不得出现版本、租户、数据库、手机号、地址或 Secret；伪造 tenant/query/header 不能改变检查范围。维护静默仍保留事件且到期自动恢复告警。镜像、Compose、端口、进程和依赖清单断言 Core 不存在 Managed Prometheus、Grafana、通用 scraper 或公网 `/metrics`。
- D49/D58 completed 口径同步测试：只有 sealed inventory 全量安全覆盖、至少一个本次恢复的新平台管理员 active，且“经审核可安全 release 的原应 active survivor 核心 smoke”或“没有这种 survivor 时已创建、验证并销毁的 DR-only scratch smoke”恰好一个分支成立，run 才能从 `reviewing` 单次 CAS 为 `completed`；任一 coverage/provenance/销毁证明缺失都保持 `/health/external` 503 和 serving P1。completed 后必须由故障域外拨测确认成功响应命中新 origin 才关闭该 P1；其余 held tenant 数与最老 review age只以不含 tenant ID 的聚合 P2 暴露，worker/evaluator/CVM Agent、`/health/monitor` 或通知链 stale 也只维持各自 P2，不回滚 run、不重开 serving P1、更不能自动 release 或启用 provider。分别测试 completed CAS 与 tenant disposition、scratch 销毁、监控恢复/再次 stale 并发，断言只有一个外部完成时点；4 小时只写内部阶段指标/改进项，未到、超出或计时错误都不改变状态、severity 或门禁。
- 监控通知测试：创建隔离的 P1/P2/恢复测试事件，验证 P1 同时到达已验证手机的电话、短信和邮箱，P2 到达个人微信和邮箱，恢复通知沿原渠道送达；消息内容通过敏感字段 allowlist 检查。任一接收人、模板或渠道变更后重跑；无企业微信或 webhook 时告警链仍完整，重复相同 fingerprint 能收敛且新根因不会被错误静默。
