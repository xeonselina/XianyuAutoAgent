## 16. Observability, SLO and Operations

- 结构化日志统一带 `request_id`, `tenant_id`, `actor_type`, `actor_id`, `route`, `job_id`；PII 和 secret 先脱敏再输出。
- 监控信号维度采用 allowlist，只允许 environment、component、signal key、severity、region 和低基数 result class；禁止 tenant/user/phone/request/job/device/rental/warehouse、原始 URL、自由文本及 provider request ID 成为指标维度或告警正文。租户级故障只在受鉴权平台页面通过内部技术 ID 下钻，不能把客户标识扩散到腾讯云指标标签。
- D49 第一层使用腾讯云 CVM/云监控基础指标。生产主机必须安装并运行官方监控 Agent，至少覆盖实例状态、CPU/load、内存、磁盘/分区、网络及 Agent 数据新鲜度；Agent 未安装、停止上报或指标 stale 本身就是告警，不能因曲线为空被解释为正常。磁盘 inode 和 Docker/Web/MySQL/worker 进程状态若不在基础指标中，由下述轻量 host/application evaluator 补充，不为此引入通用采集器。
- D49 第二层使用腾讯云云拨测从云主机外访问两个专用端点。`GET /health/external` 表达 serving plane：DNS/TLS/Nginx/Web、控制库最小短查询失败返回 503；当外部部署 marker 表明正在执行 D58 host restore 时，还必须以同一最小查询确认 current recovery run 已达到 D59 的 `completed` 条件，在此之前即使平台后台/hold 页可访问也继续返回固定 503，不能把 recovery UI 冒充租户安全读写已经恢复。completed 后其他 tenant 仍可各自 held，端点只返回全局 serving 成功，未完成审核数量改走不含 tenant ID 的 P2 聚合状态。只有来自不同拨测点的实际 DNS/TLS/HTTP/status/body 失败达到 quorum 才形成 P1 并作为整机 DR 内部耗时起点。`GET /health/monitor` 只表达 worker/evaluator heartbeat 和已锁存的自定义消息投递失败，异常时返回 503/P2，不改变 serving 状态或启动整机 DR。拨测任务自身无数据对两个端点都表示监控失明 P2，不等于已证明 serving outage。两个端点都不接收 tenant/query 参数，不经过 CDN/页面缓存，不执行业务写入或 provider 调用，只返回固定最小 body，响应带 `Cache-Control: no-store` 且不返回版本、主机、数据库、队列数、租户或错误详情；它们使用独立的极小连接/信号量预算、严格超时和 Nginx 端点专用限频，不占用租户连接池、不遍历租户库，超载时快速失败而不得启动无界控制库查询。初始按 1 分钟频率和至少两个不同 IDC 拨测点分别配置；Phase 0 只记录 provisional 频率、拨测点、超时/quorum 和预算计划，端点与云拨测实现后再通过受控非生产故障测试修订为版本化参数并作为普通任务勾选。
- D49 第三层只维护少量 `platform_operational_signals` 当前状态：MySQL 连通/连接耗尽，Web/worker/evaluator heartbeat，队列最老等待时间与持续失败，最近一次经 checksum/manifest 验证的数据库备份年龄和 dump 时长，以及短信、SF/闲鱼/快麦的系统性认证/限流/错误状态。provider 健康仅聚合真实业务调用，不定时发送验证码、创建顺丰运单或制造其他外部副作用。NAS 每次在本地备份完成 checksum/manifest 验证后立即通过既有 forced-command SSH 身份提交独立、幂等的 `backup-status-ack`；云盘同步完成后再提交独立 `sync-status-ack`。两者分别计算 freshness，任一方不得等待或推断另一方成功；应用/云主机仍不持有云盘账号或凭证。
- 轻量 evaluator 只在状态变化、需要重复提醒、恢复或显式发布/凭证变更测试时，通过腾讯云 `SendCustomAlarmMsg` 等当前支持的自定义消息接口写入 D38 通知链；使用独立最小权限 CAM 身份和宿主机只读 Docker Secret，不复用主账号长期密钥，不把凭证写入控制库、镜像或环境变量值。稳定 fingerprint、幂等 delivery ledger、有限重试和迟滞防止告警风暴。真实投递尝试失败或超时后必须原子锁存 `delivery_unhealthy`，使 `/health/monitor` 返回 503 并由独立 P2 云拨测链路接管告警；只有后续真实事件或显式测试成功投递才能清除锁存。健康空闲期没有应投递事件时不按“最后一次发送时间”判 stale，也不发送周期性 canary；evaluator heartbeat 只能证明 evaluator 存活，不能证明腾讯云消息投递可用。
- Core 不建设通用时间序列数据库、Managed Prometheus、Grafana、metrics scraper 或完整 tracing backend；只保留当前健康状态、只追加告警生命周期和结构化日志。Web → MySQL job → worker → provider 继续传播 `request_id/job_id/correlation_id`，用于日志串联而不承诺分布式 tracing 产品。请求率、全量延迟分位、细粒度租户用量与业务大盘留到有明确容量需求后再单独评估。

| 信号层 | 最小信号与来源 | 缺失数据语义 | 初始级别 |
|---|---|---|---|
| CVM 基础监控 | 实例状态、Agent、CPU/load、内存、磁盘/分区、网络；腾讯云 Agent/宿主机补 inode | instance/Agent 无数据不得为绿色；实例不可达为 P1，单资源逼近阈值先 P2、进入危险水位升为 P1 | P1/P2 |
| 站外 serving 云拨测 | 生产 DNS/TLS、Nginx、Web、控制库最小查询 | 实际 DNS/TLS/HTTP/status/body 失败达到 quorum 才按对外不可用处理，并启动内部恢复耗时记录；拨测任务无数据另报监控失明 P2 | P1（实际失败）/ P2（拨测无数据） |
| 站外 monitor dead-man 云拨测 | worker/evaluator heartbeat、`delivery_unhealthy` 锁存 | heartbeat stale、投递失败锁存或拨测任务无数据表示后台/告警链降级，不等同 serving outage | P2 |
| 应用/worker | MySQL 连接失败/耗尽、worker heartbeat、queue depth/oldest age/持续失败、provider/SMS 聚合错误 | heartbeat stale 或 evaluator 未更新为异常，不能沿用最后一个 ok | MySQL/认证整体不可用 P1，其余 P2 |
| NAS 状态 | 已校验 backup latest-success/duration、云盘 sync latest-success/safe result | backup ack 超龄按 D29 P1；sync heartbeat 超龄 P2，不能从 dump 成功推断 sync 成功 | P1/P2 |

- `MonitoringPolicy` 必须版本化且拒绝缺失配置，至少包含 probe interval/timeout/quorum、连续失败与恢复次数、missing-data 窗口、健康端点连接预算/限频、CPU/内存/load、磁盘/inode 水位、worker/evaluator heartbeat stale、`delivery_unhealthy` 的失败锁存/清除规则、数据库连接高水位持续窗口、queue depth/oldest age/job failure、provider error/latency 聚合窗口、backup age/duration、cloud-sync age、自定义消息重试与重复提醒间隔。D29 已确认 backup age 超过 90 分钟为 P1、full dump 连续三次超过 20 分钟触发架构切换评估；Phase 0 只登记 provisional 非空策略和核对计划，其余数值在端点/evaluator 实现后的受控非生产故障测试中修订。勾选项目完成任务时不得仍为空或依赖代码隐式默认值，但不需要独立审批。
- 腾讯云产品名称、指标和接口可能变化，部署 runbook 每次新环境建立时复核官方的 [CVM 监控指标](https://cloud.tencent.com/document/product/248/6843)、[云拨测 HTTP(S) 任务](https://cloud.tencent.com/document/product/248/87257)、[云拨测告警](https://cloud.tencent.com/document/product/248/87272)和 [SendCustomAlarmMsg API 迁移说明](https://cloud.tencent.com/document/product/248/81039)；如果接口被下线，只能替换为腾讯云当期等价的基础监控/站外探测/自定义消息能力，不能静默删除信号层或借机引入未批准的第三方监控。
- D38 通知使用腾讯云消息接收人，不自建公开 webhook：维护者的个人微信、手机和邮箱均须完成渠道验证。P1 包含云拨测确认 Core 对外不可用、MySQL 不可用、磁盘/inode 危险、最新成功数据库恢复点超过 90 分钟、数据库身份/跨租户隔离校验失败、根密钥/关键 Secret 导致生产启动失败及生产短信认证整体不可用，全天同时电话 + 短信 + 邮件；P2 包含任务积压或重复失败、数据库连接持续高水位、provider 系统性错误/延迟升高、备份耗时连续接近切换阈值、NAS 报告的云盘同步落后或任一信号 stale 等，使用微信 + 邮件。
- 同一根因按 fingerprint 收敛并设置重复通知间隔，避免故障风暴；状态恢复必须沿触发时渠道发送恢复通知。首次上线以及接收人、模板或渠道变更后逐渠道发送测试通知并记录送达结果；测试失败时对应普通任务保持未勾选，修复后重试，不形成独立发布审批或 hard release gate，也不要求另建固定周期演练任务。
- 计划维护使用有明确开始/结束时间、操作者和原因的告警静默窗口；信号与事件仍记录，窗口超时立即恢复通知。D49 只负责维护者内部告警，不自动创建公开状态页或向全部租户群发事故通知；计划维护仍按已确认规则提前通知，未来若需要客户事故通知须单独决定。
- 告警正文只允许环境、组件、severity、UTC/上海时间、非敏感资源标识、聚合指标和受鉴权的站内/runbook 链接；不得包含验证码、Secret、完整手机号、客户地址、月结号、邀请 token、租户自由文本或原始 provider 请求/响应。
- D22 的同机 Docker 拓扑不具备高可用。D10/D29/D59 已确认 Core 只按 best-effort 对外提供服务，不承诺 99.9% 等数值可用性 SLA、严格 RPO 或硬 RTO，也不设置停机或数据损失赔偿；可预见的计划维护提前通知。小时级恢复点与标称 RPO 约 1 小时是能力目标，4 小时只是整机恢复的内部演练参考值；备份间隔、实际 dump 时长与失败重试共同决定实际 RPO，恢复耗时和各阶段仍通过全新主机演练记录、改进。
- 每份控制库/租户库备份 manifest 记录备份时点、租户数据库映射、所需 `root_key_version` 及其指纹，以及当时已知的 `tombstone_head_sequence/head_hash`，但绝不包含根密钥；根密钥离线副本不得与唯一数据库备份置于同一主机、同一归档或只依赖同一恢复口令。恢复时 manifest head 可以落后于 NAS 最新 ledger，但不能领先于可取得且验证成功的 ledger head。
- 提供 Core runbook：租户暂停/恢复、密钥泄露、误删恢复、整机灾难恢复、队列堆积、provider 故障和跨租户安全事件。支付 webhook 重放属于未来 Commercial SaaS，不是 Core 运行手册或发布门禁。

D64 的项目流程边界：Phase 0 只核对当前可独立取得的云账号/产品 capability、备份目标和 provisional 策略，并记录实现/测试计划；它不要求健康端点、monitor adapter、NAS wrapper、平台根密钥 loader、备份 artifact 或恢复演练结果已经存在。全部运维实现及首次生产规模演练前可执行的必要测试作为普通可勾选任务完成，与全项目实现、默认租户迁移/回滚工具一起直接产生 `project_complete_at=T`，无需签字、receipt、evidence digest、阶段审批或 hard release gate。首次生产规模演练、实际切换、切换后 48 小时观察和 contract cleanup 不在 T 的前置范围；演练安排在不早于 `T+168h` 的可用窗口。影响迁移结果的实现变更在重跑相关测试后更新 T；不存在迁移冻结、冻结例外或解冻流程。该简化不改变本章 D49/D58/D59 的运行时 fail-closed、recovery hold 和 tenant release 安全规则。

### 16.1 Host disaster recovery (D10/D58/D59 confirmed)

- 内部恢复耗时从站外 serving 云拨测首次达到“实际探测失败 quorum”的 P1 事件 UTC 时间开始；新主机申请、系统/Docker 安装、镜像拉取、NAS 下载、数据库导入、DNS/IP 切换、D58 recovery-hold 安装、平台管理员恢复、tenant review 和 smoke test 都计入。D59 的内部安全前提是最新 tombstone 与全量安全覆盖完成、至少一个新平台管理员恢复，并由一个经审核可安全 release、原应 active 的 survivor 完成路由、库存/rental 与 provider 隔离 smoke；若没有经审核可安全 release 的 active survivor，则改走下述 DR-only scratch smoke。满足内部前提后 run 从 `reviewing` 直接进入 `completed`；故障域外 `/health/external` 首次以成功响应命中新 origin 是主机恢复完成的唯一外部判据。恢复工具记录 `host_hold_ready_at`、条件适用的 `first_tenant_smoke_at` 或 `dr_scratch_smoke_at`、`host_recovery_completed_at` 及每个 `tenant_released/kept_closed_at`；这些只是阶段耗时，不增加恢复状态。4 小时仅作内部参考，超时记改进项但不改变安全状态，也绝不能为赶时间批量 release。
- 若平台管理员审核 survivor 后确认没有经审核可安全 release 的 active survivor，provisioner 才能创建随机命名、绑定 current `run_id` 和一次性 DR route handle 的临时 scratch schema/account。scratch 明确不是 tenant：不写 tenant/membership/invitation/兑换码，不装 provider secret，不进入普通 tenant router、注册或续期流程，也不启动短信、job、worker 或任何外部调用；恢复 CLI 仅通过 DR-only route harness 验证 schema identity、目标路由、DML 最小 grant、跨 schema 拒绝，并执行最小 inventory-rental create/read/update/delete。验证完成必须先 `DROP USER`、删除 scratch schema并负向确认均不存在，才保存不含测试数据或密码的 schema/grant/test/destroy 摘要证明并允许完成；任何创建、验证、销毁或摘要步骤失败都保持 `reviewing`。该 fallback 不创建伪租户，因此不会与“新注册/兑换码仅在 current run completed 后开放”的门禁形成死锁。
- 版本锁定的 Compose/部署脚本、镜像引用、数据库 migration 工具和恢复 runbook 必须保存在故障主机之外；云账号恢复、SSH、NAS 备份目录访问和平台根密钥离线副本均有独立可用的 break-glass 路径。恢复脚本只接受已校验 manifest 中的 schema 白名单和版本，不对任意 dump 执行生产导入。
- 任何受支持的生产旧恢复点导入都只能通过这一套版本锁定、root-owned 的 restore wrapper，wrapper 只接受 manifest/schema 白名单、校验摘要和明确的 `full/control/tenant-only` 模式，普通应用、migration CLI 和 Web 均无直接导入入口。同机导入 control plane 或 full restore 时，wrapper 必须在首笔数据库变更前轮换数据库外 marker generation、令 `/health/external` fail closed、停止 tenant route/worker/scheduler/provider，并无条件建立新的 host-restore run 走完整 D58，不能因 installation ID 或主机未变而走快速开放路径。tenant-only schema restore 必须先在控制事务为目标 tenant 安装 restore hold、递增 access version、把 DML desired state 置 locked，再由 provisioner 在 fencing + MySQL advisory lock 下锁定并排空全部 DML 代数、隔离 route/job lease/provider submission；旧 schema 只可导入不可路由的 staging schema，核对 `database_identity`、schema version、表/行摘要、路由目标、最小权限与跨 schema 拒绝后才可在同一屏障下受控切换，之后仍须按单租户审核决定 release/keep-closed。直接使用宿主机 root/DBA 权限绕过 wrapper 可以同时篡改 MySQL 和外部 marker，这是明确接受并登记的 root residual risk；只能用最小 root 权限、命令审计、marker/manifest 核对和恢复演练降低风险，产品与文档不得承诺技术上绝对阻止此类绕过。
- D49 的 CVM 告警策略、云拨测任务、消息模板、最小权限 CAM policy 和 `MonitoringPolicy` 同样版本化保存在故障主机之外。新主机/DNS 切换后，D59 只以故障域外 `/health/external` 的成功响应确实命中新 origin 作为主机恢复完成的外部证据；CVM 对象/Agent 数据、`/health/monitor`、worker/evaluator heartbeat 及同一告警生命周期的恢复通知仍应逐项恢复，但缺失或 stale 只保持独立 P2 后续事项，不阻止 `reviewing → completed`、不重新打开已关闭的 serving P1，也不形成第二个恢复完成状态或时间点。worker/scheduler/provider 是否启用仍服从逐租户 hold、配置核对和提交门禁，不能把这一轻量完成判据解释为允许全局重放。
- 新主机首次启动强制设置外部 `DISASTER_RECOVERY_MODE=1`：Web 只开放恢复 CLI/setup/验证入口，普通 worker、scheduler、tenant 短信、顺丰、快麦、闲鱼和其他第三方写操作均不启动。唯一例外是 restore wrapper 进程内的 root-owned、current-run-only cleanup executor：它不复用普通 worker 队列，只能执行本次 normalization 生成且列入 sealed allowlist 的 system cleanup，逐项核对 installation/marker/run、normalization item、generation/fencing 与 backup/DDL + MySQL advisory lock，不挂载 provider 凭证、不能创建新码/tenant/membership/subscription或处理普通 job；executor 完成/失败 disposition 是 coverage 的一部分，run 离开 installing 后立即停用。新主机 provisioner 必须在导入数据库前创建随机、非秘密、root-owned 的 installation ID；目标路径必须 absent-by-default 并使用 one-shot/O_EXCL 语义，发现来自旧主机的现存 installation ID 或 marker 时立即 fail closed。恢复 CLI 把新 installation ID、随机 run UUID 与新的只读 marker 绑定后才写 current run，应用要求三者匹配；旧 dump 中的布尔值/completed run，即使搭配被误拷贝的旧 marker，也因当前 installation ID 不符而不能开放。installation ID/marker 明确排除于 Git、镜像、Compose bundle、数据库 dump、NAS/云盘同步及可复用 CVM/磁盘镜像；普通同机重启保留并核对，整机恢复绝不复制。没有 current run、marker 缺失/不匹配或恢复工具未完成覆盖证明时，Compose/readiness 必须 fail closed。
- 普通重启的定义是继续使用同一控制库及持久卷、同一 installation/非 restore marker 和对应根密钥版本，只重启 Web/worker/MySQL 容器或原主机操作系统。该路径不得进入 D58：`platform_admins` 状态/auth version、confirmed TOTP 密文与 `last_accepted_time_step`、恢复码 generation/used 状态及平台服务端 session 均保持原值并服从原过期时间；重启前已接受的 TOTP 时间步重启后仍拒绝，未使用恢复码继续可用。缺失/错误根密钥或密文无法解密时 readiness/login fail closed，但不能自动作废或重置因子；恢复正确根版本后原 TOTP 继续可用。只有受支持的 control/full restore、D58 normalization、主动 TOTP 替换/CLI 重置或明确安全事件才使旧因子/session 失效；tenant-only schema restore 不触碰平台认证行。
- dump 先导入与应用网络隔离、不会被 Web/worker 连接的 staging MySQL；不能把包含待筛查 tenant 的旧 `--all-databases` 流直接导入已开放的生产实例。按 manifest 挂载正确 `root_key_version` 后恢复 control plane 与 tenant schema，但暂不创建租户数据库账号或业务路由；逐库核对 `database_identity`、schema version、表/行数摘要。未知根版本、已提交/可路由 survivor 缺失 schema 或身份不匹配均 fail closed。provisional database 缺失只允许两类可证明例外：其一，只被非终态 registration attempt 引用，且不存在权威 `tenant_registration_commits` 行或任何 source-linked 部分提交事实；其二，attempt 已终态 `superseded_by_replacement`，唯一 replacement/source/successor lineage 完整，普通 janitor 的 succeeded outbox、immutable terminal cleanup disposition、资源清单摘要和认证 drop/negative proof 均匹配。前者先与 attempt、replacement link、内部 integrity incident 和 system-cleanup disposition 一并隔离，待 D58 把 code 置 recovery_revoked、旧 provisioning/cleanup generation与 lease失效并核对无 published route/可登录账号后，由 current-run cleanup executor 收口；后者直接以已认证的历史 terminal disposition 从 survivor schema expected-set 排除，同时仍封存 lineage/attempt/code/outbox 供 coverage。两类都永远不能作为 survivor 开放。缺少任一判据、存在未收口 integrity incident，或发现部分 commit/source-linked 事实时仍 fail closed，只能由 root-owned ops 流程处理，不能把普通 tenant 丢库伪装成 D54 补发或普通 janitor 清理。
- 在 staging 控制面记录恢复后、创建任何租户 MySQL 用户或开放业务路由前，必须从 NAS 单独读取可证明为最新的永久 deletion tombstone ledger；若 NAS 不可用，则改从 D31 云盘副本读取。恢复流程验证 sequence 无缺口、hash chain、head checkpoint MAC 和 artifact checksum；命中的 tenant/database UUID 先从 survivor 集合排除，但在清除旧快照带回的 schema、provider account/binding、membership、job、Secret 和 route 前，必须先完成下述 SF claim 核对与处置。若旧 dump 的 SF claim current owner 仍指向命中的 tenant/account/warehouse，tombstone application 必须在 system-only fencing 下先失效其旧 reservation/operation，再把 claim 单调置为 `released` 并清空 owner、记录 current-run provenance；全局 claim 行本身保留，不能随 tenant 数据删除。快照中已经由其他合法 tenant/warehouse 取得且与 binding 双向一致的新 owner 不得被旧 tombstone 清除；任一 owner/account/binding orphan 或无法证明归属都使恢复 fail closed，只有核对与处置完整提交后才能删除上述 tenant-owned source rows。该 ledger 不得被选定数据库 dump 中更旧的 tombstone 表覆盖；manifest head 领先于最新可验证 ledger、ledger 缺失/截断/版本倒退或 MAC 失败时维持 disaster-recovery mode。
- 应用最新 tombstone ledger 后，恢复 CLI 先从 survivor 集合清除命中 tenant 及其 registration commit/source rows，再把旧 current recovery run 标为 superseded并建立新的 run=`installing`。在首笔 normalization mutation 前，必须从隔离 staging 的同一只读 snapshot 按 survivor 白名单封存 `disaster_recovery_normalization_items`、逐类 expected count 和 digest；之后不得从已变更状态重新计算或缩小 expected 集合。随后幂等安装安全覆盖：每个 survivor 创建 state=`held` 的 `tenant_recovery_holds`、递增 tenant access version，并在同一控制事务把 `tenant_databases.desired_login_state` 设为 locked、递增 login-state version、绑定 current run；所有 survivor 的 `tenant_registration_commits`、registration attempts、replacement links、内部 integrity incidents 和 system-cleanup generations/leases 都必须有本次 current-run normalization item。所有 active/reserved 兑换码转为不可逆 `recovery_revoked`，已 revoked/redeemed 的 source code 与 immutable replacement chain 保持原更严格历史且同样进入 coverage；全部 tenant/platform session 撤销且相应 user/admin auth version 递增；全部 pending invitation 置 superseded并释放席位；所有非终态 SMS challenge/sensitive-action intent 失效。所有非终态 registration attempt 进入 `recovery_review`，推进 provisioning generation、失效 worker lease；旧 ordinary retry/replacement worker 永不续跑。restore wrapper 只允许两种可自动证明的 registration 处置：完整 commit 与全部 immutable anchor/合法 lineage 一致时保留历史成功；commit 与全部 source-linked 成功事实均不存在时，为实际存在的 provisional schema/account/route 创建绑定 current run 的 system recovery cleanup。该 cleanup 推进独立 cleanup generation，只能由上述 installing-mode cleanup executor执行，删除或隔离资源并写 terminal disposition；无 provisional 资源时直接写经负向核验的 no-resource disposition，不创建空 outbox。它不得改写 recovery-revoked code、创建 membership/subscription、补发新码或恢复注册。任何部分 commit、immutable anchor、replacement lineage或摘要不匹配都自动 fail closed并阻止 run完成，须由无 HTTP入口的 root-owned ops流程处理后重新运行；当前 hold/route/account revision因合法恢复或轮换而高于 commit-time anchor本身不是 mismatch。每个 normalization disposition记录 current run provenance；重跑只能完成sealed inventory的剩余动作，不能复活、重复释放资源或把漏处理对象从 expected集合移除。
- 同一 normalization 失效所有旧 job lease，并失效或冻结旧 suspension action/control-outbox claim、deletion executor/lease 与 tenant database account rotation lease；相关 aggregate/request/action/rotation 行不得因失去 lease 从 sealed inventory 删除，必须写入 current run 的处理 provenance 供 coverage 核对。只有明确不可再执行的终态 job allowlist 可保持原状态，其余任何非终态、可重试或副作用不确定 job 均进入 `recovery_review`，包括 scheduled/pending/leased/running/retry-wait/provider_submitting/suspension_blocked/needs_review 及后续新增但未进入终态 allowlist 的状态。旧 worker 恢复逻辑不得直接处理这些行；按稳定 provider order/idempotency ID 查询可对账 provider，已成功的动作只补写账本，明确未提交/失败的动作也只能在 tenant release 后以新 run/access version 新建 job，未知打印等动作继续隔离并人工确认，禁止整批盲目重放。
- 对所有 survivor 用 provisioner 重建平台只读账号并验证 `database_identity`、正向读取和跨 schema 拒绝；DML current/candidate/from/to/prepared/draining/孤儿代数则在 `desired=locked` 已提交后，使用 D52 共用的控制库 fencing + MySQL advisory lock 一律以 `ACCOUNT LOCK` 重建、逐个核验，并在仍持锁的收口事务把完整 identity inventory 的 `observed_login_state`/coverage provenance 记为 locked。任一身份无法解释或无法证明 locked 时保持 run installing，不能因快照显示 active/expired 就提前解锁、发布业务 route或允许并发 rotation；held 期间任何 rotation/fleet account mutation 都继承 current run 的 desired locked；快照带回的 rotation aggregate 与所有 rotation lease 必须写 current run disposition，旧 lease 永不恢复执行，只允许新 fencing owner 将账号收敛到 locked。对快照中任一未 resolved suspension，DR-only normalization 还要 supersede 旧 freeze/resolve action、递增 suspension generation 和 tenant `access_version`、把聚合置为 freezing，并创建绑定新版本的 system `enforce_locked` action/outbox；只运行这个新的单调收紧屏障，成功后 suspension=active，不得续跑备份中的 resolve。恢复工具版本低于 manifest/ledger 的 minimum restore version 时必须拒绝。
- 旧 dump 可能带回后来已停用的平台管理员、旧密码 hash、已经撤销的 session、已经消费的恢复码、旧 setup challenge、未确认 TOTP 或较旧 confirmed TOTP。导入后先把全部恢复出的平台管理员置为 `recovery_pending`，递增 `auth_version/setup_generation/recovery_code_generation`、写 current run provenance、撤销全部 session/setup challenge，并把全部 current/未确认 TOTP credential 置 replaced/invalidated；`/platform` 普通登录与能力保持关闭。受控 CLI 显式核对当前允许的管理员名单，只为保留者创建绑定本次 run、current auth/setup generation 的短期 `dr_recovery` challenge，并要求至少一人通过 setup-only 页面重新设置密码、确认全新 TOTP、一次性获取新恢复码后变为 active；未显式确认或备份后已停用的账号保持 disabled/recovery_pending。旧 session、旧密码、旧/未确认 TOTP、旧 setup token 和旧恢复码均不能直接恢复访问。registration integrity incident 不因管理员恢复而获得 Web 处置入口：完整或全不存在的证据只能由 restore wrapper 按上一条确定性处理，部分/不一致证据持续阻断 normalization，并交给 root-owned、命令审计的离线 ops 流程修复后重新运行。不得提供 DR-only integrity-validation 页面/API，也不得借 setup-only session 授予普通平台 capability、tenant route、DML、worker、短信或 provider 权限。
- normalization 完成后，恢复工具必须以首笔 mutation 前封存的 inventory 为 expected 集合，逐类核对 survivor tenant/hold、users/auth version、tenant sessions、code、invitation、challenge、intent、所有 survivor registration commit 的 immutable anchor 与合法 lineage、registration attempt、内部 integrity incident、replacement link/source/successor、attempt provisioning generation/lease 与 system-cleanup generation/lease disposition、所有非终态 job 及 lease disposition、suspension aggregate/actions/control outbox、deletion requests/executor state/leases、tenant database account rotations/leases、platform admins/auth version/setup generation、platform sessions/setup challenges/TOTP/recovery generations，以及控制库与 MySQL 实际 DML identity 的 desired/observed locked 收口。actual digest 必须包含 required terminal state、current run/marker、provisioning/cleanup execution generation 和 fencing provenance，不能只比较仍存在的 UUID；任一未终结 integrity incident、部分 registration commit/anchor/lineage、replacement chain 分叉/缺失、system cleanup 未产生 current-run terminal disposition/负向证明/审计、缺行、重复、未知状态、旧 run provenance、摘要不符或中途崩溃都把 run 留在 `installing/failed_closed`，不得以普通补发、状态直接转换或跳过 cleanup 掩盖。commit-time revision 与当前 revision 只按历史 lineage 验证，不做相等比较。只有 tombstone head、根密钥/数据库身份、全部收紧覆盖和至少一个新平台管理员认证均验证成功，run 才能进入 `reviewing`。此时可由受审计命令关闭全局 `DISASTER_RECOVERY_MODE`，但只开放平台后台、平台 SELECT-only 和统一恢复中页面；所有 tenant 仍由独立 hold 拒绝，worker/scheduler/provider 仍默认关闭，`/health/external` 也不能把“Web 能显示 hold 页”冒充租户安全读写已经恢复。
- 首笔 normalization 前封存的 survivor 在 run 已进入 `reviewing` 或 `completed` 后若由 D26 正常删除，不能从 expected count/digest 中移除，也不能重算更小的 survivor 集合。D26 完成事务必须为该 tenant 的原 tenant/hold、registration commit 与全部 source-linked normalization item 追加同一个 run-scoped `disposition=tombstoned`，绑定 deletion UUID、永久 ledger 的 tombstone sequence/hash 和 current run；actual coverage 以这些终态 disposition 对应原 expected item，后续核验同时验证 ledger head 未倒退，不再要求被合法删除的普通 source rows 存在。缺失任一 disposition、sequence/hash 不匹配或只删行不留证明均为 coverage 失败；该 tenant 永久没有 release 入口。
- 平台管理员使用本次 DR 新建的 session 和近期 TOTP/恢复码，只能选择单个 tenant、填写非敏感原因/证据类别，并提交 decision=`release/keep_closed` 及 expected run/hold/tenant/DML-login revision。两个 decision 都按 6.2 统一锁序复核 current run、tombstone/deletion、D52 suspension 和 subscription。`keep_closed` 保留 D58 overlay 和 desired locked；`release` 移除 overlay并显露底层 gate：底层 active/expired 时复用 D52 的控制库 fencing + MySQL advisory lock，旧 published generation 全程保持 locked，只临时解锁并验证一个尚未发布的 candidate generation，其他代数保持 locked 或撤销；仍持锁的最终 CAS 成功后，才把 candidate 发布为唯一 current route 并把 desired/observed 改为 active。final CAS 前进程崩溃或版本失配时，应用 route 继续 deny，接管 reconciler 必须先重锁并撤销 candidate，不能把临时验证账号当成已开放账号。底层 suspended/deletion 时可把 hold 标为 released，但 desired/DML 保持 locked，之后由正常 D52 resume 或删除撤销流程在新的安全动作中收口。最终 decision、tenant access-version、session 再撤销、route/effective-state 投影、action 与平台审计原子提交；任一步失败、死锁重试或并发更高门禁获胜都必须在释放 MySQL lock 前按最新 effective desired state 收敛。若快照 active 但外部核对表明故障前已暂停，应先在 hold 下创建 D52 freeze，再决定 release（显露 suspended gate）或 keep_closed，不能直接开放。
- tenant release 只移除 D58 overlay：expired 的全部有效成员仍只进入统一过期提示页，Admin 仅可续期/注销、Operator 仅可查看提示/注销，账号安全、集成设置和顺丰解绑均不开放；D52 suspended 仍暂停且无解绑例外，D26 cooling/committing/deleted 仍服从删除，tombstoned tenant 永无 release 入口。release 不创建/消费顺丰解绑 challenge/intent、不释放月结账号全局 claim，也不改写既有 shipment 的 warehouse/account/integration/binding revision 或寄件资料快照；expired 必须先续期，suspended 必须先正常恢复且若落 expired 再续期，最终 active 后原绑定仓 Admin 才能按 D50/D48 普通解绑。release 也不恢复任何 recovery-revoked 兑换码、pending invitation、challenge、敏感 intent、registration attempt/system-cleanup execution、job 或 provider operation。替代码只能在 current run completed 后通过普通补发事务生成：服务端从 source code 逐字段继承 immutable plan revision UUID、entitlements schema version、canonical entitlement snapshot/digest 与 exact duration，只接受平台选择的未来 deadline，原 recovery-revoked code、旧 attempt 与 replacement lineage 永不复活或改绑。worker/provider 可在平台逐租户完成配置核对后仅为 released+active tenant 分批启用，每次 fan-out/lease/submission/call 仍实时检查 current run/hold，旧 `recovery_review` attempt 绝不原地回 pending。
- D58 不提供 D57 的租户身份恢复能力：normalization、平台管理员 DR setup、tenant review、keep_closed/release 和 tenant-only restore 均不得代替旧手机号 OTP、直接编辑 canonical 手机号、把旧 user/membership 映射到新号，或把已撤销的 session/challenge/intent 重新变为可用。release 后只有租户底层已经是可管理的 active 状态且已有另一名 active Admin 时，才可由该 Admin 走普通“移除旧 membership并撤销旧认证状态 → 新号邀请 → 新号 OTP 接受”流程；恢复出的最后一名 Admin 无旁路，平台 global read-only、恢复 CLI 和 root-owned integrity ops 都不能借灾备权限执行产品身份修改。旧 user/membership UUID、审计 actor、订单/rental/shipment 创建审批人与其他业务归属及其快照在恢复、移除和重邀前后均保持原值，新身份不能覆盖、合并或追溯改写它们。
- 在全量安全覆盖、至少一个新平台管理员恢复，并由至少一个经审核可安全 release、原应 active 的 survivor 完成路由、库存/rental、隔离和 provider 门禁 smoke 后，recovery run 以单次 CAS 从 `reviewing` 直接进入 `completed`；没有经审核可安全 release 的 active survivor 时，只能以已成功验证、销毁并保存摘要证明的上述 DR-only scratch 替代，不经过其他恢复中间状态。CAS 后 `/health/external` 才可返回正常；故障域外探测首次确认成功响应来自新 origin 时写入 `host_recovery_completed_at`，它是 D59 唯一外部完成证据而不是新的 run 状态。CVM Agent、worker/evaluator heartbeat、`/health/monitor` 和告警/恢复通知链未恢复均作为 P2 后续，不构成第二完成点；未 release/kept_closed 的 tenant 永久保持 held，不会因 run 状态自动开放，后续逐租户审核继续记录。不到或超过 4 小时都不能自动 release。恢复事件持续记录告警、各阶段时间、backup/root/tombstone/run version、丢失窗口、每租户处置、隔离 operation 和内部参考目标是否达成。D30 已确认正式对外前至少成功手工完成一次全新主机恢复；安全/数据门禁未通过不得上线，单纯超过参考时长只形成改进项。通过后不自动调度或设置固定演练周期，工具继续支持项目负责人按需运行并保存结果。

### 16.2 NAS pull backup workflow (D23 confirmed)

确认的数据流：`NAS scheduler → restricted SSH key → cloud backup wrapper → MySQL consistent compressed dump stream → NAS restricted plaintext directory → verify/retention → restricted status ack → NAS cloud-drive sync of completed artifacts → restricted sync-status ack`。

- NAS 发起全部连接，因此家庭路由器不需要映射端口，云主机也不保存 NAS 登录凭证。云防火墙在家庭公网 IP 稳定时进一步限制 SSH 来源；否则仍使用独立 key、登录速率限制和 SSH 审计，不能仅依赖修改端口。
- `authorized_keys` 对该 key 使用 forced command，并关闭 PTY、agent/X11/端口转发。forced command 只调用 root-owned、不可由备份用户修改的 wrapper，忽略或严格枚举客户端参数；备份用户不得加入 `docker` group，因为 Docker socket 等价于宿主机 root。若 wrapper 需要 root，只允许一条精确的 passwordless sudo 规则。
- wrapper 从 root-only Docker Secret/权限文件读取专用 MySQL backup credential，不把密码放在 SSH command、进程参数、NAS 脚本或输出中。该 MySQL 用户只拥有逻辑备份所需的跨 inventory schema 只读/metadata 权限，不具备写入、建库、授权或读取应用根密钥的权限；新租户 provisioning 必须同步授予其最小备份权限。
- wrapper 先取得平台 backup lease，阻止 provisioning、DDL migration、账号轮换和 schema 删除进入临界区，但不长时间阻塞普通 InnoDB DML；随后从控制库生成并校验允许备份的 schema 白名单，并以同一 `mysqldump --single-transaction` 兼容能力完成 control plane + 全租户一致性逻辑快照。具体 MySQL 版本参数由 Phase 0 capability test 固定，不能把数据库名直接拼接自不可信输入。
- dump manifest 至少包含 backup ID、UTC 时间、MySQL/app schema 版本、控制库和 tenant schema/UUID 映射、记录数摘要、可用的 binlog 坐标、所需 `root_key_version` 及非敏感指纹、当时 `tombstone_head_sequence/head_hash` 和 minimum restore version。manifest 不包含根密钥、数据库密码、完整 DSN 或第三方明文 secret；备份 schema 白名单必须是可信 registered schemas 减去已经生效的 tombstone tenant/database UUID，不能只按 tenant status 判断。
- D26 的 restore-exclusion tombstone ledger 与可轮换的数据库 dump 分开保存：只追加 tenant/database UUID、deletion UUID、执行时间、ledger revision 和校验摘要，不含名称、手机号或业务字段，也不随 48 小时/30 日/12 月 dump 保留策略删除。NAS pull 在本地落盘、fsync 并验证 ledger 后，才可通过同一受限 SSH 身份调用严格枚举的确认子命令回传 backup/ledger revision 和 checksum；云盘同步确认后再用独立枚举的 `sync-status-ack` 回报已知 backup ID、UTC 完成时间、checksum 和安全 result code。两种 ack 均幂等，wrapper 不接受路径、provider 名称、自由文本、shell 片段或任意命令，也不取得云盘凭证；服务端只有收到匹配 ledger ack 才允许 D26 drop schema，sync ack 只更新 D49 健康状态而不影响 tombstone 安全屏障。
- D24 已明确不做 NAS 静态加密：dump 可在云端流式压缩，经 SSH 传输后以 `.sql.gz`/等价压缩明文落盘；gzip/zstd 只减少体积，不提供保密性。目录由专用备份身份拥有并设为仅该身份可访问，不能发布为普通 SMB/NFS/WebDAV 共享；NAS 管理入口启用 MFA/来源限制和审计，完成文件进入 NAS 只读快照或 retention lock。上述措施不能防止 NAS 管理员、设备被盗或系统攻破后读取数据，这是已接受的剩余风险。
- D26 保证的是旧 dump 不会让已删除租户重新上线，不等于申请完成后所有历史备份立即物理擦除：删除前的客户数据仍可存在于 NAS 压缩明文和只读快照中，最长随既定 dump/快照保留窗口自然淘汰。删除确认页必须披露这一点；如果以后要求即时清除所有备份副本，需要改为可按租户销毁的独立备份 artifact/密钥或重写全部相关 full dump，不能宣称当前全库 dump 已做到。
- 平台根密钥及其离线副本不得写入未加密 dump、manifest 或同一 NAS 备份目录；第三方 Secret 在控制库 dump 中仍保持应用层 AES-GCM 密文，但租赁、客户姓名、手机号、地址等普通业务列是可直接读取的明文。发生 NAS 丢失/入侵时按潜在全租户数据事件处理，而不是仅当作备份设备故障。
- NAS 脚本检查远端 exit status、非零大小、manifest 和 checksum 后才把 `.partial` 原子改名并执行保留策略；失败不得删除最近成功副本。每次成功 full dump 加入小时层，保留最近 48 个；每天从成功副本中晋级一个日层代表并保留 30 个，每月再晋级一个月层代表并保留 12 个，同一物理 artifact 可通过标签/硬链接避免无意义复制。备份成功不等于可恢复；D30 不创建定期自动恢复任务，而是提供在隔离 MySQL/全新主机上由维护者按需手工执行的恢复与校验工具。
- D31/D32 的云盘同步完全由 NAS 端既有同步工具负责，源目录只暴露完成态压缩明文 dump、manifest、checksum 和永久 tombstone ledger；不做客户端加密。`.partial`、临时恢复目录、SSH/MySQL credential、云盘 credential 与平台根密钥必须位于同步目录之外。同步删除和云盘版本历史不得误删永久 ledger；dump 的云盘保留至少要覆盖实际声明的恢复窗口，具体 provider/保留仍需在部署清单中记录。
- 云盘同步成功不提升 D29 的对外 RPO 承诺：NAS 本地完成时点、云盘完成时点分别记录，后者只有 NAS 同步工具确认并成功提交匹配 `sync-status-ack` 后才更新；ack 缺失/stale 进入 D49 P2，云盘副本落后或失败不能伪装为最新。手工恢复工具接受 NAS 或云盘 artifact，但两者都必须先验证 manifest/checksum 和最新 tombstone head；云盘凭证由 NAS/维护者持有，不进入应用、云主机、Compose 或控制库。
- Core 初始每小时启动一次 full dump并保持任务互斥；恢复点是 dump 一致性快照的时刻，因此实际数据损失窗口约等于调度间隔 + 未完成/失败窗口，而不是严格的 60 分钟。最新成功恢复点年龄超过 90 分钟即告警小时级目标失守。若 full dump 连续三次超过 20 分钟，或数据库 IO、备份容量和线上 p95 明显恶化，则按变更流程切换为每日 full dump + 每小时归档已启用的 binlog；binlog 链至少覆盖全部 30 个日层恢复点，月层可按 dump 时点恢复。切换前后必须用恢复测试证明小时级恢复能力未退化。

## 17. Delivery Estimate

以下为方案级估算，前提是 2 名后端、1 名前端、测试与运维各部分投入，且现有未完成业务变更已稳定：

| 阶段 | 预计日历时间 | 主要产出 |
|---|---:|---|
| Phase 0 | 1–2 周 | 基线、资源矩阵、迁移演练框架、安全加固 |
| Phase 1–2 | 2–3 周 | control-plane、默认租户注册、数据库路由/provisioning/migration runner |
| Phase 3 | 3–4 周 | 登录/RBAC、全业务 routing session 验证、前端适配 |
| Phase 4 | 2–3 周 | 数据库权限分离、worker、集成凭证、临时面单/PDF 安全处理 |
| SaaS Core 试点与加固 | 2 周 | 隔离/性能/安全测试、灰度与 runbook |
| Commercial SaaS | 2–4 周 | 更细套餐/用量、运营分析与批量工具、选定支付 provider；复用而非替代 Core 最小平台安全控制台 |

SaaS Core 约 10–14 周；加自动支付的完整商业版约 12–18 周。单人串行实施通常需要 4–6 个月。详细排期应在 Phase 0 根据 endpoint 资源矩阵和真实数据量重新估算。

## 18. Risks / Trade-offs

| 风险 | 影响 | 缓解 |
|---|---|---|
| tenant context 或数据库路由错误 | 最高，可能把整个请求送入其他租户库 | 可信 control-plane route + `database_identity` + routing session fail closed + A/B 交错测试 |
| 横切改造与活跃业务变更冲突 | 迁移链/查询反复冲突 | 先处理未完成 OpenSpec，分模块迁移；正常开发冲突及时合并并重跑相关迁移/回滚/隔离测试，不使用 schema freeze |
| 租户数量增长导致连接池膨胀 | MySQL 连接耗尽 | 小连接池 + 有界 LRU engine cache + 空闲 dispose + 容量告警 |
| 前端预检查失败或预览后库存变化 | 网络错误被当成可用，或并发用户造成设备使用期/逻辑附件单元超卖 | 前端 fail closed；最终写事务固定顺序锁设备/request/link/unit 并复验，普通 `USAGE_PERIOD_CONFLICT`/`ACCESSORY_UNIT_UNAVAILABLE` 返回 409；`ACCESSORY_RELAY_CONFIRMATION_REQUIRED`、D34 接力不足例外与 D33 物流警告允许提交但不得显示已满足 |
| 甘特警告与接力候选阈值漂移 | 同一订单对在两个页面给出不同风险结论，或再次出现广东/固定天数判断 | 单一 `ScheduleOverlapPolicy`、同一状态集合和黄金边界测试；前端只展示服务端 reason code/`overlap_days`，不得自行计算 |
| 物流估算仍依赖固定深圳、自由文本误判或调仓后人工遗漏检查 | 多仓设备发货过晚、占用窗口错误，甚至顺丰寄件地址错误 | 建单时服务端按实际设备仓解析结构化 origin、要求客户地址确认并保存估算快照；调仓时集中列出受影响 rental 和编辑入口但按 D21 不自动修改订单，接受由操作者完成复核的业务风险；新运单按新仓解析，既有运单后的调仓强制取消重建并在未知结果时 fail closed，保持两联/账号一致 |
| 仓库与顺丰月结账号错配 | 错误计费、揽收地址不符、跨仓使用其他账号，重试时行为漂移；expired/suspended 越权解绑还会提前释放全局 claim | 服务端 resolver 校验仓库/account binding；解绑 final current-read 要求 released+active、原绑定仓 Admin 和 D48，expired 必须先续期、suspended 必须先恢复且必要时再续期；执行前四方一致性检查；运单账本固定 warehouse/account/integration/binding revision，解绑和 claim 转移都不改写历史快照；secret 掩码与强审计 |
| 月结账号解绑或重新绑定中途崩溃 | claim 假占用、旧仓仍能创建新动作或两个仓库同时 active | binding revision + 控制库唯一索引 + `released/reserved/active` CAS + 可重入 saga/核对任务；新动作发现任一投影不一致即 fail closed，历史动作只认 ledger 快照；不以平台审批或等待旧 operation 代替一致性控制 |
| 页面聚合接口范围过大 | 虽减少请求，却增加单次延迟、内存和传输，任一区块失败拖累全页 | 有界日期范围、服务端筛选、精简 DTO、详情按需、可选 include；用 SQL/字节/延迟预算门禁，避免万能接口 |
| 多个组件争抢刷新责任 | 同一写操作重复读取，旧响应反向覆盖新数据 | 页面唯一 refresh owner、在途请求协调器、sequence 校验和 E2E 请求预算 |
| 多租户数据库 schema 漂移 | 某些租户发布后报错 | fleet migration 状态机、批次升级、N/N-1 兼容、失败租户隔离 |
| provisioning 账号权限过大 | Web 被攻破后可访问/创建所有库 | provisioner 独立部署和凭证；Web/worker 最小权限；数据库路由白名单 |
| 应用与 MySQL 同一云主机 | 宿主机、系统盘、Docker 或误操作故障会同时停止全部租户和任务，无法提供数据库 HA | 明确持久卷、异机 NAS 备份与全新主机恢复演练；监控磁盘/内存；不公开承诺 99.9%；通过 instance key 保留迁往独立/托管 MySQL 的路径 |
| NAS→云盘是异步第二副本 | NAS 误删/勒索可能被同步到云盘；同步延迟、配额、账号失效或版本历史配置错误会让“第二副本”不可用 | D31 只同步已校验完成集合和永久 ledger；NAS 只读快照、云盘版本历史/保留、分别记录 latest-success，并在首次恢复演练中实际从云盘下载校验；应用/云主机不持有云盘凭证 |
| 云盘备份不做客户端静态加密 | 云盘账号、provider 或共享配置失陷会直接暴露全部租户客户资料；压缩、checksum 和透明服务端加密都不能阻止有账号读取权限者查看内容 | D32 明确风险接受；MFA、专用私有目录、禁公开/普通分享链接、最小同步账号、版本历史和访问审计；根密钥始终排除在外，事件按潜在全租户数据泄露处理 |
| 灾备演练仅按需手工执行 | runbook、镜像、凭证或备份格式可能在长期未演练时漂移，4 小时内部参考值可能长期无法达到 | D30 明确接受无固定周期；交付版本锁定脚本、检查清单和结果模板，界面/文档展示最后一次手工结果但不自动触发；安全/数据门禁失败必须修复，耗时超过参考值记录改进项，二者都不能被包装成客户 SLA |
| 旧快照回退安全状态，或人工 recovery review 误放行 | 备份后才发生的租户暂停、会话撤销、码消费、邀请/授权失效可能丢失；没有异机安全账本时平台管理员也无法仅凭旧 dump 证明故障前最终状态，误判会重新开放本应关闭的租户或 provider 能力 | D58 全 survivor 默认 hold、旧 session/授权失效、非终态码不可逆作废、任务隔离和单租户近期 MFA 审核；页面突出不确定窗口并要求外部运营/安全记录，审计或版本/DML 收口失败保持 held。任何时间点都不自动 release；无法证明安全的 tenant 标记 kept_closed。D59 允许主机恢复事件在一个经审核 active survivor smoke，或在无安全可 release 候选时由已销毁且留有摘要证明的 DR-only scratch smoke 后收口，但其余 held tenant 仍不可访问；明确接受人工证据可能不完整、替代码/重新邀请和后续逐租户审核的运营成本 |
| NAS dump 不做静态加密 | NAS 设备被盗、管理员账号或系统失陷时，攻击者可直接读取全部租户客户资料；压缩和 checksum 不提供保密性 | D24 明确风险接受；目录 0700、禁普通 SMB/NFS/WebDAV、管理 MFA/来源限制、快照与访问审计；事件按潜在全租户数据泄露处理，并在外部付费上线前重新做隐私/合规复核 |
| 到期租户数据永久保留 | 已流失租户持续占用在线磁盘、备份容量和迁移时间，客户姓名/手机号/地址等数据的暴露窗口无限延长 | D25 明确风险接受；expired 租户业务访问 fail closed，但仍纳入容量预算、备份、恢复和 migration；按租户统计体积并设置容量告警，定期做隐私/合规复核；Admin 主动删除仅按 D26 受控流程例外执行 |
| 主动删除部分完成或旧备份复活租户 | tenant schema 已删除但控制记录/账号残留，或恢复删除前快照后重新开放已删除数据 | D26 持久状态机、全局 deletion/backup/migration lease、先离站确认永久 tombstone 再 drop、执行后负向核对；恢复先应用最新独立 ledger 且缺失时 fail closed，UUID 永不复用 |
| 平台根密钥泄露 | 攻击者可派生全部租户数据库密码，并解密取得的第三方凭证/兑换码密文，故单根方案的泄露半径较大 | 仓库外只读 Secret、固定 UID/GID、最小挂载服务、磁盘/主机加固；泄露时用新根版本逐租户轮换实际 MySQL 账号并重加密全部外部 Secret，第三方凭证在 provider 侧同步撤销；可能暴露的未兑换码撤销并重新发行 |
| 根密钥丢失或历史备份缺少对应版本 | 应用无法重新派生租户 DML/平台只读账号密码，也无法解密控制库中的第三方凭证、完整兑换码和平台 TOTP seed | 同一逻辑根密钥至少两份异地离线加密副本、恢复演练和备份 manifest；极端情况下用 provisioner 生成新根并批量重置两类数据库账号，业务表数据仍可恢复，但外部凭证需重新录入、平台 TOTP 需用恢复码或 CLI 重新绑定 |
| 旧凭证已进入 Git、镜像或日志 | 新加密上线后旧 secret 仍可被利用；内网、固定寄件地址或本地日志权限只能降低部分可利用性，不能撤销远端历史中的值 | 仍具权威的凭证原则上轮换；D61 用户只确认接受必须有期限，当前 policy v1 以 30×24 小时为保守默认值/单次上限，每次显式复核、可更短且不自动续期，并最迟首次生产规模演练开始即失效；网络/provider 限制、异常监控、扫描、非复用和到期撤销仍执行。其他凭证、触发器命中或漏复核仍立即轮换；随后清理当前副本、历史、日志和产物 |
| 腾讯云企业资质、签名、模板或运营商报备未及时通过 | 生产手机号登录、注册和删除复验全部不可用 | Phase 0 提前申请并记录状态；审核及真实号码 smoke 是普通准备/测试任务，失败时修复或等待外部状态后重试，不设置 hard release gate，也不以 fake 或固定码绕过运行时 fail-closed |
| 短信轰炸、供应商限流或腾讯云短信故障 | 产生费用、骚扰用户或使无密码登录不可用 | MySQL 多维限流、用途隔离、错误次数锁定、腾讯云日限额/防盗刷监控/告警联系人；发送失败统一提示并保留审计，Core 不静默切换未批准 provider |
