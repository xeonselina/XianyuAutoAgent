# Change: 将库存管理系统升级为多租户 SaaS

> 状态：**讨论草案，尚未批准**。文中的架构与产品方案均为候选建议；所有关键决策必须与项目负责人逐项讨论并记录确认后，才能转为实施规格。

## Why

当前系统面向单一公司的可信内网运行：内部 API 没有用户登录与权限控制，所有业务表共享同一数据空间，顺丰、闲鱼、快麦和 OCR 等凭证由全局环境变量提供，定时任务也按全局数据集执行。该模型无法安全地让多家公司共用同一套部署，更无法提供成员管理、套餐额度、订阅生命周期和平台运维能力。

本变更将现有系统演进为可商业化运营的多租户 SaaS，同时保留设备、租赁、甘特图、发货、验货、统计和接力管理等现有业务能力。

## What Changes

- 新增租户、手机号验证码用户、成员关系、邀请、MySQL 服务端逐设备会话和角色权限模型；浏览器 HttpOnly Cookie 只保存不透明随机会话 token，不保存用户、租户或权限信息，并支持当前设备注销、指定设备撤销和全部设备注销。成员邀请由 Admin 复制单次链接并通过微信等已有渠道发送，腾讯云不发送邀请通知，接受者仍须验证链接绑定手机号。同一手机号可以同时收到不同租户的待接受邀请，但任一注册或邀请首次建立有效 membership 时，必须在同一控制库事务中使该手机号的其他 pending 邀请全部失效并释放席位
- SaaS Core 的租户账号、注册、登录、成员邀请、换号和安全短信复验只接受中国大陆 `+86` 手机号；数据库继续按 E.164 保存规范值，页面固定 `+86` 而不展示国际区号选择，国际身份和短信路由留到后续。该限制只适用于登录身份，不自动限制客户收货电话、仓库联系电话或顺丰业务电话
- 租户账号继续使用手机号验证码无密码登录，不新增租户 Admin 密码或长期 TOTP。第三方集成凭证及顺丰绑定变更、授予/移除 Admin 和租户删除等 Admin 高危操作，必须向当前操作者自己的手机号发送与具体动作及请求内容绑定的短信验证码；任一有效成员更换本人手机号则使用自己的旧号与新号验证码。验证码单次消费且不能形成可复用的“近期已验证”窗口；换号的两码、删除申请/撤销各自的专用码已经满足该动作，不再额外叠加第三个验证码。普通库存、租赁、发货、打印、验货和调仓不要求重复验证
- D57 已确认 Core 不提供“无法接收旧手机号”时的平台人工恢复、代改手机号、代输验证码或 impersonation 入口。若租户仍有另一名 active Admin，该 Admin 可按既有成员权限移除丢号成员，再向新号码创建一条全新邀请；移除 Admin 以及把新邀请授予 Admin 仍分别遵循 D48，流程不会原地改写旧 user/membership 的手机号或自动复制角色。最后一名 active Admin 丢失旧号时没有平台或其他身份旁路，只能先通过运营商等租户系统之外的方式恢复旧手机号；未来若要支持其他找回方式，必须另立产品与安全决策
- 新增兑换码注册与续期：平台后台可生成兑换码并在生成成功时一次性下载批量 CSV，也可撤销、逐码重复查看和审计；Core 不支持历史批次再次导出全部完整码。每次有效兑换只作用于一个租户及一段服务有效期；整机灾备从旧快照恢复出的 active/reserved 码一律进入不可再次兑换的恢复作废终态，需要时生成全新替代码，不能把旧快照状态人工改回可用
- D56 已确认过期/暂停租户不获得顺丰账号解绑例外：服务期到期后，所有有效成员都可完成手机号登录但统一进入同一过期续费提示页；Operator 只可查看提示和注销，Admin 仅额外保留既有兑换码续期提交，账号安全、顺丰解绑、集成管理及全部其他业务/设置入口均拒绝。suspended 租户继续使用既有暂停说明/账号安全 allowlist，但不开放顺丰解绑，必须由平台先完成 D52 恢复；若恢复后 subscription 已过期，再进入上述过期闭环。该状态门禁不修改任何历史 shipment 保存的仓库、account、binding、credential 或寄件资料快照
- 开户失败不会让已预留兑换码重新流通：该码持续绑定完成短信验证的原用户和原 registration attempt，只有原用户重新完成同手机号 `register` OTP 后才能自助重试同一 attempt；平台没有开户 retry、abandon 或 cleanup UI。平台唯一处置是受审计地“补发兑换码”：同一控制库事务与 registration final commit 竞争并二选一，先把原 attempt 永久 fence 为 `superseded_by_replacement`、推进 provisioning generation、失效旧 worker lease、把旧码永久置为 `revoked(reason=replaced)`，再立即创建唯一新码。新码复制 source code 的不可变 entitlement snapshot、plan revision 和精确 service duration，只由平台选择一个晚于数据库当前时间的新截止日，并使用新 UUID、crypto context 和随机明文；它是普通 bearer，可用于注册或续期且不绑定原手机号。旧 provisional 数据库、账号、路由和任务只由 system-only outbox/janitor 异步清理，失败告警但绝不复活旧码、阻塞新码或发布旧 attempt；provisional tenant 不提前占用对外 name/slug，immutable tenant/database UUID 不因补发或清理而删除
- 平台管理员使用独立全局账号、密码、TOTP 验证器和一次性恢复码登录，与租户手机号账号及会话完全隔离。平台管理员可以选择任一租户并只读其业务数据，但不能修改租户业务、执行发货/打印等动作或 impersonate；兑换码、租户状态、D53 服务期调整和删除复核等控制面写操作继续使用独立平台权限与审计。所有 active 平台管理员可单人调整服务期，但每个新动作必须重新验证 TOTP 或消费一枚恢复码，不复用登录或其他操作留下的近期 MFA，也不建设双人审批
- Core 监控采用三层轻量方案：腾讯云 CVM 基础监控、从云主机外发起的腾讯云 HTTPS 云拨测，以及 MySQL/Web/worker、任务、备份和短信/SF 等 provider 的少量应用健康状态与自定义消息告警。Core 不部署 Managed Prometheus、Grafana、通用 metrics scraper 或完整 tracing backend
- 为每个租户创建独立业务数据库和只能访问本租户 schema 的独立数据库账号；首期数据库共享同一个 MySQL 实例，并通过可信数据库路由、数据库权限、缓存、任务和日志实施隔离
- 为桌面端和移动端新增手机号验证码注册/登录、成员管理、权限控制和租户设置界面；一个手机号账号只归属一个租户
- 新租户注册后自动创建待完善的默认仓库，首位 Admin 首次登录必须补齐并确认联系人、电话和完整地址，完成前后端均禁止进入业务功能
- D55 已确认 SaaS Core 完全不提供 tenant API key 或其他机器身份入口：移除/禁用现有 `/external-api` 与单个全局 `X-API-Key`，不建设 key 的生成、查看、轮换、scope、有效期、撤销或恢复能力；租户业务 API 只接受有效的服务端用户会话和 membership 权限。未来若需要外部 API，必须在 Core 之后重新决定认证、授权、数据模型、迁移和安全边界，不能启用或复用 Core 中的潜在代码路径
- 将顺丰、闲鱼和快麦配置从进程环境变量迁移为按租户加密保存的集成配置；顺丰进一步支持每仓绑定独立月结账号，并由设备实际仓自动路由 API connection、月结号和寄件资料；短信由平台统一通过腾讯云提供，所有租户共享平台运营主体签名且不随租户品牌变化
- 租户 Secret 体系只使用一把仓库外、版本化的平台根密钥：租户数据库密码结合 tenant/database UUID 和密码代数通过 HKDF-SHA256 确定性派生，控制库不保存密码；顺丰/闲鱼/快麦凭证和可重复查看的兑换码使用同一根密钥按用途及记录派生独立子密钥，再以 AES-256-GCM 直接认证加密，不引入逐条 DEK 或两层信封加密
- 移除身份证 OCR、租赁合同及独立的单张/批量发货单业务页面；保留顺丰下单、物流查询、批量发货和快麦打印，并把打印流程明确拆为“顺丰 API 第一联 + 本地生成的寄回信息第二联”
- 新增租户显示信息设置，Admin 可配置系统显示名称、公司全称和联系方式，消除“光影租界”等公司信息硬编码；Core 不提供公司 Logo 上传
- 新增多仓库库存模型：每个租户必须有一个默认仓库，设备记录所在仓库；预约档期可指定优先仓库并允许从其他仓选择主设备，但同一订单的库存附件必须与主设备同仓；每个订单提供会打印到第二联、但不会传给顺丰的客户可见备注
- 新建租赁的物流时效必须按“最终选中主设备当前仓库的结构化地址 → 客户结构化收货地址”估算；优先仓只提供选设备前的预览，不能继续把广东深圳或任一公司地址写死为全部租户、全部仓库的发货起点
- rental 建立后设备再调仓时，只列出受影响订单并提示操作者自行检查；系统不得自动修改已有物流天数、计划寄出/回仓日期、物流窗口或估算快照，也不自动重算甘特警告/接力候选或增加“物流待确认”门禁。尚未创建运单的顺丰动作按设备新仓执行；已经创建运单后再调仓时，必须阻断打印/实发，提示用户显式取消旧运单并按设备新仓重建
- 每个仓库可以绑定独立顺丰月结账号，同一个规范化月结账号在全平台不得同时绑定多个仓库，无论仓库属于同一租户还是不同租户。控制库使用平台根密钥按独立用途派生的 keyed fingerprint 维护当前绑定的全局唯一声明，不能通过随机密文或重复建档绕过；租户侧冲突提示不得泄露账号被哪个租户或仓库使用。原仓 Admin 主动解绑后释放当前绑定，历史运单保持原 account/binding/仓库快照且不占用当前绑定名额；同租户或不同租户的新仓必须重新提交并验证账号，不增加未完成任务检查或平台人工审批。租户默认共享一组顺丰 API 接入凭证，特殊月结账号可以显式引用独立凭证。时效查询和创建新运单使用主设备当时实际仓库的绑定，创建后保存仓库/account/binding 快照；完整月结号及 API secret 加密保存，客户端不能为单笔订单跨仓选择账号。后续历史运单操作使用创建快照；设备在实际发货前换仓时，旧运单必须显式取消并按新仓重建
- 顺丰账号不是仓库启用的必填项：未绑定仓库仍可管理库存和建单，物流时效改为人工确认；实际使用顺丰下单、批量顺丰动作或第一联时明确提示绑定。Admin 可直接跳转对应仓库设置，Operator 获得联系 Admin 提示，二者均可跳转站内顺丰配置指引
- 每个仓库最多绑定一台快麦面单打印机，操作者只选仓库；第一联由顺丰接口生成且不传寄回地址，第二联本地生成寄回信息，两联必须使用一致的仓库/打印机执行上下文。没有既有运单时取主设备最新仓库；运单创建后设备又调仓时，旧运单取消完成前禁止继续打印或实发，随后按新仓重新创建两联上下文。验货仓库决定主设备入库位置；随设备实际验收到的逻辑附件单元也自动归入验货仓，未收到或无法对应的附件不得恢复可用
- Core 不建设正式调拨单；Admin 和 Operator 可即时改变设备仓库，系统原子记录移动历史并重新分配尚未发货订单的逻辑附件单元关联，提交前预览受影响订单
- 新增可配置附件目录：每台主设备可配置可选附件；手柄/镜头支架按设备配套，手机支架/三脚架按每份容量创建仅系统内部可见的逻辑库存单元。用户仍只勾选附件类型、不选择单元编号；总量、可用和在外数量均由逻辑单元及订单关联实时聚合。需求只表达客户勾选了什么，一张无角色/状态的关联表只表达哪个单元计划或实际经过哪张 rental。主设备调仓时重新分配未来关联，目标仓没有可用单元则动态显示附件不足并执行已确认的发货门禁或接力例外
- 将 Web 进程内 APScheduler 迁移为 MySQL 持久化任务表 + 单个独立后台进程，所有任务显式携带 `tenant_id` 和幂等键
- 重构高扇出页面 API：预约建单把逐设备 `check-conflict` 合并为一次实时可用性查询，甘特图把逐日 `daily-stats` 与主视图合并为范围聚合，并消除写后重复刷新、编辑页重复初始化、深层列表 DTO 和其他 N+1 HTTP/SQL；库存、仓位、附件数量和统计不使用浏览器持久缓存或跨请求业务数据缓存，仍以租户数据库实时查询和最终写入事务复核为准
- 保留甘特档期冲突提示，并与接力候选共用服务端规则：同一主设备客户使用期重叠是阻断建单的硬冲突；使用期不重叠时，物流窗口重叠不阻断建单，`overlap_days = 前单计划回仓日 - 后单计划寄出日`。只有 `> 1` 天才同时显示甘特警告、进入接力候选，`<= 1` 天两处都不提示；两种情况都允许提交。删除前端广东/深圳和固定天数判断
- 闲鱼告警改为后台按租户每 3 分钟同步，页面只读取租户库摘要并展示最后成功时间；用户显式刷新时创建可去重的即时同步任务，多个在线账号或标签页不再各自每 60 秒调用闲鱼
- 新增 Core 单一套餐、订阅状态、功能开关和 10 席额度校验；支付渠道通过 provider adapter 接入
- SaaS Core 每个租户的有效成员与未过期待接受邀请合计最多 10 个；邀请默认 7 天有效，创建时只预占发送租户自己的席位、接受时原子转正、撤销/过期/因同手机号已加入其他租户而失效时立即释放，重新生成会轮换旧链接并重新计时；不限制同一账号的登录设备数，也不对设备数、月 rental 数、API 调用量或集成账号数设置套餐硬额度
- 新增平台管理、租户暂停/恢复、服务期人工增减、灾备逐租户放行、审计、可观测性、备份恢复、数据导出与删除流程。平台暂停作为安全/违规应急冻结：近期完成第二因子验证的平台管理员填写原因并确认后，立即拒绝租户业务访问、既有 session、新任务和新第三方副作用；Admin 仅保留暂停说明与账号安全入口，Operator 仅可查看暂停说明，顺丰解绑没有例外且必须由平台先恢复租户。暂停动作本身不改变服务期且暂停期间不能兑换续期；恢复时按实时到期时间进入 active/expired，旧发货、打印等任务不得盲目补跑。平台双向调整服务期是独立、受审计的异常处理动作，只接受增加/减少整数天或独立“立即到期”，不允许直接编辑任意到期日期；所有 active 平台管理员均可单人执行，但每个新动作必须重新验证 TOTP 或消费一枚恢复码。目标可为 active、expired 或冻结已完成的 suspended 租户；暂停中只改服务期且绝不解除暂停，过渡态、灾备 hold 和删除流程均拒绝。退款场景只记录原因、备注和可选线下参考号，不保存金额或支付状态，也不执行退款
- 提供现有单租户数据到“默认租户”的可核对迁移路径；维护窗口内、重新开放新版业务写入前可回滚旧应用，开放后只回到兼容新结构的 tenant-aware 版本或 forward-fix
- **BREAKING**：生产环境租户业务 API 将要求登录、有效租户成员关系和对应权限；独立的平台只读 API 要求平台管理员会话，既不要求也绝不能为平台管理员创建 tenant membership
- **BREAKING**：应用从单一固定数据库连接改为“控制库 + 租户数据库路由”；现有 `/external-api` 与全局 `X-API-Key` 在 Core 中移除/禁用，第三方集成配置改为租户范围的数据结构

## Recommended Delivery Scope

建议分两次可发布成果交付，避免把数据隔离与商业计费一次性大爆炸上线：

1. **SaaS Core（已确认先行）**：租户隔离、兑换码注册/续期、登录、基础 RBAC、成员管理、租户显示信息、多仓库库存与仓库回寄地址、可配置附件及逻辑单元自动分配、租户级第三方配置、独立任务进程、默认租户迁移、审计与隔离测试，以及支撑兑换码生成/补发、注册故障审计、租户冻结/恢复、服务期人工调整和删除复核所必需的最小平台安全控制台；开户失败只允许原用户自助重试，不提供平台代重试或放弃清理界面。不包含 OCR、合同和独立发货单页面，也不新增 Logo 上传或通用文件存储系统。
2. **Commercial SaaS（在 Core 稳定后）**：更细套餐额度、试用/订阅状态、支付 provider、账单、运营分析与批量营销工具、租户自助导出，以及建立在 D49 三层基线之上的更完整告警/SLO。它扩展 Core 最小平台控制台，而不是把 Core 必需的兑换码和安全运维能力推迟。

支付渠道不阻塞 SaaS Core。首发正常开通或续期使用平台生成的兑换码；平台可在补偿、退费或纠错场景受审计地增加或减少服务期，但退款只保存原因、受限备注和可选线下参考号，不保存金额/币种/支付状态，也不自动计算、执行或证明资金退款。待目标市场和收款主体确认后，再讨论 Stripe、微信/支付宝或合同制账单。

腾讯云企业实名认证、短信实名资质、平台统一签名、验证码模板和运营商报备，以及受控真实号码端到端验证，是 Core 生产注册、登录和安全复验的发布硬门禁。开发和自动测试可使用仅限非生产的 provider fake，但生产不能用固定验证码、接口回显或 fake 绕过短信未就绪状态。

验证码采用 6 位数字、5 分钟有效、60 秒冷却和单 challenge 最多 5 次错误；每手机号跨用途最多 5 次/小时、10 次/上海自然日，每可信来源 IP 最多 30 次/小时、200 次/上海自然日。应用使用 MySQL 原子计数，腾讯云控制台同步相同上限；无需引入 Redis。

## Impact

- Affected specs: `tenant-isolation`、`identity-access`、`subscription-entitlements`、`tenant-integrations`、`saas-operations`（均新增）
- Affected backend: `app/__init__.py`、全部模型、路由、handler、service、scheduler、库存/仓库/附件数量/顺丰下单/两联打印、现有外部 API 移除、配置与数据库迁移；删除 OCR、合同及独立发货单页面服务，重构现有热敏发货单服务为面单第二联服务
- Affected frontend: `frontend`、`frontend-mobile` 的路由、API client、导航、权限展示、登录/成员/租户设置/仓库/设备附件配置/库存/订阅页面；删除合同和独立发货单视图，重做租赁附件选择及批量两联打印；移除逐设备/逐日请求扇出和甘特统计本地缓存
- Affected infrastructure: Core 暂时在同一台云主机的 Docker Compose 中运行应用、worker 和共享 MySQL 实例；家庭 NAS 每小时通过受限 SSH 主动拉取一致性 full dump，分层保留 48 个小时、30 个每日和 12 个每月副本，再由 NAS 既有能力把已校验完成的备份集合和永久 tombstone ledger 自动同步到云盘作为第二异机副本。应用/云主机不接入云盘或保存其凭证。另含 MySQL 独立租户账号与索引/连接预算、持久卷、恢复演练、Nginx keep-alive/压缩、Docker Compose Secret、短信、密钥，以及腾讯云 CVM Agent、云拨测和轻量自定义消息告警；不引入 Redis、业务对象存储、托管 MySQL 或 Managed Prometheus
- Data migration: 现有业务数据库直接注册为第一个默认租户数据库，不对每张业务表回填 `tenant_id`；全局第三方配置转换为该租户的集成记录。首次切换提前 24 小时通知并预留 2 小时维护窗口，目标停写不超过 30 分钟，满 60 分钟仍未通过验证则回滚旧应用
- Compatibility: 现有业务 URL 可在过渡期保留；通过服务端活动租户上下文实现租户化，不要求前端把任意 `tenant_id` 作为可信参数传入

## Success Criteria

- 任意租户成员无法读取、修改、导出、打印、搜索或推断其他租户的数据，包括通过对象 ID 猜测、批量接口、文件 URL、任务和缓存侧信道
- 租户 A 的真实 MySQL 账号在绕过应用直接连接时也无法读取或修改租户 B schema；Web/worker 不持有建库、授权或跨 schema 权限
- 平台根密钥、派生子密钥、派生数据库密码和完整 DSN 不进入 Git、镜像、环境变量值、日志、API、控制库、审计或平台页面；系统只有一个逻辑平台根密钥系列且任一时刻只有一个活动版本，日常只需备份该版本，根密钥换代后仍被历史备份引用的旧版本需离线保留到引用过期；相同版本上下文可稳定重新派生，外部 Secret 可认证解密，单租户密码代数和平台根版本均能按 runbook 轮换和恢复
- 所有业务写入均记录租户、操作者和请求追踪信息；所有平台租户业务读取（含失败或拒绝）以及高风险平台操作均有不可由租户修改的审计记录，平台审计不可写入时对应读取或操作 fail closed
- 现有单租户数据迁移前后按表行数、关键金额、设备/订单关联和抽样校验一致；维护窗口内、尚未重新开放新版业务写入时可以回滚旧应用。新版开始写入多仓库、逻辑附件单元/需求/事件或新租户数据后，只允许回到 tenant-aware 版本或 forward-fix，不承诺旧版无损回滚
- Web 实例可水平扩容，定时任务不会因多 worker 重复执行；可证明未提交或第三方明确失败的任务可以幂等重试。第三方已接收但结果未知的物理打印不得自动重试，应进入人工核对，避免把“无法确认”错误承诺成“绝不重复打印”
- 重建 MySQL 容器不会丢失数据；整台云主机永久损坏时，可仅凭异机数据库备份、备份 manifest 和对应离线根密钥版本在全新主机恢复控制库与全部租户库。Docker volume、同机目录或同机快照不被算作唯一备份
- NAS 备份连接由家庭侧主动发起，家庭网络无需开放入站端口；云主机为 NAS key 提供的身份只能调用固定备份 wrapper，不能获得通用 shell、Docker root 或应用根密钥。备份按确认不做静态加密，以压缩明文存放在不可对普通 SMB/NFS/WebDAV 开放的专用目录，并使用 checksum、只读快照、访问控制和脱离原云主机的恢复演练；明确接受 NAS 失陷后客户数据可读的风险
- NAS 只把已完成原子改名并通过 checksum/manifest 校验的 dump 集合和永久 tombstone ledger 同步到既有云盘；不同步 `.partial`、临时文件或平台根密钥。云盘凭证只存在于 NAS，应用和云主机无权访问；从云盘下载后仍必须执行相同校验和防复活流程
- 云盘同步不增加客户端静态加密：压缩明文 artifact 原样上传，依靠云盘 MFA、专用私有目录、禁止分享链接、最小同步账号和版本历史降低风险；明确接受云盘账号/provider 失陷后全部租户客户资料可被直接读取，透明服务端加密不被视为抵御账号读取权限的边界
- 数据库提供小时级恢复点，标称 RPO 约 1 小时；实际最坏值还包含 dump 耗时和失败窗口，不在 Core 单机阶段承诺严格 60 分钟上限。若小时 full dump 连续三次超过 20 分钟或明显影响线上 IO/延迟，则切换为每日 full dump 加小时级 binlog 归档，并通过恢复测试保证小时级能力不退化
- 上述数据 RPO 不自动代表安全控制也可以回退。D58 已确认不新增异机单调安全账本，任何受支持的生产旧恢复点导入都必须经过唯一 restore wrapper：整机或同机 control/full restore 创建新的 recovery run 并轮换宿主机 marker generation；单 tenant schema restore 则先在当前 run 下为该 tenant 安装 hold、锁定 DML 并隔离 job/provider，再从 staging 导入核对。最新 tombstone ledger 过滤完成后，受影响租户先进入正交 recovery hold；旧租户/平台会话、短信 challenge、邀请、敏感动作授权和未终结注册流程全部失效或隔离。D55 使 Core 不存在 tenant API-key 表、Secret 或认证路径；旧快照中的遗留全局 `X-API-Key` 配置不得导入为可用凭证，`/external-api` 在恢复前后都保持移除/禁用。active/reserved 兑换码进入不可逆恢复作废终态。只有使用新密码/TOTP 恢复的平台管理员，才能带近期第二因子、原因和版本校验逐租户审核；release 不复活兑换码、旧任务或第三方副作用，也不覆盖到期、暂停和删除门禁。拥有生产 root 的 DBA 绕过 wrapper 直接导入无法由应用完全阻止，属于明确禁止并审计的剩余运维风险
- 整台云主机永久损坏时，从站外 serving 云拨测首次达到“实际探测失败 quorum”的 P1 事件 UTC 时间开始记录恢复耗时，并以 4 小时作为初期内部演练参考目标；它不是客户 SLA、赔偿承诺或发布硬门槛。新主机完成最新 tombstone、全量 recovery hold/安全资源覆盖和平台管理员恢复，并至少让一个经审核可安全 release 的 active 租户通过路由、库存/rental 与外部副作用隔离 smoke 后，recovery run 才达到内部安全完成状态；若没有可安全放行的 active survivor，则由恢复 CLI 创建不属于任何租户、无 membership/兑换码/provider Secret、禁止外部调用的临时 scratch schema/account，完成等价的隔离和最小 CRUD smoke 后销毁。只有故障域外 `/health/external` 随后成功命中新 origin，才记为主机恢复完成并停止本次内部耗时记录。其余租户继续 held，随后逐个审核，既不阻止主机恢复事件收口，也绝不会因到时自动放行。恢复期间 worker 和第三方写操作默认关闭，运单/打印等快照之后的外部副作用先按幂等 ID 对账或隔离，禁止从旧数据库快照盲目重放
- 正式对外开放前必须手工完成一次脱离原云主机的全新主机恢复，证明安全覆盖、至少一个安全租户或临时 scratch 核心 smoke、旧副作用隔离，以及故障域外 `/health/external` 确实命中新 origin 均可执行；同时记录总耗时及各阶段时间。超过 4 小时形成内部改进项，但只要安全与数据门禁通过便不单独阻止 Core 上线。此后不设置自动恢复任务或固定演练周期，只保留版本锁定的手工命令、runbook、检查清单和结果记录，由项目负责人按需执行
- Core 单机阶段对外按 best-effort 提供服务，套餐、页面、合同和宣传不承诺 99.9% 等数值可用性 SLA，也不设置停机赔偿；内部监控、小时级恢复点与整机恢复目标不作为客户 SLA，可预见的计划维护提前通知租户
- 兑换码服务期到期只关闭业务访问，不自动删除租户数据库或历史记录；到期租户永久保留并继续纳入备份、恢复与 schema migration，任意时间续期后使用原租户身份恢复全部数据。明确接受长期存储、备份增长和客户信息暴露窗口延长的代价；只有 Admin 主动申请才能进入受控删除例外流程
- 平台暂停从首个 deny-all 事务起阻止新的租户业务写入和第三方提交；暂停前已越过持久 provider 提交边界的操作只允许查询/对账，不得自动重试。暂停期间不改变 subscription 到期时间或消费兑换码，恢复后用户重新登录，只有仍满足当前时效和幂等前提的安全任务可以恢复
- 租户 Admin 主动删除不是即时按钮：新短信复验、平台人工复核和 30 天冷静期全部完成后，才删除在线 tenant schema 与 tenant-owned 数据；审核通过时立即冻结 Operator、业务 API、既有 session、定时任务和第三方动作，Admin 只能撤销/查看倒计时/管理账号安全。撤销按当时订阅状态恢复且不补服务天数；永久只追加 tombstone 不含业务内容。删除前旧备份按既定 12 个月窗口自然淘汰，但任何恢复都必须先应用 NAS 上独立的最新 tombstone ledger，禁止旧 dump 复活已删除租户
- 删除完成前原租户全部成员手机号继续被占用；完成后删除 tenant-only 用户身份并释放手机号，可凭新兑换码注册或接受新邀请。新注册必须生成全新的 user、tenant 和 database UUID，不能通过相同手机号连接旧租户；独立平台管理员身份不随租户删除
- 预约页面一次已稳定的日期/型号/仓库变更最多触发一次实时可用性请求，不再按设备或附件数量增加 HTTP/SQL 查询；甘特图一次范围加载不再逐日请求，核心 SQL 数量不随展示天数或设备数线性增长
- 创建/编辑订单不能依赖前端冲突检查作为正确性边界：可用性请求失败不得按可用处理，最终写事务必须重新查询、锁定并复验。客户使用期和普通订单的可用逻辑附件单元属于硬约束；接力候选可保存“有需求、暂无单元关联”并提示等待确认，已确认的接力补寄例外只显示不足并保留内部备注，二者都不能伪装成已备足。物流重叠属于允许提交的警告。任一甘特相关写操作成功后最多再发起一次当前窗口刷新，不能由 store、页面和 watcher 重复读取
- 库存敏感接口返回 `Cache-Control: no-store`，浏览器 localStorage/IndexedDB、Service Worker 和服务端跨请求缓存均不得作为库存、仓位、附件数量、硬冲突、物流警告或甘特统计的事实来源；创建/编辑订单必须在最终事务中重新校验并锁定硬约束资源
- 每个主设备始终具有有效仓库归属；预约优先仓只影响自动选货排序。逻辑附件单元离仓后随主设备流转：接力 `agreed` 只建立下一张 rental 的无状态关联，实际交接时才追加交接事件并更新当前持有订单；中间订单未勾选时不创建虚假需求或特殊状态，界面根据“本单有关联 + 本单无需求”动态提示继续保管/转寄。在外单元不能被当作当前可用或再次发给另一设备，但可以为预计回仓后的不重叠未来订单建立 link；每次实际发货前必须复验它已经真实回仓，或属于同一主设备已同意接力。验货入库和人工调仓均可追溯
- 物流时效估算的起点由服务端从最终选中主设备的当前仓库解析，客户端不能伪造起点；跨仓选择后估算结果随实际设备仓切换，最终创建事务再次核对仓库与估算上下文，系统中不得存在默认广东深圳起点
- 同一租户的不同仓库可以使用不同顺丰月结账号，但同一个规范化月结账号在全平台只能被一个仓库占用；同租户或跨租户的顺序、并发重复绑定都只能一个成功，且失败响应不能泄露现有归属。下单时仓库、月结账号、寄件资料和打印机解析结果一致，仓库未绑定有效账号时顺丰动作明确失败且不得回退到全局、默认仓或其他仓账号；历史运单保留创建时的账号/仓库掩码快照并继续使用原账号上下文
- 面单第一联来自顺丰 API，第二联使用同次打印 job 选定仓库的寄回资料并记录快照，两联发送到同一仓绑定的打印机；尚无既有运单时该仓为主设备最新仓，已有运单后设备换仓则必须取消旧运单并按新仓重建，禁止混用旧仓第一联与新仓第二联
- 手机支架和三脚架每份库存容量对应一个仅系统内部可见的逻辑单元；该 ID 是可替代库存的记账 token，不是现实附件序列号，用户不查看、选择或扫码。前单携带的单元继续随同一主设备跨多单流转；接力同意后，即使后单未勾选也为后单建立一条无角色、无状态的单元关联，因此可可靠覆盖多段接力，而界面仍只动态提示“随设备带来”，不保存 `carryover_only`。后单勾选且接力仍是候选时只动态提示“等待接力确认”，不保存 `relay_dependent`。后一单需要但设备未携带时，系统尝试自动关联另一个可用单元；没有单元则由“存在需求但没有单元关联”动态显示不足并允许填写内部备注，不保存 `supplemental_dispatch`。该例外不阻止接力状态，Core 不新增第二正式运单、自动下单、打印或跟踪流程
- 同一设备客户使用期重叠时禁止创建；使用期不重叠但相邻订单 `overlap_days > 1` 时允许创建，甘特提示与接力候选必须同时出现且数值一致，`<= 1` 时二者都不出现
- Core 的 10 席额度和订阅状态由服务端统一执行，绕过前端不能创建第 11 个占用；设备、rental、普通 API 调用和集成账号不得因未定义的套餐计数被拒绝。防刷限流、请求大小、分页、连接池和 provider 固有限制仍作为安全/容量保护执行，但错误语义不能伪装成“套餐额度已用尽”
- 关键租户隔离、数据库路由、RBAC、订阅状态和迁移测试进入 CI；租户数据库 schema 漂移或不可信数据库选择在合并/发布前被发现
- 平台管理员密码使用抗暴力哈希，TOTP seed 加密保存并拒绝同一时间步重放，恢复码按代数只保存单次使用的不可逆摘要且仅能替代 TOTP；正常 Web/worker/MySQL 容器或同机服务重启不得清空 TOTP、重放游标、恢复码状态或平台服务端会话。平台会话不能被租户 Cookie/API 接受。平台跨租户业务读取必须经显式租户选择和 SELECT-only 数据库账号，任意 HTTP/ORM/原生 SQL 绕过尝试均不能写 tenant schema；每次业务读取和完整 PII 查看均进入平台审计，平台响应禁止浏览器持久缓存
- 租户浏览器会话只在控制库保存 token 摘要、用户、期限、设备摘要和撤销状态，Cookie 中的原始随机 token 不进入日志、URL、本地存储或数据库明文。注销当前/指定设备必须在服务端立即撤销对应行，注销全部设备、手机号变更或安全事件必须使全部旧会话失效；从旧备份灾备恢复时不得复活历史会话
- 从旧恢复点执行整机、同机 control/full 或单 tenant schema 恢复时，必须在任何受影响租户业务路由可用前完成对应 recovery coverage 核对；缺少 hold、恢复事件不匹配、初始化中断或覆盖摘要不一致时受影响范围 fail closed。平台管理员只能单租户审核，审计或数据库账号收口任一步失败都保持 held；D55 已移除的外部 key/认证路径不得因旧配置或租户 release 重现，active/reserved 兑换码、pending 邀请、challenge、敏感授权、未终结注册和旧 provider job 也不能恢复
- 任意注册、登录、邀请、换号和短信复验 API 即使绕过前端，也只能把有效中国大陆手机号规范化为唯一 `+86...` E.164 身份；输入格式变体必须命中同一用户和同一限流桶，`+852/+853/+886` 及其他国际号码不得调用 Core 短信 provider。客户、仓库和物流联系电话继续按各业务/provider 规则校验，不能被误套用身份手机号限制
- 任一需要 D48 的高危写接口在没有当前 AuthContext 操作者对应、未过期且尚未消费的动作专用验证码时必须拒绝；Admin 控制面动作要求操作者仍是 active Admin，本人换号则要求当前有效成员的 old/new 两码。验证码上下文绑定 tenant、actor、action、目标资源/版本和规范化请求摘要，修改 payload、跨操作/跨租户复用、重放或在签发后失去所需权限均不能执行。最后一名 Admin 保护仍是绝对约束，不能被验证码绕过；普通业务接口不得误套用该门禁
- 同一 canonical 手机号在尚无有效 membership 时可以保有多个租户各自的 pending 邀请，且每条只占对应租户一个席位；并发接受、兑换码注册或换号占用该身份时只能一个租户成为最终归属，提交事务必须把其他 pending 邀请置为不可恢复的失效终态并立即释放其租户席位。旧链接、旧验证码或稍后重放不能建立第二个 membership，任何租户端响应也不能泄露该手机号还收到了哪些租户邀请或最终加入了哪个租户
- 生产短信始终使用腾讯云平台统一签名，修改任一租户品牌不会改变签名；企业资质、签名、模板或运营商报备任一未就绪时，注册、登录和短信安全复验均 fail closed，验证码和腾讯云 Secret 不出现在响应、日志、数据库明文或指标中
- CVM/云监控 Agent 缺失或停止上报、整台云主机停止、Nginx/Web/MySQL/worker 故障、备份超龄、任务持续积压及短信/SF 等 provider 系统性异常都必须由已确认的三层信号之一发现；整机停止时不能依赖同机应用自报。站外 serving 探测负责 P1 对外不可用和内部恢复耗时计时，独立 monitor dead-man 探测把 worker/evaluator heartbeat stale 或已锁存的告警投递失败作为 P2，不能误启动整机 DR。公开探测端点不得泄露版本、租户、数据库或 Secret，也不得被 CDN/缓存返回假绿色；生产部署中不存在 Managed Prometheus、Grafana 或通用 metrics 抓取依赖
- 监控使用腾讯云消息接收人绑定维护者个人微信、手机和邮箱；P1 全天电话 + 短信 + 邮件，P2 微信 + 邮件，恢复通知沿原渠道发送。首次上线和接收配置变更后必须逐渠道验证，告警正文不得包含租户业务数据或 Secret

## Dependencies and Conflicts

- 当前未归档 OpenSpec 变更已经逐项分类：顺丰产品类型在切换前收尾、损坏备注按完成归档，只暂停旧 A4 独立发货单和旧扫码发货流程，其余能力（包括甘特冲突提示）全部保留并随 SaaS 的租户、仓库、持久任务及聚合 API 边界适配。首次生产数据迁移演练前 7 天起冻结 schema 和 rentals、发货、甘特图、顺丰、闲鱼核心模块，直到正式切换稳定 48 小时；冻结期间只允许有记录的 P0 安全或生产故障修复，并须重跑迁移、回滚、隔离与受影响 API 契约测试。
- 生产短信、监控告警渠道及 D49 三层信号采集均已确认使用腾讯云能力，Core 不引入 Managed Prometheus；支付渠道可推迟到 Commercial SaaS。异机备份介质、Core 不使用托管 MySQL、本地平台根密钥与 Secret 加密方式均已确认。
- 默认租户显示名称和首位 Admin 手机号在首次生产迁移时作为必填部署参数录入，不写死在代码、镜像或迁移默认值中；现有第三方凭证归入该默认租户。

## Approval Gate

D01–D59 的 SaaS Core 产品与技术方案决策均已逐项确认，但这不自动等于总体批准。开始编写约束性 delta spec、业务代码、数据库迁移或基础设施变更前，仍须由项目负责人明确通过 SaaS Core 整体 Approval Gate；通过后再创建 delta specs 与 `tasks.md` 并运行严格校验。未来商业化或新找回能力等 Core 之外事项继续另立决策，不阻塞本次整体审批。
