# rental-management Specification

## Purpose

由当前 `app/routes/rental_api.py`、`app/handlers/rental_handlers.py`、`app/services/rental/rental_service.py`、`app/models/rental.py`，以及 PC／移动端租赁表单和甘特图入口反推的已实现行为。覆盖查询、档期、创建、同单多设备、编辑、状态、删除、确认信息与发货单查询。物流估算、验货、快递下单等独立功能只记录和租赁单直接相接的行为。本文件描述当前代码，不把尚未实现的期望写成现状。

## Requirements

### Requirement: 按租户和仓库查询租赁记录

系统 MUST 在当前租户的数据范围内读取租赁记录，并支持按仓库、设备、客户姓名、电话、地址、状态和日期范围筛选。列表 MUST 按租赁 ID 倒序分页返回，每页最多 100 条。

#### Scenario: 按仓库查看记录
- **WHEN** 操作员选择一个仓库查询租赁列表
- **THEN** 结果只包含该仓库的租赁记录

#### Scenario: 组合条件筛选
- **WHEN** 操作员同时提交设备、状态和完整的起止日期筛选条件
- **THEN** 结果只包含满足全部条件、且租赁开始日期不早于筛选起日、结束日期不晚于筛选止日的记录

#### Scenario: 查看单条记录
- **WHEN** 操作员打开一个存在的租赁记录
- **THEN** 系统返回该记录的当前数据；记录不存在时返回不存在错误

#### Scenario: 分页结果
- **WHEN** 操作员未指定页大小，或请求大于 100 的页大小
- **THEN** 列表分别按默认 20 条或最多 100 条分页，并返回总数、总页数、当前页及前后页标记

### Requirement: 列出已过应归还日的租赁

待归还列表 MUST 只列出所选仓库中，状态为 `shipped`、没有父租赁且结束日期不晚于昨天的主租赁，并显示设备名称、应归还日及逾期天数。

#### Scenario: 显示逾期主租赁
- **WHEN** 一条已发货主租赁的结束日期不晚于昨天
- **THEN** 待归还列表包含该记录、设备名称和逾期天数

#### Scenario: 排除尚未逾期或已寄回记录
- **WHEN** 租赁尚未达到待归还条件，或状态已变为 `returned`
- **THEN** 待归还列表不包含该记录

### Requirement: 创建租赁单时验证基本信息和租期

创建请求 MUST 提供主设备、客户名称、开始日期和结束日期。日期字符串 MUST 可按 `YYYY-MM-DD` 解析，结束日不得早于开始日；同一天租赁可创建。系统 MUST 验证有效占用时间，并将新租赁的初始状态设为 `not_shipped`。

#### Scenario: 创建有效租赁
- **WHEN** 必填信息、租期和设备选择均有效
- **THEN** 系统创建主租赁并返回创建结果

#### Scenario: 缺少必填信息或占用区间无效
- **WHEN** 请求缺少必填字段，或寄出时间不早于收回时间
- **THEN** 系统拒绝创建，且不留下部分租赁记录

#### Scenario: 同一天租赁
- **WHEN** 开始日与结束日相同，且其他信息有效
- **THEN** 系统允许创建，租赁天数为 1 天

### Requirement: 新建租赁时严格验证库存

新建租赁 MUST 使用所选仓库内处于正常可出租生命周期的主设备和库存附件。系统 MUST 拒绝与活动租赁占用时间重叠的设备，且主设备与附件不能重复选择同一库存设备。

#### Scenario: 主设备或附件被占用
- **WHEN** 新建请求选择的主设备或库存附件与另一条活动租赁的有效占用时间重叠
- **THEN** 系统返回设备不可用错误，且不创建租赁

#### Scenario: 设备不属于所选仓库
- **WHEN** 主设备或附件属于其他仓库
- **THEN** 系统返回仓库不匹配错误，且不创建租赁

#### Scenario: 设备已售出或停用
- **WHEN** 新建请求选择非正常可出租生命周期的设备
- **THEN** 系统拒绝该设备选择

### Requirement: 按实际占用时间判断档期冲突

档期检查 MUST 优先使用寄出时间和收回时间；缺失时分别使用租赁开始日的起点和结束日的终点。`not_shipped`、`scheduled_for_shipping`、`shipped`、`returned` 状态占用档期，完成或取消的租赁不再占用档期。

#### Scenario: 物流时间延伸到另一租赁
- **WHEN** 两条租赁的起止日期不重叠，但寄出至收回的有效占用时间重叠
- **THEN** 新建租赁的冲突检查将该设备判定为被占用

#### Scenario: 旧记录缺少物流时间
- **WHEN** 一条活动租赁没有寄出或收回时间
- **THEN** 档期检查使用其租赁日期边界判断冲突

### Requirement: 保持设备型号与租赁组合一致

创建租赁 MUST 使用所选设备型号允许的启用租赁组合，并在租赁上保存组合名称及项目快照。未指定组合时使用型号默认组合；没有可用组合的型号无法创建租赁。编辑时明确更换设备型号后，原组合不兼容时 MUST 改用目标型号的默认组合；不换型号的历史订单仍保留已保存的组合快照。

#### Scenario: 创建时选择无效组合
- **WHEN** 请求选择设备型号不允许或已停用的租赁组合
- **THEN** 系统拒绝请求，不创建租赁

#### Scenario: 编辑时换成另一型号
- **WHEN** 操作员更换主设备，原组合不适用于新型号
- **THEN** 编辑器或服务端选择新型号的默认组合，并保存新的组合快照

#### Scenario: 型号库配置事后变化
- **WHEN** 一条租赁已保存组合快照，之后型号库修改组合名称或项目
- **THEN** 查询该历史租赁仍返回下单时的组合名称和项目

### Requirement: 同单多设备预约原子保存

同单录入的主设备 MUST 属于同一型号，且主设备和库存附件不能在同一次预约或已录同单记录中重复。多设备创建及补齐 MUST 在同一个事务中保存全部设备及其附件。

#### Scenario: 同单创建两台设备
- **WHEN** 操作员为同一订单选择两台同型号且均可用的主设备
- **THEN** 系统一并创建对应主租赁和附件租赁，并关联同一预约

#### Scenario: 第二台设备校验失败
- **WHEN** 同单的任一设备或附件无效、被占用或跨仓库
- **THEN** 整个创建请求失败，先前选中的设备也不会被部分保存

### Requirement: 区分配套附件与库存附件

手柄和镜头支架等配套附件 MUST 以主租赁上的标记保存；选中的库存附件 MUST 以关联主租赁的子租赁记录保存。编辑主租赁的附件选择时，系统 MUST 在同一事务中增删对应子租赁，并同步其仓库、租期和状态。

#### Scenario: 同时选择两类附件
- **WHEN** 操作员选择配套手柄及一个库存三脚架
- **THEN** 主租赁保存手柄标记，三脚架生成一条子租赁记录

#### Scenario: 编辑库存附件
- **WHEN** 操作员移除旧库存附件并加入新的可用库存附件
- **THEN** 系统删除旧子租赁、创建新子租赁，并保持主租赁和子租赁信息一致

### Requirement: 租赁设备选项按型号和名称排序

PC 和移动端的新建、编辑设备选项 MUST 先按型号名称、再按设备名称升序自然排序；名称中的数字按数值顺序比较。

#### Scenario: 型号和设备名称含数字
- **WHEN** 清单同时包含型号 X2、X10，以及同型号下的设备 2、设备 10
- **THEN** X2 排在 X10 前，设备 2 排在设备 10 前

### Requirement: 编辑设备清单同时提示档期与生命周期状态

PC 和移动端编辑租赁时，设备清单 MUST 分别标出设备在当前编辑租期内是否有档期冲突，以及是否已售出、损坏、停用或退役。档期查询 MUST 排除正在编辑的租赁本身；查询失败时不得把未知状态显示为可用。已有租赁当前使用的非正常生命周期设备仍须可见。

#### Scenario: 同一设备既已售出又有档期冲突
- **WHEN** 操作员打开编辑页设备清单，而某设备同时满足这两个条件
- **THEN** 清单同时显示“已售出”和“档期冲突”

#### Scenario: 修改租期后再次打开设备清单
- **WHEN** 操作员修改租赁日期或物流时间，再打开设备清单
- **THEN** 清单按修改后的时间重新检查，不沿用旧租期的查询结果

#### Scenario: 档期查询失败
- **WHEN** 查询设备冲突的请求失败
- **THEN** 清单显示档期未确认或查询失败，不显示档期可用

### Requirement: 编辑主设备允许冲突但保留其他库存限制

编辑已有租赁时，系统 MUST 提示所选主设备与其他租赁的档期重叠，并允许操作员继续保存，以支持两条租赁交换设备。更换后的设备仍 MUST 存在、属于目标仓库、处于正常可出租生命周期，且同单设备保持同一型号；库存附件的占用冲突仍 MUST 拒绝。设备和附件选择均未改变、占用时间也未改变时，原有历史选择可继续保存。

#### Scenario: 两条租赁对换主设备
- **WHEN** 两条租赁时间重叠，操作员先将第一条改用第二条的设备，再将第二条改用第一条的设备
- **THEN** 两次编辑均可在冲突提示后保存

#### Scenario: 编辑时换成已售设备
- **WHEN** 操作员将主设备换成已售出的另一台设备
- **THEN** 系统拒绝保存，原设备保持不变

#### Scenario: 编辑时选择已占用附件
- **WHEN** 操作员为租赁选择与其他租赁档期重叠的库存附件
- **THEN** 系统拒绝保存，主租赁及子租赁均保持原状

### Requirement: 编辑租赁信息原子提交

编辑页 MUST 读取当前租赁数据，允许修改租期、物流时间与单号、客户电话和地址、设备、附件、状态、订单信息、代传照片及损坏备注。PC 编辑页显示客户 ID 但保持只读；移动端表单可提交客户名称。系统 MUST 在验证完整选择后原子提交；并发修改导致未显式提交的关键字段过期时 MUST 要求重试。

#### Scenario: 任一校验失败
- **WHEN** 编辑请求同时修改客户信息和选择一个跨仓库附件
- **THEN** 系统拒绝整个请求，客户信息、主设备和附件均保持原值

#### Scenario: 并发编辑使用过期数据
- **WHEN** 另一操作已修改租赁的设备、附件或租期，而当前编辑请求沿用旧的默认值
- **THEN** 系统拒绝按过期默认值保存，并要求重新查询

### Requirement: 保存并展示当前损坏备注

租赁 MUST 最多保存一条当前损坏备注。PC 与移动端编辑页 MUST 加载、编辑和清空它；非空备注 MUST 在编辑页明显提示。保存时备注去除首尾空白，空值存为 `null`，超过 1000 字或非字符串值 MUST 被拒绝。

#### Scenario: 编辑和清空备注
- **WHEN** 操作员保存一条备注后重新打开编辑页，再将其清空
- **THEN** 首次可看到保存的备注与提示，清空后 API 返回 `damage_note = null`

#### Scenario: 备注格式无效
- **WHEN** 编辑请求提交非字符串备注或去空白后超过 1000 字
- **THEN** 系统拒绝请求，原备注不变

### Requirement: 更新租赁状态并同步库存附件

编辑租赁可保存 `not_shipped`、`scheduled_for_shipping`、`shipped`、`returned`、`completed`、`cancelled` 状态；独立状态更新接口接受上述状态中除 `scheduled_for_shipping` 外的五种。通过租赁编辑或状态更新接口变更状态时，变化 MUST 同步到库存附件的子租赁；首次变为已发货且没有寄出时间时补写寄出时间，首次变为已完成且没有收回时间时补写收回时间。

#### Scenario: 主租赁完成
- **WHEN** 操作员把有库存附件的主租赁改为 `completed`
- **THEN** 主租赁和附件子租赁均为 `completed`；未填写的收回时间被补写

#### Scenario: 非法状态
- **WHEN** 编辑请求提交不在允许集合中的状态
- **THEN** 系统拒绝编辑，不改变租赁状态

#### Scenario: 独立状态接口提交已预约
- **WHEN** 客户端通过 `/api/rentals/<id>/status` 提交 `scheduled_for_shipping`
- **THEN** 接口返回无效状态错误；编辑接口仍可保存该状态

### Requirement: 单条租赁发货到闲鱼

PC 与移动端编辑页可触发单条租赁的闲鱼发货操作。系统 MUST 要求该租赁已有闲鱼订单号和寄出快递单号；仅在闲鱼服务返回成功后，将该租赁标记为 `shipped`，并在缺少寄出时间时补写。此入口当前只更新指定租赁本身，不调用普通状态更新的子租赁同步逻辑。外部服务失败时 MUST 保持租赁原状并返回失败信息。

#### Scenario: 成功发货
- **WHEN** 租赁具备订单号和快递单号，且闲鱼服务确认发货成功
- **THEN** 系统将该租赁标记为已发货，并返回成功结果

#### Scenario: 缺少必要单号或外部发货失败
- **WHEN** 租赁缺少订单号、快递单号，或闲鱼服务未确认成功
- **THEN** 系统不把该租赁标记为已发货，并返回错误

### Requirement: 删除租赁时清理其库存附件记录

删除主租赁 MUST 同一事务删除其库存附件子租赁；删除不存在的租赁 MUST 返回不存在错误。

#### Scenario: 删除带库存附件的主租赁
- **WHEN** 操作员删除一条带库存附件的主租赁
- **THEN** 主租赁及其关联的子租赁均被删除

#### Scenario: 删除不存在的租赁
- **WHEN** 删除请求指向不存在的租赁 ID
- **THEN** 系统返回不存在错误，不修改其他租赁

### Requirement: 区分读仓库和写仓库

租赁列表、待归还和发货日期查询 MUST 接受具体仓库或 `all` 读范围。创建与编辑 MUST 解析为一个具体仓库：只有租户恰好有一个仓库时才可省略；有多个仓库时必须指定。PC 与移动端在“全部仓库”视图 MUST 阻止租赁表单提交。

#### Scenario: 在全部仓库查看租赁
- **WHEN** 操作员以 `warehouse_id=all` 读取租赁列表
- **THEN** 系统不按仓库过滤，但结果仍限于当前租户

#### Scenario: 多仓库租户未选择仓库就创建
- **WHEN** 多仓库租户的新建请求不含具体仓库
- **THEN** 服务端拒绝写入；PC 和移动端在全部仓库视图禁用创建提交

#### Scenario: 单仓库租户省略仓库
- **WHEN** 租户只有一个仓库且创建请求省略仓库
- **THEN** 系统把租赁及库存附件绑定到该仓库

### Requirement: 租赁详情包含展示和后续编辑所需字段

单条租赁和列表的 `to_dict` 结果 MUST 包含主设备、仓库、租期、有效物流时间和运单号、客户和订单信息、状态、损坏备注、配套附件标记、代传照片标记、镜头兼容字段、租赁组合快照、库存附件和子租赁、同单摘要，以及创建／更新时间。租赁天数按包含首尾两天计算；`is_overdue` 仅在状态为 `shipped` 且今天晚于结束日时为真。

#### Scenario: 读取有库存附件的主租赁
- **WHEN** 操作员读取关联手机支架子租赁的主租赁
- **THEN** 响应同时提供 `accessories` 的设备摘要和 `child_rentals` 的租赁记录，供表单恢复已选附件

#### Scenario: 读取同单多设备租赁
- **WHEN** 一条主租赁关联 `RentalBooking`
- **THEN** 响应的同单摘要包含应录、已录、已发台数、总金额和各有效主设备摘要；已取消主设备不计入已录和已发数量

### Requirement: 搜索接口沿用租赁列表筛选和分页

`/api/rentals/search` MUST 支持设备、客户姓名、电话、地址、状态、完整起止日期、仓库及分页，并返回与列表相同的分页结构。当前通用查询 `q` MUST 按客户姓名模糊匹配；只有明确传入 `phone` 或 `destination` 时才分别筛选电话或地址。

#### Scenario: 用通用词搜索
- **WHEN** 客户端提交 `q=张`，同时提交具体客户姓名筛选值
- **THEN** 查询使用 `张` 作为客户姓名模糊条件，并继续应用其他显式筛选条件

#### Scenario: 用电话或地址搜索
- **WHEN** 客户端显式提交 `phone` 或 `destination`
- **THEN** 对相应字段使用包含匹配，并与其他条件取交集

### Requirement: 待归还日期与接力信息可供操作员处理

待归还查询 MUST 将租赁结束日的次日作为应归还日，并以今天距该日的天数计算逾期天数；结果按逾期天数降序、租赁 ID 升序排列。若该主租赁是接力发货的前一单，结果 MUST 标记接力并给出后一单 ID。`/api/rentals/due-today` MUST 返回同一列表。

#### Scenario: 昨天结束的已发货租赁
- **WHEN** 今天查询一条昨天结束且仍为 `shipped` 的主租赁
- **THEN** 它的应归还日为今天，逾期天数为 0，并出现在待归还列表

#### Scenario: 接力前单
- **WHEN** 待归还租赁存在接力绑定的后一单
- **THEN** 列表项带接力标记及后一单租赁 ID

### Requirement: PC 待归还抽屉可标记已寄回

PC 甘特图 MUST 显示待归还数量，并把列表分为今日、逾期 1 至 3 天、4 至 7 天、超过 7 天四组；列表显示设备、租期、应归还日、地址、租赁人及电话。操作员在具体仓库可将记录标记为 `returned`，成功后从列表移除并刷新甘特图；全部仓库视图只能查看，不能执行该操作。

#### Scenario: 今日应归还
- **WHEN** 一条待归还记录的 `overdue_days` 为 0
- **THEN** 它显示在“今日”组，可查看联系信息并复制电话

#### Scenario: 标记已寄回
- **WHEN** 操作员在该记录所属具体仓库点击“标记为已寄回”，状态接口保存成功
- **THEN** 记录从待归还列表移除，甘特图刷新；即使随后列表刷新失败也不误报状态更新失败

### Requirement: 按发货日期查询批量打印候选

`/api/rentals/by-ship-date` MUST 要求完整的 `YYYY-MM-DD` 起止日期，拒绝逆序或超过 365 天的范围，并按仓库返回未取消的主租赁。`not_shipped` 按寄出时间筛选，缺失时回退到开始日；`scheduled_for_shipping` 按预约发货时间筛选；`shipped`、`returned`、`completed` 按寄出时间筛选。结果 MUST 包含接力后单标记、上一单状态和发货分组信息。

#### Scenario: 旧待发货单缺少寄出时间
- **WHEN** 一条 `not_shipped` 主租赁没有寄出时间，开始日落在指定日期范围
- **THEN** 它仍进入发货单候选

#### Scenario: 预约发货和已发货单
- **WHEN** 一条已预约租赁的预约发货时间、另一条已发货租赁的实际寄出时间落在范围内
- **THEN** 两者都进入候选，并使用各自对应的时间字段判断

#### Scenario: 批量打印预览后切换仓库
- **WHEN** PC 操作员预览后切换仓库
- **THEN** 预览结果被清空；开始打印前还会确认所有候选属于当前具体仓库

### Requirement: 新建表单以型号、租期和物流天数选择设备

PC 和移动端新建表单 MUST 允许选择开始日、结束日、设备型号、主设备和 0 至 7 天物流预留。PC 型号清单只显示启用型号；结束日不得早于开始日。PC 默认可继承甘特图当前型号；型号、租期、物流天数或仓库变化后，旧档期查询与不再可靠的设备选择 MUST 失效。收件信息中提取到手机号且电话栏为空时，表单 MUST 自动填入。

#### Scenario: 修改型号或租期
- **WHEN** 操作员已选主设备，之后改变型号或租期
- **THEN** 表单清除或重新核对旧选择，不能直接沿用旧的可用档期结论

#### Scenario: 收件信息带手机号码
- **WHEN** 操作员粘贴含手机号的收件信息，电话栏仍为空
- **THEN** 表单把提取出的手机号填入电话栏；已经填写的号码保持原值

### Requirement: 新建表单按物流预留生成占用时间

新建表单 MUST 根据租赁日期和物流天数计算发货、入库占用边界：发货日在开始日前 `物流天数 + 1` 天，入库日在结束日后 `物流天数 + 1` 天。移动端生成的默认时刻分别为 09:00 和 18:00；PC 在未采用查找档期返回时间时使用计算出的日期起点。服务端 MUST 以请求中的实际时间校验占用。

#### Scenario: 预留一天物流
- **WHEN** 租赁从 10 日到 12 日，物流天数为 1
- **THEN** 表单生成 8 日寄出、14 日入库的占用边界，再把实际时刻提交给服务端

### Requirement: 新建设备清单与查找档期

PC 新建设备清单 MUST 限于所选型号，标出生命周期或档期状态；非正常生命周期设备不得选择。操作员可手动选设备或调用甘特图查找档期自动匹配。移动端设备列表 MUST 使用当前日期、型号和物流天数查到的可用设备，按型号、名称自然排序。多设备选择 MUST 排除表单中已经占用的主设备和库存附件 ID。

#### Scenario: 查找可用设备
- **WHEN** 操作员已填型号、租期和物流天数并点击“查找档期”
- **THEN** 表单从可用候选中选一台尚未被本次订单其他行选中的设备，并显示其名称

#### Scenario: 查找时改变条件
- **WHEN** 较早一次档期查询尚未返回，操作员已经修改型号或租期并发起新查询
- **THEN** 较早的结果不覆盖当前表单选择

### Requirement: 查找档期接口返回可用设备候选

`/api/rentals/find-slot` MUST 要求租赁起止日、物流天数、型号和是否附件参数；按所选仓库和正常可出租生命周期筛选设备，并检查物流预留后的占用时间。指定型号时按型号 ID 查主设备；附件查找可不限制型号。接口 MUST 返回首台设备、全部可用设备、数量及寄出／收回日期；没有可用设备时返回不存在错误。当前服务端查询占用的时刻分别为寄出日 19:00、收回日 12:00。

#### Scenario: 查到多台候选
- **WHEN** 同型号两台设备在所选仓库和档期内均可用
- **THEN** 响应包含两台设备、总数、首台设备和计算出的物流日期

#### Scenario: 找不到候选
- **WHEN** 所选型号所有正常设备均在该档期内被占用
- **THEN** 接口返回无可用档期，不创建租赁

### Requirement: 库存附件在表单中按类型选择

新建和编辑表单 MUST 分别提供手机支架与三脚架库存附件选项；PC 新建表单在日期已填写后检查附件档期，并标出可用或不可用。主租赁创建／编辑 API 以设备 ID 列表接收库存附件，并验证类型、仓库、生命周期、重复选择和占用冲突。配套手柄和镜头支架通过布尔标记提交。移动端编辑表单与该 API 格式的差异记录在下方缺口中。

#### Scenario: 同一订单选择多个库存附件
- **WHEN** 表单选择一台手机支架和一台三脚架
- **THEN** 请求包含两台库存设备 ID，保存后主租赁有两条子租赁

#### Scenario: 库存附件档期冲突
- **WHEN** 操作员提交一台和其他活动租赁占用重叠的库存附件
- **THEN** 服务端拒绝整个创建或编辑请求，即使表单先前显示可用

### Requirement: 创建时保存客户、订单和附加服务字段

创建租赁 MUST 保存客户姓名、可选电话与收件信息、闲鱼订单号与店铺、订单金额、买家 ID、寄出及寄回运单号、寄出与收回时间、配套附件标记和代传照片标记。未选配套附件或代传照片时，相应标记为假。创建响应 MUST 同时给出首台主租赁、全部新建主租赁和首台库存附件子租赁。

#### Scenario: 只有主机的租赁
- **WHEN** 新建请求不选库存附件、配套附件及代传照片
- **THEN** 系统创建一条主租赁，附件列表为空，相关布尔标记为假

#### Scenario: 创建后恢复表单
- **WHEN** 客户端使用创建返回的首台租赁 ID 读取详情
- **THEN** 订单、客户、物流、租赁组合及附件选择均可从详情恢复

### Requirement: 单设备和多设备创建的事务边界

一次新建请求可包含首台设备和 `additional_devices`。多台设备 MUST 使用同型号；每台可独立选择租赁组合、配套附件、库存附件和代传照片，公共客户、仓库、租期和订单信息由首台继承。任何一台校验失败时，主租赁、子租赁和预约记录 MUST 全部回滚。

#### Scenario: 第二台选择不同组合
- **WHEN** 同单两台同型号设备分别选择不同的有效租赁组合
- **THEN** 两条主租赁分别保存各自的组合快照

#### Scenario: 第三台设备被占用
- **WHEN** 同单前三台中的第三台与其他活动租赁冲突
- **THEN** 本次请求不留下前两台或预约记录

### Requirement: 多设备请求标识支持安全重试

多设备创建或补齐 MUST 携带有效 UUID 请求标识。服务端 MUST 在同一事务保存请求内容摘要和创建的租赁 ID；同标识同内容重试返回已有结果，同标识不同内容、或原创建记录已删除时拒绝重放。前端在表单内容变化后 MUST 换用新的请求标识。

#### Scenario: 网络超时后重试原请求
- **WHEN** 首次多设备创建已提交，但客户端用原标识和原内容重试
- **THEN** 返回原设备记录，不生成第二组租赁

#### Scenario: 标识被用于另一内容
- **WHEN** 客户端复用请求标识但修改订单金额或设备
- **THEN** 系统拒绝请求，原订单保持不变

### Requirement: 同单金额按分精确分摊

多设备预约 MUST 把同单订单总金额按整数分分摊到所有有效主设备，使每台金额非负且总和精确等于订单总金额。订单金额必须有限、非负且不超过 `99999999.99` 元；未提供金额时不强制写入各台金额。

#### Scenario: 金额不能整除设备数量
- **WHEN** 101.01 元订单分给两台设备
- **THEN** 两台分摊金额之和仍为 101.01 元，不因四舍五入丢失分

#### Scenario: 极小金额的多设备订单
- **WHEN** 0.02 元订单分给五台设备
- **THEN** 各台金额不为负数，五台合计仍为 0.02 元

### Requirement: 同单上下文只查同店同订单号

新建表单输入闲鱼订单号后，MUST 可按已解析的店铺及订单号读取尚未取消的同单主租赁；没有订单号时返回空列表。PC 和移动端 MUST 允许操作员查看已录设备，并在尚缺设备时明确选择补齐；已录齐时提示到甘特图查看。

#### Scenario: 同一订单号属于不同店铺
- **WHEN** 两个店铺存在相同订单号
- **THEN** 同单查询只返回当前指定店铺的主租赁

#### Scenario: 订单已录齐
- **WHEN** 同单已录数量达到应录数量
- **THEN** 表单提示已录齐，不进入补齐模式

### Requirement: 声明现有单台订单需要两台

对于有效的单台主租赁，`declare-booking` MUST 在原仓库把订单显式声明为应租两台，并把原租赁关联到预约；重复声明返回现有预约。若同店同订单号已有多条未取消主租赁但未关联为同单，MUST 拒绝自动合并。

#### Scenario: 先录一台再声明两台
- **WHEN** 原订单只有一条有效主租赁，操作员确认需要补齐第二台
- **THEN** 同单摘要显示应录 2 台、已录 1 台，原租赁金额暂时保持不变

#### Scenario: 已有多条未关联主租赁
- **WHEN** 同店同订单号下已有多条有效主租赁
- **THEN** 声明接口要求人工核对，不自动把它们合并

### Requirement: 补齐设备继承原单公共信息

补齐请求 MUST 引用一条有效同单主租赁，并要求仓库、闲鱼订单号和店铺与原单一致。新设备 MUST 继承原单客户、电话、地址、共同租期、物流边界和买家 ID；不得重复选择已录同单主设备或库存附件，且补齐后有效设备台数不得超过应录台数。补齐时系统 MUST 重新分摊原单总金额。

#### Scenario: 补齐时提交不同客户名或金额
- **WHEN** 补齐请求额外填写另一个客户名或新金额
- **THEN** 新台仍使用原单公共客户资料与原单总金额分摊

#### Scenario: 补齐超过应录数量
- **WHEN** 追加后有效主设备台数超过同单应录台数
- **THEN** 系统拒绝补齐，不修改原有租赁

### Requirement: 同单取消、重补和减租

同单摘要 MUST 只把未取消的主租赁计入已录数量。取消一台后，原预约仍保留应录台数，操作员可补齐一台。只有原本应录两台、当前恰好剩一台有效主租赁时，才可用 `reduce-booking` 确认改为一台；必须提交最多 500 字的非空原因和最多两位小数的减租后金额，并记录审核日志。

#### Scenario: 取消一台后重新补齐
- **WHEN** 两台订单取消其中一台，随后补入另一台同型号设备
- **THEN** 已录数量重新达到 2，未取消主租赁金额合计仍等于同单总金额

#### Scenario: 正式减租为一台
- **WHEN** 两台订单只剩一台有效主租赁，操作员提交原因和有效新总金额
- **THEN** 同单应录数量变为 1，剩余主租赁金额改为新总金额，并留下减租审核日志

### Requirement: 同单设备可分别查看和处理

PC 编辑弹窗和移动端租赁详情 MUST 显示同单应录、已录、已发数量及各有效主设备摘要，并允许打开另一台的租赁记录。每台主设备的开始日、寄出时间、状态、验货与归还处理仍落在该台租赁上；单台编辑不得改动同单结束日、收回时间、客户、仓库、闲鱼订单或分摊金额。

#### Scenario: 查看另一台
- **WHEN** 操作员从同单第一台点击“查看此台”进入第二台
- **THEN** 打开第二台租赁详情，保留它自己的设备、组合和状态

#### Scenario: 单台修改共同结束日
- **WHEN** 操作员只在某台编辑请求中改同单结束日
- **THEN** 服务端拒绝修改，不悄悄改变同单其他租赁

#### Scenario: 单台调整独立档期
- **WHEN** 操作员只调整同单某台设备的开始日期或寄出时间
- **THEN** 系统只更新该台租赁及其库存附件，不改变同单其他主设备的独立档期

### Requirement: 单设备冲突查询返回重叠租赁详情

`/api/rentals/check-conflict` MUST 使用请求的设备 ID、寄出时间和收回时间检查活动租赁，可按 `exclude_rental_id` 排除正在编辑的记录。重叠结果 MUST 包含关联租赁 ID、客户、租期、物流时间和状态；时间边界相接但不交叠不构成冲突。

#### Scenario: 排除当前租赁
- **WHEN** 编辑页检查现用设备，并提交当前租赁 ID 作为排除项
- **THEN** 当前记录不作为自身冲突返回，其他重叠活动租赁仍返回

#### Scenario: 两段占用首尾相接
- **WHEN** 新区间的开始时间恰好等于旧区间的结束时间
- **THEN** 冲突结果不包含该旧租赁

### Requirement: 批量设备冲突查询给出冲突设备 ID

`/api/rentals/check-device-conflicts` MUST 接受最多 500 个正整数设备 ID、有效且有序的寄出／收回时间和可选排除租赁 ID，对请求 ID 去重，并按升序返回发生冲突的设备 ID。前端设备清单超过 500 台时 MUST 分批查询；任一批查询失败时，编辑下拉清单不得把未知档期标为可用。

#### Scenario: 无效批量请求
- **WHEN** 请求包含布尔值、非正整数、超过 500 个设备 ID，或收回时间不晚于寄出时间
- **THEN** 接口返回参数错误，不返回误导性的可用结果

#### Scenario: 超过 500 台设备
- **WHEN** 前端需要检查 501 台设备
- **THEN** 它分成至少两次批量请求，再合并冲突状态用于下拉清单

### Requirement: 疑似重复订单采用客户或地址的精确匹配

`/api/rentals/check-duplicate` MUST 在活动状态租赁中，以去掉首尾空白后的客户名称或收件信息完全相同作为疑似重复条件，排除指定当前租赁，按创建时间倒序最多返回 10 条。若请求同时提供完整有效的起止日期，结果 MUST 标出租赁日期是否重叠；名称和地址均为空时直接返回无重复。重复提示不自动阻止创建。

#### Scenario: 地址相同但租期不重叠
- **WHEN** 新建表单的地址与历史活动租赁完全相同，但租赁日期不重叠
- **THEN** 接口仍返回疑似重复，日期冲突标记为假；操作员可确认后继续创建

#### Scenario: 只有部分客户名称相同
- **WHEN** 新客户名称仅包含历史客户名称的一部分，且地址不同
- **THEN** 精确重复查询不因客户名称子串而返回该历史租赁

#### Scenario: 创建表单发现疑似重复
- **WHEN** PC 或移动端新建表单检测到同名或同地址的活动租赁
- **THEN** 提交前显示重复提醒；操作员取消则不创建，确认则继续后续校验

### Requirement: 物流时效不足只触发确认提示

创建和编辑表单 MUST 可按目的地查询顺丰标快预计时效。创建时若预留天数不足，提交前提示；编辑时只有地址、设备或占用档期等相关表单快照变化时才重新提示。用户取消则停止提交，确认则继续；估算请求失败时表单提示错误并停止本次提交。

#### Scenario: 创建时预留不足
- **WHEN** 操作员选定的物流天数小于地址估算天数
- **THEN** 表单显示两者差异，允许“仍要创建”或返回修改

#### Scenario: 编辑时只改损坏备注
- **WHEN** 地址、设备、租期和物流时间均未变化，仅编辑损坏备注
- **THEN** 编辑表单不重新弹出物流时效确认

### Requirement: 闲鱼订单号和店铺解析保持关联一致

租赁创建和编辑保存闲鱼订单号时 MUST 去除首尾空白并关联店铺；明确提供的店铺必须存在且启用。未指定店铺时，若该订单号恰好有一个待处理闲鱼告警，则使用告警店铺；否则只有系统恰好一个启用店铺时才能自动选择。清空订单号 MUST 同时清空店铺关联。历史告警关联的店铺已停用时，仍按该告警原店铺解析。

#### Scenario: 唯一启用店铺
- **WHEN** 保存带订单号的租赁，未指定店铺且当前只有一个启用店铺
- **THEN** 系统自动绑定该店铺

#### Scenario: 多店铺且无法判断
- **WHEN** 多个店铺启用、订单没有唯一待处理告警，而请求未指定店铺
- **THEN** 系统要求明确指定店铺，不猜测归属

#### Scenario: 清空闲鱼订单号
- **WHEN** 编辑请求将订单号清空
- **THEN** 保存后的订单号和店铺 ID 都为空

### Requirement: 拉取闲鱼订单时保留金额单位和收件组成

拉取闲鱼订单详情 MUST 要求非空订单号和有效的整数店铺 ID，并通过该店铺调用外部服务。响应 MUST 提供收件人姓名、手机、省市区镇及详细地址、买家 EID／昵称和支付金额（分）。PC 与移动端可用这些字段填充收件信息、电话、买家 ID 和以元为单位的表单金额。

#### Scenario: 店铺服务返回订单
- **WHEN** 指定店铺成功返回收件人、地址和以分计的支付金额
- **THEN** API 保留原金额单位，表单转换为元并填充对应字段

#### Scenario: 店铺配置或外部服务失败
- **WHEN** 店铺不存在、配置不完整或服务没有返回订单
- **THEN** 接口返回明确错误，不把别的订单资料填入表单

### Requirement: 编辑页重新读取租赁并保留历史设备

打开 PC 编辑弹窗或移动端编辑页时，客户端 MUST 读取租赁详情并恢复设备、租期、物流、状态、组合、附件和损坏备注。PC 在读取最新详情失败时显示错误并保留可用的已有记录；移动端在记录不存在或加载失败时提示并返回。已保存但现已售出、损坏、停用或退役的当前设备仍可显示；仅更换到另一台这类设备受到限制。

#### Scenario: 当前设备后来售出
- **WHEN** 一条历史租赁所用设备已售出，操作员打开编辑设备清单
- **THEN** 当前设备仍显示为已售出且可保持原选择；其他已售出设备不可作为新选择

#### Scenario: 获取最新详情失败
- **WHEN** PC 编辑弹窗打开时详情读取失败
- **THEN** 弹窗提示最新数据读取失败，并保留已有租赁数据供查看

### Requirement: 编辑同步主租赁和库存附件的公共字段

编辑主租赁成功后，保留或新建的库存附件子租赁 MUST 与主租赁同步仓库、客户、电话、地址、租期、寄出及收回时间、运单号和状态。移除的库存附件子租赁 MUST 删除。更换主设备本身不自动更换库存附件；附件仍要通过有效性校验。

#### Scenario: 修改客户地址和归还时间
- **WHEN** 主租赁编辑更新地址与收回时间，库存附件选择不变
- **THEN** 对应子租赁的地址与收回时间也更新

#### Scenario: 移除一件附件
- **WHEN** 编辑请求不再包含原有三脚架 ID
- **THEN** 该三脚架的子租赁被删除，其他已选附件记录保留

### Requirement: 历史选择不变时允许修改非档期信息

当主设备、仓库、库存附件及有效占用时间都未改变时，编辑 MUST 可沿用历史已售出或停用设备以及原有冲突选择，仅保存损坏备注等非选择字段。只要设备、附件或占用时间发生改变，服务端 MUST 重新验证相应选择；即使状态已完成，也按同一编辑规则处理。

#### Scenario: 历史非正常设备只改备注
- **WHEN** 已完成租赁所用设备现已停用，操作员只修改损坏备注
- **THEN** 保存成功，主设备与附件不被强制替换

#### Scenario: 改动历史订单占用时间
- **WHEN** 操作员改变原租赁的寄出时间，同时保留一件现已被其他订单占用的库存附件
- **THEN** 系统重新校验并拒绝冲突附件，不留下部分时间更新

### Requirement: 删除操作由界面显式确认

PC 编辑弹窗和移动端租赁详情 MUST 在删除前要求操作员确认，并在删除成功后刷新甘特图数据。服务端删除子租赁时只删除该子记录；删除主租赁时一并删除它的子租赁。

#### Scenario: 用户取消删除确认
- **WHEN** 操作员关闭删除确认框
- **THEN** 客户端不发送删除请求，租赁仍在甘特图中

#### Scenario: 直接删除库存附件子租赁
- **WHEN** 删除接口收到一条子租赁 ID
- **THEN** 只删除该子租赁，主租赁保留

### Requirement: 保存后展示租赁确认信息

PC 在新建或编辑成功后、移动端在取得最新租赁详情后，MUST 可显示客户确认信息。确认信息 MUST 组合收货地址与电话、寄出日期、预计收货日（开始日前一天）、客户归还日（结束日后一天）、设备型号、租赁组合和配套／库存附件；同单租赁还显示已录台数及各设备配置。缺少或无效日期使用“未填写”。PC 与移动端 MUST 提供复制全部文本的操作。

#### Scenario: 地址已有同一手机号
- **WHEN** 收件地址文本已包含客户电话
- **THEN** 确认信息不重复附加该号码

#### Scenario: 保存成功但详情加载失败
- **WHEN** 数据已保存，随后确认信息所需的最新详情读取失败
- **THEN** 客户端明确提示“保存成功，但确认信息加载失败”，不误报保存失败

### Requirement: 甘特图提供租赁创建与编辑入口

PC 甘特图 MUST 可打开预定和编辑弹窗，移动端甘特图 MUST 可进入新建页，并从租赁条打开详情底部面板及编辑页。保存或删除成功后，客户端 MUST 重新读取租赁数据；PC 同时刷新日统计和相关提醒。切换仓库时，移动端 MUST 清除旧租赁选择和详情面板。

#### Scenario: 创建成功返回甘特图
- **WHEN** 操作员完成一条有效租赁
- **THEN** 甘特图重新加载，新的租赁记录出现在对应设备档期上

#### Scenario: 移动端切换仓库
- **WHEN** 操作员在租赁详情面板打开时切换仓库
- **THEN** 旧面板关闭、旧租赁选择清空，并读取新仓库的甘特图数据

### Requirement: 外部 API 的租赁读写与主表单入口分开

`/external-api/rentals/<id>` 的读取、更新和取消接口 MUST 要求 `X-API-Key`。其更新入口当前只写寄出／收回时间与状态，取消入口使用独立的 `can_cancel` 判断；它们不通过主租赁编辑服务进行设备和附件选择校验。主表单使用 `/api/rentals` 与 `/web/rentals` 的租赁服务规则。

#### Scenario: 缺少外部 API 密钥
- **WHEN** 外部调用方未带有效 `X-API-Key` 读取或更新租赁
- **THEN** 外部 API 返回 401

#### Scenario: 外部更新租赁
- **WHEN** 外部调用方提交有效密钥、租赁 ID 和寄出时间
- **THEN** 外部更新入口只处理其支持的时间与状态字段，不作为主表单的设备更换入口

## 代码核对中发现的缺口（不作为已实现要求）

- 移动端编辑表单把库存附件提交为 `{id, is_bundled}` 对象，主编辑服务却逐项转成整数 ID；选择附件时该保存路径会失败。上面的库存附件要求描述服务端可接受的格式，并不表示移动端已正确发送。
- `/external-api/rentals` 的创建路由调用旧 `app/services/rental_service.py` 时未传它要求的寄出、收回时间参数，因此当前不能作为可用的创建契约；外部 API 的读取、更新和取消入口是另一条路径。
- PC 编辑页的两个运单号“查询”按钮目前只执行日志输出，没有发起查询；本 spec 只约定运单号可保存，没有把按钮写成已完成的查询功能。
- 单设备冲突提示及疑似重复检查的前端辅助函数在请求失败时返回“无冲突／无重复”；编辑设备下拉使用的批量查询则把失败状态显示为未确认。这两类错误处理当前并不一致。
- 查找档期服务端按寄出日 19:00、收回日 12:00 检查可用性，却只把日期返回客户端；PC 选中该结果后将日期解析为零点再提交。最终仍由创建接口重新校验，因此某些边界档期可能出现“找到候选、保存时拒绝”的情况。
- PC 新建表单再次按 `is_active` 过滤型号，移动端直接列出 `/api/device-models` 返回的型号；该接口本身只返回启用型号，正常情况下两端可选范围相同。

## 复刻用实现契约

本节把前面的行为场景展开为数据、HTTP、算法和页面契约。字段名、状态值、边界与当前代码一致。另一项目可改变技术栈，但要保持这些外部可观察的行为。此契约只涵盖租赁管理及直接依赖；设备管理、租户开通、快递履约、验货、统计、接力排期各自仍需独立规格，不能从这里推断其全部功能。

### 1. 运行边界与依赖

- 业务数据按租户分库。`/api/*`、`/web/*`、`/external-api/*` 请求先解析 `tenant_session` Cookie；缺失或过期返回 HTTP 401、`code=AUTH_REQUIRED`。写请求还需要有效 `X-CSRF-Token`，否则 HTTP 403、`code=CSRF_INVALID`。当前租户暂停、到期、尚未开通时分别按租户边界返回错误，不能读写其他租户的租赁。外部 API 另外检查 `X-API-Key`；API Key 不能代替租户会话。
- 一个租赁只属于一个仓库，`Rental.warehouse_id` 是履约仓库；`Device.warehouse_id` 是设备当前仓库。读取仓库参数可为具体 ID、`all` 或省略。写入必须得到具体 ID：请求明确给出有效整数 ID，或租户恰有一个仓库时自动选择。多仓库租户省略、非法 ID、布尔值均拒绝。当前代码没有在通用详情读取路由上按 UI 当前仓库再做过滤；跨租户隔离依靠租户数据库。
- 设备清单依赖 `GET /api/devices`（用 `is_accessory`、`warehouse_id`、分页读取）和 `GET /api/device-models`。主设备 `is_accessory=false`，库存附件为 `true`；可新租的生命周期只有 `active`。设备型号同时保留旧字符串 `model` 和可空 `model_id`。新建/编辑的备选项按型号 `device_model.display_name → device_model.name → model → 空串`，再按设备 `name`，使用中文、数字自然排序，不分大小写；完全相同再按 ID 升序。
- 页面依赖甘特图 API 提供主设备和主租赁的档期视图，依赖闲鱼店铺／订单接口填充订单，依赖顺丰时效估算提供提醒。这些服务不可用时，租赁核心的直接 API 校验仍是最终写入判断。
- 当前服务使用 Flask、SQLAlchemy、MySQL 租户库；前端 PC 为 Vue 3 + Element Plus，移动端为 Vue 3 + Vant。服务端返回的日期为 `YYYY-MM-DD`，日期时间为无时区 ISO 字符串。服务端自动补写的时间使用 `datetime.utcnow()`；复制实现不能暗中改用本地时区计算后声称结果一致。

### 2. 持久化数据字典

`rentals` 每条库存附件本身也是一条租赁，通过 `parent_rental_id` 指向主租赁；配套手柄和镜头支架不产生子记录。

| 字段 | 当前类型／默认 | 含义和写入规则 |
|---|---|---|
| `id` | 自增整数主键 | 公开租赁标识；列表按它倒序，不用 `created_at` 代替 |
| `booking_id` | 可空外键 | 指向同单多设备 `rental_bookings`；普通单台为空 |
| `device_id` | 非空设备外键 | 当前分配的实物设备；子租赁指向库存附件 |
| `warehouse_id` | 非空仓库外键 | 该租赁的履约仓库；子租赁跟随主租赁 |
| `parent_rental_id` | 可空自引用外键，删除父记录级联 | 空为主租赁，非空为库存附件子租赁 |
| `start_date`、`end_date` | 非空日期 | 包含首尾两日；结束日可以等于开始日，不可更早 |
| `ship_out_time`、`ship_in_time` | 可空日期时间 | 实际／计划的设备占用边界；有值时用于冲突判断，无值回退租赁日期边界 |
| `customer_name` | 非空，最多 100 字符 | PC 新建标签称“闲鱼 ID”，编辑只读；移动端称“客户姓名”，编辑可提交 |
| `customer_phone` | 可空，最多 20 字符 | PC 表单正则要求填写时符合 `^1[3-9]\d{9}$`；服务端没有同等正则 |
| `destination` | 可空，最多 100 字符 | 收件人、电话和地址可合写；表单可从中提取手机号 |
| `xianyu_order_no` | 可空，最多 50 字符 | 保存时去首尾空白；空订单号同时清空店铺 ID |
| `xianyu_shop_id` | 可空店铺外键 | 有订单号时按明确店铺／唯一告警店铺／唯一启用店铺解析 |
| `order_amount` | 可空 `DECIMAL(10,2)` | 单台金额；同单时为总金额分摊值，金额单位元 |
| `buyer_id` | 可空，最多 100 字符 | 闲鱼买家 EID，可由订单拉取填入 |
| `damage_note` | 可空文本 | 编辑前去首尾空白；空串变 `null`，非字符串或超过 1000 字拒绝 |
| `ship_out_tracking_no`、`ship_in_tracking_no` | 最多 50 字符 | 发货／寄回运单号；编辑后同步到库存附件 |
| `scheduled_ship_time` | 可空日期时间 | 预约发货时间，由发货流程使用；本租赁编辑服务当前不在通用可写字段表中 |
| `express_type_id` | 整数，默认 2 | 顺丰服务类型：1 特快、2 标快、263 半日达；通用编辑服务允许显式改写 |
| `status` | 枚举，默认 `not_shipped` | 六种状态见下表；新建忽略客户端自带状态而设为 `not_shipped` |
| `includes_handle`、`includes_lens_mount` | 非空布尔，默认假 | 随主机配套的手柄／镜头支架；没有单独的实物编号或子租赁 |
| `photo_transfer` | 非空布尔，默认假 | 是否代传照片 |
| `lens_combo` | 非空旧枚举，默认 `lens_400mm` | `lens_400mm`、`lens_200mm`、`bare`、`lens_dual`；为旧客户端和旧订单兼容保留 |
| `rental_package_id`、`rental_package_name` | 可空文本 | 下单时使用的型号组合稳定 ID 和名称快照 |
| `rental_package_items` | 可空 JSON 文本 | 下单时组合物品快照；合法项目为非空 `name` + 正整数 `qty` |
| `created_at`、`updated_at` | UTC 日期时间 | 创建／最近更新，响应中为 ISO 字符串 |

`rental_bookings`：`id`、`xianyu_shop_id`、`order_no`、`expected_quantity`（默认 2）、`total_amount`（`DECIMAL(10,2)`）、`quantity_change_reason`、`xianyu_waybill_no`。`(xianyu_shop_id, order_no)` 唯一。计算 `recorded_quantity` 时只计未取消且无父租赁的主机；`shipped_quantity` 只计其中状态为 `shipped`、`returned`、`completed` 的记录。同单成员按租赁 ID 升序返回。

`rental_booking_requests`：UUID 字符串主键 `id`、请求 JSON 按键排序后的 SHA-256 `payload_hash`、本次创建的主租赁 ID 数组 `rental_ids`。请求收据和租赁记录在同一事务写入。其内容不是按订单号去重；不同请求 ID 可触发另外的业务检查。

| 状态 | 中文 UI 文案（移动端） | 是否占用设备档期 | 是否计入同单已发台数 |
|---|---|---|---|
| `not_shipped` | 待发货 | 是 | 否 |
| `scheduled_for_shipping` | 已预约 | 是 | 否 |
| `shipped` | 已发货 | 是 | 是 |
| `returned` | 已寄回 | 是 | 是 |
| `completed` | 已完成 | 否 | 是 |
| `cancelled` | 已取消 | 否 | 否，亦不计已录台数 |

### 3. 响应协议与租赁详情形状

除外部 API 的旧 JSON 格式外，租赁路由使用统一响应壳：成功至少 `{ "success": true }`，有数据才带 `data`，有消息才带 `message`；失败为 `{ "success": false, "message": "..." }`，认证、CSRF、库存／仓库冲突等特定错误另带 `code`。HTTP 状态码由处理器设置，不能只看 `success`。列表响应的 `data` 包含 `rentals`、`total`、`pages`、`current_page`、`per_page`、`has_next`、`has_prev`。创建成功为 201，`data` 含 `main_rental`、`main_rentals` 和首台的 `accessory_rentals`。

`Rental.to_dict()` 必须返回下列键；空值使用 JSON `null`，空数组使用 `[]`。设备摘要同时在 `device` 和兼容别名 `device_info` 返回。`accessories` 是库存附件的设备摘要，不把两个配套附件混入这个数组；`child_rentals` 是库存附件租赁的递归详情。`rental_package` 是 `{id,name,items}` 快照或 `null`。

```text
id, booking, device_id, warehouse_id, start_date, end_date,
ship_out_time, ship_in_time, customer_name, customer_phone, destination,
xianyu_order_no, xianyu_shop_id, order_amount, buyer_id, damage_note,
ship_out_tracking_no, ship_in_tracking_no, scheduled_ship_time,
express_type_id, status, created_at, updated_at, duration_days, is_overdue,
device, device_info, accessories, parent_rental_id, child_rentals,
includes_handle, includes_lens_mount, photo_transfer, lens_combo,
rental_package_id, rental_package_name, rental_package_items, rental_package
```

- `duration_days = end_date - start_date + 1`。`is_overdue = (status == shipped && today > end_date)`，与待归还列表的 `overdue_days` 是两个不同字段。
- 库存附件摘要：`{id,name,model,is_accessory,value}`；`model` 优先型号库名称，`value` 来自型号库设备价值。子租赁递归最多两层，避免父子循环。
- 同单摘要：`{id,expected_quantity,recorded_quantity,shipped_quantity,total_amount,rentals}`。每台摘要包含 `id,device_id,device_name,lens_combo,status,rental_package_name,rental_package_items,includes_handle,includes_lens_mount,photo_transfer,accessories`，其中 `accessories` 为库存附件名称数组。已经取消的成员不显示。
- 甘特图的 `/api/gantt/data` 返回另一个轻量形状：`{devices,rentals,date_range:{start,end},today}`。只列主租赁、排除取消状态；设备列表只含主设备。每条甘特租赁带 ID、设备 ID／名称、仓库、订单号／店铺、客户、日期、物流时间、运单号、状态、旧镜头组合、同单摘要和用于展示的附件。甘特图数据不能代替 `GET /api/rentals/<id>` 作为编辑详情。

### 5. 关键算法与事务顺序

#### 5.1 日期和占用区间

- `start_date`、`end_date` 先转日期，必须满足 `start_date <= end_date`。同一天租赁的 `duration_days` 为 1。
- `ship_out_time`、`ship_in_time` 接受 ISO 日期时间、`T` 或空格分隔，以及纯 `YYYY-MM-DD`；空串与 `null` 视为无值。有效占用起点 = `ship_out_time ?? start_date 00:00:00`；终点 = `ship_in_time ?? end_date 23:59:59.999999`。必须满足起点严格早于终点。
- 两条有效占用区间 `[a,b)`、`[c,d)` 冲突当且仅当 `a < d && b > c`。恰在边界相接不冲突。参与占用的状态仅有 `not_shipped`、`scheduled_for_shipping`、`shipped`、`returned`。已完成和已取消均不占用。
- 列表的起止日期筛选是“记录完全落入指定窗口”：`Rental.start_date >= query.start_date && Rental.end_date <= query.end_date`；只给一端日期时不应用日期筛选。甘特图窗口则用租赁日期的重叠判断，两者语义不同。

#### 5.2 新建：严格库存校验

1. 解析具体仓库、日期、物流时间和组合快照。锁定所有选中设备，顺序为设备 ID 升序。
2. 主设备必须存在、`is_accessory=false`、属于目标仓库，且生命周期为 `active`。每个库存附件必须存在、`is_accessory=true`、同仓、`active`。附件 ID 不得重复。
3. 锁定选中实物对应的有效占用租赁，顺序为租赁 ID 升序。主设备和库存附件任何一件在所选有效占用区间冲突，就整单返回 `409 DEVICE_UNAVAILABLE`，不写入半条数据。
4. 解析订单号与店铺；空订单号对应空店铺。主租赁状态固定为 `not_shipped`。每件被接受的库存附件创建子租赁，继承客户、电话、地址、租期、物流时间、运单号和状态。名字中含“手柄”或“镜头支架”的库存设备被跳过，不创建子记录；这两个配套物由布尔字段表示。
5. `additional_devices` 和补齐动作进入同一个 `create_booking` 事务；第二台失败时，首台和所有附件、同单记录、请求收据全部回滚。单台普通创建也走该入口，但不强制提供请求 UUID。

#### 5.3 编辑：冲突提示与保存约束

- 编辑可换主机，即使目标主机与另一有效租赁占用区间重叠。客户端仍显示“档期冲突”，提交时主机冲突不使服务端拒绝。这使 A、B 两条租赁可以依次对换设备。新建仍禁止这种冲突。
- 换入的主机或库存附件仍必须同仓、类型正确、生命周期 `active`。库存附件冲突仍拒绝。因此“允许冲突”只放宽编辑主机的档期重叠，不放宽已售出／停用状态、仓库、库存附件或数据格式。
- 当仓库、主机 ID、库存附件 ID 集合以及四个日期／时间边界都与原记录相同时，进入 `preserve_existing`：允许继续保存历史已售出、停用或已有冲突的原选择。只修改备注、地址等字段不迫使操作员更换历史设备。任一选择或占用边界变化就重新验证。
- 编辑先按 ID 锁设备，再锁相关占用记录，最后锁当前主租赁及其子租赁。对省略的设备、附件或时间字段，若在锁定期间已被另一修改更新，返回“租赁记录已被其他操作修改，请重试”；不能把旧快照覆盖到新状态。
- 提交成功后，库存附件子租赁集合等于请求中的有效附件集合：删去未选子记录，新增新选子记录，其余保留 ID。所有子记录同步仓库、客户、电话、地址、起止日期、寄出／收回时间、寄出／寄回运单号、状态。主子更新在同一事务中。
- 编辑 `status` 字段可接受六种状态；切换到 `shipped` 且寄出时间为空时填当前 UTC，切换到 `completed` 且收回时间为空时填当前 UTC。独立 `PUT /api/rentals/<id>/status` 不接受 `scheduled_for_shipping`，但其余状态变化也同步子租赁状态。

#### 5.4 同单多设备、重试与金额

- `additional_devices` 必须为对象数组。第 2 台起只允许覆盖 `device_id,lens_combo,rental_package_id,rental_package_name,rental_package_items,includes_handle,includes_lens_mount,photo_transfer,accessories`；其余公共字段取首台。各台主机和附件、既有同单成员使用的实物 ID 不得重复；所有主机必须同一 `model_id`（无 ID 时按旧 `model` 字符串）。
- 提交多设备或 `append_to_rental_id` 时必须带合法 UUID `booking_request_id`。服务端对完整请求对象按 JSON 键排序并计算 SHA-256；同 UUID + 同内容返回原租赁 ID 对应的记录，不重复创建；同 UUID + 不同内容拒绝。原记录已删除也拒绝并要求人工核对。UUID 收据与租赁记录同事务提交。
- 同单由 `(xianyu_shop_id,order_no)` 唯一确定。先锁店铺，再读取并锁同单，再锁设备，避免并发新增突破应录数量。新建多台同单的 `expected_quantity` 为本次台数；已有同单补齐受其应录数量约束。补齐时从原租赁强制继承客户、电话、地址、起止日期、寄出／收回时间和买家 ID，不能用新请求覆盖。未关联的同店同单有效主租赁会使补齐拒绝，要求先核对。
- 订单总金额按十进制处理，必须有限、非负，且不超过 `99999999.99`；按 `ROUND_HALF_UP` 四舍五入到 2 位。设总分数 `C`、总台数 `N`，`q=floor(C/N)`、`r=C mod N`，按既有主租赁 ID 升序再到新增请求顺序，前 `r` 台分配 `q+1` 分，其余 `q` 分。每台金额之和严格等于总金额。例如 `101.01` 元分两台为 `50.51` 与 `50.50` 元；`0.01` 元分两台为 `0.01` 与 `0.00` 元。
- 声明两台仅针对有效、未关联同单、同店同订单号的单台租赁；重复声明返回现有同单。取消一台后 `recorded_quantity` 降低，可补齐空缺。正式减租只允许 `expected_quantity=2` 且当前一台有效，要求非空且最多 500 字的原因和合法总金额；保存减租原因、应录数量 1、总金额及该台分摊金额，并记操作日志。
- 编辑同单某一台时，仓库、结束日、收回时间、客户、电话、地址、订单号／店铺、分摊金额不可在单台编辑里改；开始日、寄出时间、设备、组合、附件、状态可独立改变，但换入设备仍须与同单其他有效主机同型号。

#### 5.5 列表、提醒和辅助查询

- 租赁列表包含主租赁与库存附件子租赁，按 ID 倒序分页；查询对象可筛设备、客户名、电话、地址、状态。`POST /search` 的 `q` 只映射到客户名模糊匹配。前端甘特只显示主租赁。
- 待归还提醒只收集 `status=shipped`、无父记录、`end_date <= 今天-1天` 的租赁。`due_date=end_date+1天`，`overdue_days=今天-due_date`；按逾期天数降序，再按 ID 升序。接力前单另附 `is_relay_handoff` 和后单 ID。`GET /pending-returns` 与 `/due-today` 当前结果相同。
- 按发货日期查询只收集未取消主租赁。待发货使用 `ship_out_time`，空时用 `start_date`；已预约使用 `scheduled_ship_time`；已发货、已寄回、已完成使用 `ship_out_time`。返回行保留原状态、是否接力、物流与仓库信息以供批量发货单处理。
- 冲突详情接口返回每条重叠租赁的 `rental_id,customer_name,start_date,end_date,ship_out_time,ship_in_time,status`；批量冲突接口只返回去重并升序的设备 ID，最多查 500 台。编辑时传当前租赁 ID 排除自身。
- 疑似重复使用客户名或收件地址的**精确相等**条件（两者择一匹配），只查有效占用状态，最多返回最近 10 条；给了两端日期时还要求租赁日期窗口有交集。这只是创建前确认提示，不能代替库存冲突校验。

### 6. PC 与移动端页面契约

#### 6.1 甘特图与入口

- PC 甘特图从 `/api/gantt/data` 取得按仓库及日期窗口的主设备与主租赁；点击空档可打开“预定档期”，点击租赁可打开“编辑租赁记录”。移动端甘特点击租赁条先出现底部详情，再进入编辑；新建为独立页面。两端切换仓库都要重新加载，移动端还关闭旧详情。
- 移动甘特每条租赁有两层时间表达：浅色外层按寄出／收回占用时间（缺失时用租赁日期），内层按起租／还租日期；状态改变颜色。点击条形区域打开详情，不能把条上显示的轻量信息当编辑源。
- 创建、编辑、删除成功后刷新甘特。PC 同时刷新日统计与相关提醒；移动端返回当前仓库数据。失败保留原表单和用户输入，显示服务端错误消息。

#### 6.2 新建表单字段矩阵

| 业务字段 | PC“预定档期” | 移动端“新建租赁” | 数据规则 |
|---|---|---|---|
| 仓库 | 沿用当前仓库 | 沿用当前仓库；`all` 不可提交 | 写入具体 `warehouse_id` |

- PC 新建设备下拉显示设备名、型号、生命周期、档期可用性；生命周期非正常和已被本单其他台数选用的 ID 禁用。档期不可用会显示警告，实际提交仍由服务端严格拒绝。库存附件选项在查询到占用冲突后禁用。
- “查找档期”需先有型号、起止日期和非负物流天数；服务端候选按对应仓库、主机／附件类型和型号过滤，必须生命周期 `active`。PC 多台查找时跳过已被本单其他台选择的 ID；查询代次变化后，旧异步结果不得覆盖新条件。服务端按寄出日 19:00、收回日 12:00 校验，返回日期字符串；PC 把结果日期解析为零点再保存。这一边界不一致见“代码核对中发现的缺口”。
- 提交顺序：验证必填和每台设备 → 查询疑似重复并允许人工继续 → 估算顺丰时效，不足则允许人工继续 → 生成占用时间与所有台数请求 → 保存 → 读取最新详情 → 显示确认信息。确认框取消时不得写入。保存请求内容不变的重试沿用同一 UUID；表单内容变化生成新 UUID。

- 仅改变损坏备注不触发物流时效二次确认；当地址、主机、租期、物流天数或寄出时间的快照改变时，预留天数小于时效估计则提示“仍要保存／返回修改”。移动端运单查询调用 `/api/shipping/track/<trackingNo>`；PC 当前两个查询按钮没有接入实际查询，不能在复刻验收中把它们当作已工作功能。
- 成功保存后重新拉取完整详情显示确认信息；如果新详情失败，明确提示“保存成功，但确认信息加载失败”，不能让用户重复保存。关闭确认信息后返回甘特／刷新相应数据。

#### 6.4 客户确认信息精确格式

PC 与移动端均按以下顺序以换行符拼接。日期按 `YYYY-MM-DD` 显示；缺失或无效为“未填写”。电话已包含在地址的数字串内则不重复附加，反之在地址后添加 `，<电话>`。附件去重；识别“手机支架／phone”和“三脚架／tripod”后使用类别名。

```text
收货地址：<地址和电话或未填写>
寄出时间：<ship_out_time 的日期或未填写>
预计收货：<start_date - 1 天或未填写>
客户归还：<end_date + 1 天或未填写>
寄出型号：<设备型号或未识别型号> + <租赁组合或未填写租赁组合> + <镜头支架/手柄/库存附件类别，若没有则无附件>
```

同单时追加 `同单设备：已录 <recorded_quantity>/<expected_quantity> 台`，再按同单摘要顺序逐台追加 `第 N 台：<设备名> + <租赁组合> + <手柄/镜头支架/库存附件名称/代传照片>`。PC 与移动端都提供复制全部文字的操作。

### 8. 旧外部 API 的兼容边界

`/external-api/*` 除租户会话和写操作 CSRF 外还要求 `X-API-Key`。此路由返回旧格式错误 `{success:false,error:"..."}`，与 `/api/rentals/*` 的 `message` 不同；不能把两种协议混为一个客户端。外部接口也在当前租户库内执行。

| 方法与路径 | 当前行为 | 复刻限制 |
|---|---|---|
| `GET /external-api/rentals/<id>` | 200 `{success:true,data:<Rental.to_dict()>}`；不存在 404 `error` | 直接读当前租户记录，无仓库筛选参数 |
| `PUT /external-api/rentals/<id>` | 接受非空 JSON，仅写非空 `ship_out_time,ship_in_time` 和存在的 `status`，提交后返回详情 | 不走主表单库存／同单校验；无状态枚举的处理器级验证；解析或数据库异常以 500 `error` 返回 |
| `POST /external-api/rentals/<id>/cancel` | 调旧服务 `can_cancel()` 规则，仅 `not_shipped` 或未逾期的 `shipped` 可取消 | 与主表单编辑为 `cancelled` 的入口不同；请按旧服务结果返回 |
| `POST /external-api/rentals` | 当前路由未传旧服务必需的寄出／收回时间位置参数，实际会失败 | 属于已知实现缺口，不作为可用的创建入口；复刻当前行为时不能误称其已可创建 |

### 9. 固定数据验收样例

下面的 ID 是**测试夹具**，用来验证复刻实现的行为，不要求生产数据库存在这些 ID。每例从干净租户数据库开始或明确继承上一例。设置仓库 `W=3`、主机型号 `M=9`（显示名 `X300U`）、主机 `D101` 名 `机身2`、`D102` 名 `机身10`、`D103` 名 `机身1`（生命周期 `sold`），库存手机支架 `A201` 与三脚架 `A202`；其余设备均 `active` 且在 W。另一型号 `M=10` 显示名 `X200U`、主机 `D104` 名 `机身3`。请求都携带当前租户会话及写请求的 CSRF Token。

| 编号 | 初始记录／操作 | 必须观察到的结果 |
|---|---|---|
| F01 自然排序 | 将 `D104,D102,D101,D103` 放入同一设备下拉 | 先 `X200U` 的 `D104`，再 `X300U` 的 `D103,D101,D102`；同型号 `机身2` 在 `机身10` 前。排序遵循 `Intl.Collator('zh-CN',{numeric:true,sensitivity:'base'})`。 |
| F02 占用与新建 | 先存在主租赁 `R500(D102,10月10日至12日,ship_out=10月8日09:00,ship_in=10月14日18:00,status=not_shipped)`；再请求新建 `D102`、10月11日至12日且物流占用重叠 | 返回 HTTP 409、`code=DEVICE_UNAVAILABLE`；不产生新主租赁或子租赁。 |
| F03 边界相接 | 沿用 F02 的 `R500`，请求同一 `D102` 的有效占用起点恰好为 `10月14日18:00` 且终点更晚 | 不因 `R500` 判为冲突；仍需通过日期、生命周期、仓库等其余校验。 |
| F04 对换主机 | 已有相同时段 `R500→D102` 和 `R501→D101`；先 PUT `R501.device_id=D102`，再 PUT `R500.device_id=D101`，均保留 W 和起止时间 | 两次编辑都成功；最终两条有效租赁在相同档期各有目标设备。中途两条占同一实物被允许，编辑下拉在第一步后显示冲突。 |
| F05 生命周期与档期独立 | `D103` 已售出，并是历史租赁 `R502` 当前设备；为 `R502` 只改损坏备注，再从另一租赁尝试选 `D103` | 前者保留当前设备并成功；后者下拉显示“已售出”且不可选择，服务端直接请求也拒绝 `409 DEVICE_UNAVAILABLE`。即使 `D103` 同时冲突，两个状态标签都应可见。 |
| F06 库存附件仍严格 | `A201` 已被有效租赁在同一占用区间使用；编辑 `R501` 选择 `A201` | 返回 HTTP 409、`code=DEVICE_UNAVAILABLE`，`R501` 主机、时间、备注和子租赁全保持原值。 |
| F07 同单分摊 | 一个新订单请求 `D101+D102`，总金额 `101.01` 元，两个附件分别为 `A201,A202`，请求 UUID 合法 | 只生成一个 `RentalBooking`、两条主租赁和两条附件子租赁；按请求顺序主租赁金额为 `50.51,50.50`；`recorded_quantity=2`，`shipped_quantity=0`。 |
| F08 幂等 | F07 的 UUID 与完整 JSON 原样重发；随后仅将金额改为 `102.00` 而继续用该 UUID | 原样重发返回相同主租赁 ID，不增加记录；改内容返回 400 和“此请求已保存，请刷新后重新操作”。 |
| F09 状态分歧 | 对 F07 第一台调用独立状态接口写 `scheduled_for_shipping`，随后在编辑 PUT 中写相同状态 | 独立接口返回 400；通用编辑保存成功，附件子租赁状态同步。 |
| F10 删除 | 对带 `A201` 的主租赁 DELETE，再查主／子 ID | 主／子都不存在；若只 DELETE 子 ID，主仍可查。 |
| F11 详情与甘特 | 一条主租赁带手机支架、手柄布尔值和同单关系，GET 详情、GET 甘特 | 详情 `accessories` 只含手机支架设备摘要，`includes_handle=true`，有 `child_rentals` 与 `booking`；甘特只列主租赁且展示配套＋库存附件信息。 |
| F12 确认文案 | 租赁起租 `2026-10-10`、还租 `2026-10-12`、寄出 `2026-10-08 09:00`、地址中已有电话 `13800000000`、设备型号 `X300U`、组合“裸机”、无附件 | 前五行分别为地址原文、`寄出时间：2026-10-08`、`预计收货：2026-10-09`、`客户归还：2026-10-13`、`寄出型号：X300U + 裸机 + 无附件`；电话不重复。 |
| F13 会话过期 | 从甘特打开编辑前使 `tenant_session` 过期，再触发租赁 API；重新登录后继续访问原页面 | API 返回 401 `AUTH_REQUIRED`；客户端进入登录页，并在成功登录后恢复原目标路由。此场景是系统登录契约对租赁界面的要求，具体认证页面仍需认证模块规格。 |

对于 F01，中文／英文混合型号的扩展夹具须以 `Intl.Collator` 的实际输出为准，不能按 ASCII 臆测。对于 F04，“先换第一台”阶段产生刻意的重叠，因此编辑界面必须提醒操作员，服务端不得以主机重叠阻断。所有写入失败样例都应再次读取数据库确认事务回滚。

### 11. 租赁界面依赖的最小设备契约

本节只定义租赁页面要读取的设备数据，不代替完整设备管理规格。

- `GET /api/devices?is_accessory=false&warehouse_id=<id>&page=1&per_page=100` 返回**直接分页对象** `{devices,total,pages,current_page,per_page,has_next,has_prev}`，此旧查询路径没有 `success/data` 壳。`is_accessory=true` 查库存附件；省略生命周期过滤时返回正常、售出、损坏、停用、退役设备，编辑下拉才能显示历史状态。`per_page` 上限 100，客户端须翻页读取全部备选，不得把第一页误当完整清单。`status` 参数已移除，应使用 `lifecycle_status`。查询结果原始数据库顺序是生命周期日期／创建时间降序，租赁下拉必须在客户端另按第 1 节自然排序。
- 每条设备 JSON 含 `id,name,serial_number,model,model_id,device_model,is_accessory,warehouse_id,lifecycle_status,lifecycle_reason,lifecycle_date,created_at,updated_at`。`lifecycle_status` 只允许 `active,sold,decommissioned,damaged,retired`；租赁新选可用的只有 `active`。设备当前仓库和租赁履约仓库必须相同；设备移仓或售出后，历史租赁仍可读取，编辑选择不变时按 5.3 节保留。
- `GET /api/device-models` 返回 `{success:true,data:[...]}`，顶层列表只含启用的主设备型号，主型号的 `accessories` 嵌套数组只含启用的附件型号。型号 JSON 至少含 `id,name,display_name,is_active,is_accessory,parent_model_id,default_accessories,device_value,allowed_lens_combos,default_lens_combo,rental_packages,default_rental_package_id`；`accessories` 只在主型号上有。设备自身可关联 `device_model` 对象；若 `model_id` 为空或型号关联不可用，租赁显示与排序回退旧 `model` 字符串。
- 库存附件类型在租赁界面用设备 `name` 和 `model` 中是否包含“手机支架／phone”或“三脚架／tripod”识别。甘特展示数组又带 `type`、`is_bundled`：配套手柄／镜头支架 `is_bundled=true` 且没有库存 ID；库存附件 `is_bundled=false` 且有 `id,serial_number,name,type`。任何未知库存附件仍按通用设备 ID 参与服务端占用校验，界面上的两个专用选择器未必能展示它。
