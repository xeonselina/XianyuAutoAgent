# 跨模块复刻验收旅程

## Purpose

单个页面或 API 正确仍可能把不相关功能改坏。本规格把控制库、设备、租赁、排期、发货、验货、接力、统计和两端登录串成可重复的端到端旅程。具体字段及错误语义由相应领域规格定义；此处约束跨模块结果。

## Requirements

### Requirement: 新租户从平台创建后形成完全隔离的可操作店铺

复刻实现 MUST 能由平台管理员登录、创建租户、生成控制库租户与管理员成员、创建独立业务库、迁移并得到初始仓库；租户成员再用配置的密码或短信方式登录，读取 `/auth/me`、`/api/warehouses` 并进入 PC 甘特。再建第二个租户，用相同 API 读设备／租赁时不可看到第一租户任何业务行，第一租户成员手机号也不能被第二租户复用。

#### Scenario: 两租户相同业务 ID
- **WHEN** A、B 两个店铺各自存在 `devices.id=1`，A 添加租赁并切换浏览器到 B 会话
- **THEN** B 的设备 1 只对应 B 的设备记录，B 甘特和客户历史不包含 A 的租赁

### Requirement: 登录过期恢复原页面及其参数

PC 与移动端 MUST 在业务 API 返回 401 `AUTH_REQUIRED` 时清理旧会话并跳到 PC 登录页，`next` 保留当前内部路径、query 和 hash；重新登录同一店铺后回到原位置。`next` 不得接受外站或平台管理路径。受限租户（暂停、到期、未完成开通）按访问状态进入受限页，不能把 403/503 误当作普通 Cookie 过期继续无声重试。

#### Scenario: 移动编辑中会话到期
- **WHEN** 用户在 `/mobile/edit-rental/17?source=gantt#device` 保存时收到 401
- **THEN** 登录后返回该移动编辑地址；表单重新从业务 API 读取租赁，不能沿用失效会话的提交结果

### Requirement: 型号、设备、租赁和甘特以同一组身份关联

管理员建立主型号和可用租赁组合，操作员把两台有唯一序列号的 active 主设备放入具体仓库，再为其中一台创建租赁。业务库 MUST 保留 `model_id` 与旧 `model` 编码、设备当前仓、租赁履约仓、起止日及寄出／收回窗口；甘特出现一条主租赁，库存可用性按物流窗口排除已占用设备，客户历史可按电话找到该笔。编辑租赁换成第二台时，同一订单 ID、客户与同单关系保持，甘特和库存查询随设备 ID 更新。

#### Scenario: 两设备对换顺序保存
- **WHEN** 同期 A、B 两单各占设备 1、2，先把 A 编辑为设备 2，收到冲突提示但按允许重叠规则保存，再把 B 改为设备 1
- **THEN** 两次编辑保留原租赁 ID，最终甘特显示交换后的设备，客户历史订单数不变；冲突提示不等同于禁止编辑

### Requirement: 同一闲鱼订单的多设备数量贯穿提醒和发货

一笔闲鱼订单被声明需要两台主设备时，系统 MUST 创建或维护 `RentalBooking.expected_quantity`，在只录一台时于漏单快照显示 `1/2`，补齐第二台后不再显示欠录。两台租赁应共享订单归属且金额按分精确分摊；如同仓、同地址、同电话、同快递和同发货日，预约顺丰只生成一个包裹与一个运单，响应 `scheduled_count=2,shipment_count=1`。worker 到预约时刻按主租赁逐笔发货并改变相关子租赁状态；外部失败的那笔不能误标已发货。

#### Scenario: 同单补齐后预约
- **WHEN** 一笔需要两台的订单先录一台，后补一台并一次提交两台预约
- **THEN** 欠录提醒消失，两条主租赁指向同一 booking 和同一寄出运单，包裹数为 1

### Requirement: 设备出售和跨仓收货不抹去历史经营数据

已有租赁的设备被标 sold 后 MUST 保留设备、旧租赁、验货及客户历史；新租赁不能选择该非 active 设备。周期统计在生命周期日期之前计算在役天数和折旧；仓库过滤订单依历史履约仓，而设备分母依当前仓。已寄出主设备验货收回到另一仓时，检查项、主子租赁状态、物理仓库变更与修复预览摘要需一事务处理；历史租赁履约仓不因实物移动改写。

#### Scenario: 收货到新仓后看旧仓报表
- **WHEN** A 仓履约的旧单在 B 仓验货收回，随后设备出售
- **THEN** 旧单仍在 A 仓收入历史，设备当前仓在 B；出售日后的新租赁选择和统计在役分母排除该设备

### Requirement: 接力绑定阻止仓库重复发货

同设备相邻重叠的两主租赁进入 agreed 后 MUST 建不可分叉 binding；批量发货候选与预约均识别后单为接力后单，不能为它从仓库再次创建运单。首次进入 shipped 时将前单标 returned、后单写客户直寄运单并标 shipped；之后查询顺丰物流与闲鱼同步结果。接力 case 的运营状态与 binding 分表保存，状态回退时相应解除 binding。

#### Scenario: 后单同时出现在批量发货日期窗口
- **WHEN** 一笔已绑定的接力后单原本也满足普通发货日期筛选
- **THEN** 批量发货流程把它排除／拒绝预约，只有接力状态更新能写直寄单号

### Requirement: 客户、经营统计、审计和旧 API 的口径互不替换

客户历史 MUST 按归一化电话或姓名／买家 ID 关联全部租赁；周月经营统计只数未取消主租赁、按 booking 去重订单数、按设备租赁条数扣每单 15 元；旧每日统计快照保留自身最近 30 天和金额回退公式。移仓、验货修复、减租与接力写各自审计，不因统计刷新产生重复业务变更。外部 API 需要租户会话和 Key，其旧响应壳、410 已移除端点及未验证建单入口不能被内部新 API 语义覆盖。

#### Scenario: 一笔取消的子租赁与两台同单主租赁
- **WHEN** 报表、客户历史和旧统计快照读取同一批数据
- **THEN** 各自依上述代码口径计算；不能为了让三个数字相同而删除子租赁或修改订单

### Requirement: 同包裹预约与打印按票和设备分别计数

同仓两台同单主设备预约为一票后，PC 批量发货页面 MUST 显示两条设备行、一个唯一运单的面单按钮计数；打印时按票取一次顺丰 PDF 并由快麦打印地址联，再按设备各打一张内容联。顺丰取件／PDF 转图失败只影响当前包裹，不改预约租赁状态；快麦 B 仓未配置也不能借 A 仓 SN。批量响应同时保留 `total,parcel_count,waybill_success_count,slip_success_count,failed_count,results`，其计数单位不同。

#### Scenario: 双机一票、内容联局部失败
- **WHEN** A 仓双机共用一票，顺丰 PDF 和地址联成功、第二台内容联失败
- **THEN** 页面面单按钮计 `(1)`；结果为 2 台、1 票、1 张成功地址联、1 张成功内容联、1 台失败，两台仍保留原预约和运单

### Requirement: 切换仓库后过期页面响应不能覆盖当前视图

PC 和移动的仓库选择 MUST 影响设备、甘特每日统计、发货候选和可执行写操作；旧仓库异步请求晚返回时不能把其结果写进新仓页面。在 `all` 视图允许合并读取，但新增租赁、改设备生命周期、移仓、预约发货和打印都必须重新确定具体履约仓。仓库级顺丰与快麦密钥不会随着页面选择自动拷贝。

#### Scenario: A 仓请求晚于 B 仓返回
- **WHEN** 用户先打开 A 仓甘特又迅速切 B 仓，B 仓数据先到、A 仓数据后到
- **THEN** 设备行、每日统计和候选订单保持 B 仓数据；后续提交只可用 B 仓 ID

## 重建项目的对照方法

使用固定的控制库种子、两个租户、两个仓库、主机及附件型号、至少三台设备、带相同地址电话的双机闲鱼订单、重叠接力、跨仓验货、售出日期和失效会话。对原项目与重建项目执行同一旅程，逐步比对：HTTP 状态、响应 JSON 字段／错误码、各表行与关联、PC／移动路由、页面关键操作、后台任务之后的状态。外部顺丰、快麦、闲鱼与短信使用相同的可控模拟返回。对页面外观还需固定视口截图；仅靠静态文档无法给“99%”数值作证。

代码与测试依据：`tests/integration/{test_tenant_isolation,test_multi_device_booking,test_warehouse_rental_flow,test_batch_shipping_relay,test_inspection_warehouse,test_rental_stats_api,test_xianyu_order_alert_api,test_auth_api}.py`，以及本规格引用的各业务实现。该文件定义复刻验收步骤，不代表这些步骤已在一个新项目运行过。
