# 接力管理页设计

## 背景

当同一设备的前后两笔主 rental 在物流占用区间上重叠至少 2 天时，设备无法先回到店内，需要由前一位客户直接转寄给后一位客户。现有甘特图只能间接看到重叠，无法集中跟进客户通知、同意、寄出、物流和完成状态。

项目已有不可分叉的永久接力绑定和顺丰轨迹查询。新功能在这两项能力上增加独立的运营管理页，不改变 rental 日期或设备分配。

## 目标

- 自动识别物流区间重叠至少 2 天的相邻主 rental 组合。
- 在桌面端宽表和移动端卡片中展示完整客户、租期、设备组合、接力日期和物流信息。
- 管理待处理、已通知、已同意、已寄出和已完成的人工流程。
- 在已同意阶段与现有永久接力绑定保持一致。
- 复用现有顺丰 SDK，使用前单客户手机号后四位查询转寄运单。

## 非目标

- 不支持顺丰以外的快递公司。
- 不自动创建运单或向客户发送消息。
- 不根据顺丰签收自动完成接力。
- 不通过后台定时任务物化全部待处理候选。

## 候选识别和日期口径

候选仅在同一设备上的主 rental 中识别。排除已取消 rental，按 `ship_out_time` 和 ID 稳定排序，仅比较相邻组合。定义：

- `overlap_days = predecessor.ship_in_time.date - successor.ship_out_time.date`
- `overlap_days >= 2` 时为潜在接力。
- 前单应寄出日 = 前单 `end_date + 1 天`。
- 后单收货日 = 后单 `start_date - 1 天`。

没有管理记录的当前候选以虚拟“待处理”返回，第一次状态变更时再持久化，避免 GET 查询产生写入或引入定时同步任务。

## 数据设计

新增 `rental_relay_cases` 表，前后 rental 组合唯一，主要字段包括：

- `predecessor_rental_id` 和 `successor_rental_id`
- `status`: `pending`, `notified`, `agreed`, `shipped`, `completed`
- `sf_tracking_number`
- `sf_tracking_status`, `sf_tracking_summary`, `sf_last_checked_at`
- `notified_at`, `agreed_at`, `shipped_at`, `completed_at`
- `created_at`, `updated_at`

永久接力约束仍由现有 `rental_relay_bindings` 负责。上线迁移会为每个现有绑定创建一条 `agreed` 管理记录。

## 状态与绑定

主流程是 `pending -> notified -> agreed -> shipped -> completed`。界面允许正向推进和经确认后回退。状态更新会清理目标阶段之后的时间戳。

- 进入 `agreed` 或之后状态时，必须在同一事务中创建或保持永久绑定。
- 从 `agreed` 或之后回退到 `pending` 或 `notified` 时，在同一事务中删除永久绑定。
- 新进入 `agreed` 前重新验证候选。档期已失效或前后 rental 已被其他绑定占用时拒绝更新。
- 进入 `shipped` 必须提供非空顺丰运单号。
- `completed` 只能由运营人员手动设置。

## 档期变化

每次列表和状态更新都根据当前 rental 重新判定候选。

- 不再满足条件的虚拟待处理组合不再显示。
- 已持久化且仍为 `pending` 的失效组合不显示。
- `notified` 及之后的失效组合仍显示，并返回 `schedule_changed` 警告。
- 失效组合不允许新进入 `agreed`；已有绑定保留，直到运营回退状态或完成处理。

## 顺丰物流

将现有顺丰客户端初始化、轨迹查询和响应解析抽取为共享服务。接力运单查询使用前单 `customer_phone` 的后四位作为顺丰验证信息。

保存 `shipped` 后立即尝试查询。成功时缓存状态摘要和查询时间；无轨迹、缺手机号或顺丰不可用时仍保存已寄出状态，并在列表中显示可重试原因。界面支持单条和当前页批量刷新，顺丰签收不自动修改接力状态。

## API

- `GET /api/relay-cases`: 接受多个状态、前单应寄出日范围、页码和每页条数，返回虚拟待处理与已持久化记录的合并列表。
- `PUT /api/relay-cases/<predecessor_id>/<successor_id>`: 新建或更新组合状态，必要时接受顺丰运单号。
- `POST /api/relay-cases/<case_id>/tracking/refresh`: 刷新单条物流缓存。
- `POST /api/relay-cases/tracking/refresh-batch`: 刷新请求中当前页的已寄出或已完成记录。

列表项直接包含前后客户的租期、地址、电话、`buyer_id` 昵称、`customer_name` 收件人、型号、镜头组合、附件、接力日期、物流摘要和档期警告，前端不逐行补查 rental。

## 桌面端页面

新增 `/relay-management`，从甘特图“更多”菜单进入。页头包含待办数和当前页物流刷新。

状态为多选筛选，默认选中除“已完成”外的四个待办状态。“寄出时间范围”筛选前单应寄出日，默认为服务端本地今日 T-3 至 T+5。

桌面端使用紧凑宽表，展示状态、设备/镜头/附件、前单客户和租期、应寄出日、重叠天数、后单客户和租期、收货日、顺丰摘要和状态操作。状态和操作列固定；13 寸屏幕允许横向滚动，4K 屏幕尽量同屏。服务端默认每页 50 条。

## 移动端页面

新增 `/mobile/relay`，底部标签栏增加“接力”。移动端是独立设计的操作工作台，不复用桌面表格布局：顶部提供状态快捷筛选和日期预设；卡片首屏突出应寄出日、前后客户、配置差异与当前状态；电话可直接拨打，完整地址和租期按需展开；物流与状态更新使用不小于 44px 的双主操作。状态变更和运单录入使用底部弹层。两端共用同一 API。

桌面宽表和移动卡片都会比较前后设备配置。若镜头组合不一致，或后单附件数组长度大于前单，设备区域显示黄色 `⚠` 告警并列出具体原因；两项同时满足时合并展示。

## 错误处理

- 状态更新前重新验证 rental 组合。
- 状态、永久绑定和审计记录在同一事务中提交，任何失败全部回滚。
- 顺丰查询与状态事务解耦，物流失败不撤销“已寄出”。
- 列表为空、部分物流刷新失败、档期变化和绑定冲突都使用明确的中文状态或错误提示。

## 测试与验收

- 单元测试覆盖 1 天不命中、2 天命中、相邻主 rental、取消和附件排除、日期计算、档期失效、状态变更和绑定原子性。
- API 测试覆盖状态多选、寄出日范围、分页、历史绑定迁移、顺丰成功、无轨迹、缺手机号和服务失败。
- 桌面端和移动端组件测试覆盖默认筛选、信息渲染、状态回退确认、已寄出运单必填、物流刷新和错误提示。
- 最终运行相关 pytest、两套前端 Vitest、类型检查和生产构建，并检查 13 寸、4K 和移动宽度下的布局。
